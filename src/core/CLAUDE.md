# CLAUDE.md — src/core/

세션 JSONL의 파싱·그래프 구축·타입 정의. **타입과 스키마의 단일 진실.**

`src/cli/`와 `src/web/` 어느 쪽도 이 디렉터리를 단독 소유하지 않는다. 변경은 루트 CLAUDE.md의 "인터페이스 변경 게이트" 절차를 따른다.

## 이 스코프의 책임

- JSONL 한 줄 → 레코드 파싱
- uuid 인덱스 + 부모/자식 관계 구축
- 중복 레코드 처리
- 세그먼트(컴팩트 경계로 나뉜 조각) 식별
- orphan·root 판정
- 위 결과를 질의하는 순수 함수 제공

## 이 스코프가 하지 않는 것

- **파일 쓰기.** 이 디렉터리의 어떤 함수도 파일을 수정하지 않는다. 쓰기는 `src/cli/`가 한다
- 출력 포매팅. 사람이 읽는 문자열을 만들지 않는다 — 자료구조만 반환한다
- 프로세스 종료. `process.exit()`를 호출하지 않는다. 오류는 throw한다

## 인덱스는 본문을 담지 않는다

세션 파일은 노드 수에 비해 본문이 압도적으로 크다 — 실측한 한 파일은 86,668줄 중 distinct 노드가 10,726개뿐이고, 중복을 제거해도 본문이 수백 MB다.

따라서 인덱스에는 **구조 필드와 바이트 오프셋만** 담는다:

```
uuid → { parentUuid, type, subtype, timestamp, lineNo, byteOffset, byteLength }
```

본문이 필요하면 오프셋으로 `seek`해서 그때 읽는다. 전체 파일을 문자열로 메모리에 올리지 않는다. 이것이 대형 세션에서 기존 도구들이 느려지는 이유였다.

## 중복 레코드 처리

같은 uuid가 여러 번 출현한다 (실측: 한 파일에서 최대 23회, 전체 줄의 84%가 중복). 출현마다 `parentUuid`가 다른 경우도 있다.

**임의로 하나를 고르지 않는다.** 어떤 출현을 채택할지는 Spec 문서에 명문화된 정책을 따르고, 정책이 없는 케이스를 만나면 그 사실을 결과에 포함해 보고한다.

이 규칙이 있는 이유: 정책만 달리한 세 구현이 같은 파일에 대해 세 가지 답을 냈고, 그중 하나는 끊긴 노드가 있는데도 "문제 없음"을 보고했다. 상세는 [ADR-0004](../../docs/adr/ADR-0004-schema-drift-defense.md).

## 시끄러운 실패

정상 세션에서 성립할 수 없는 상태를 만나면 **0이나 빈 결과를 반환하지 않고 throw한다.**

- uuid를 가진 레코드가 있는데 부모를 가진 레코드가 하나도 없음 → 스키마 변경 의심, 중단
- 알려진 필드 집합을 벗어난 키가 다수 등장 → 경고

`orphans: 0`처럼 "문제 없음"을 뜻하는 값이 곧 고장의 증상이기도 한 구조에서는, 값이 아니라 불변식으로 판정해야 한다.

## 테스트

새 계산 로직(`buildIndex`, `findSegmentForUuid` 등)은 **TDD 순서**로 만든다 — 기대 출력(픽스처)을 먼저 작성하고 구현으로 통과시킨다. 구현 결과에 맞춰 기대값을 사후에 고치는 **스냅샷 갱신 함정**에 빠지지 않는다.

- 픽스처는 작은 합성 JSONL이어도 된다. 실제 세션에서 추출한 대형 픽스처가 없다고 시작을 미루지 않는다
- 기대값은 사람이 직접 계산해 픽스처와 함께 커밋한다. 구현이 아직 없어도 된다
- 픽스처는 `test/fixtures/`에 있고, **익명화본만** 쓴다 (루트 CLAUDE.md "픽스처 정책" 참고)

기대 수치를 못박아 스키마·정책 변경이 조용히 통과하지 못하게 한다.
