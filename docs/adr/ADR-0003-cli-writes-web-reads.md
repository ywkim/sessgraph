# ADR-0003: 웹은 읽기 전용이고 쓰기는 CLI가 단독으로 수행한다

## Status

Accepted

## Context

이 도구는 세션 구조를 보여주는 웹 뷰어와, 끊긴 체인을 잇는 수술 기능을 함께 갖는다. 수술 대상을 고르려면 39개 조각 중 어디를 이을지 눈으로 봐야 하므로, "웹에서 고르고 CLI가 실행한다"는 구성이 자연스러워 보인다.

이 구성은 웹과 CLI 사이에 핸드오프 포맷(패치 파일)을 요구한다.

## 후보 기술 & 각 선택지

**후보1: 웹이 수술 계획을 패치 파일로 내보내고 CLI가 적용**

- 장점: 웹에서 시각적으로 고를 수 있음. 패치 파일이 "무엇을 왜 했는지" 기록으로 남음
- 단점: 포맷을 설계·버저닝·검증해야 함. 웹이 읽기 전용이 아니게 됨

**후보2: 웹은 읽기 전용, 수술은 CLI에서 직접 지정**

- 장점: 핸드오프 포맷이 불필요. 웹의 공격 표면이 0
- 단점: 대상 uuid를 사람이 CLI로 옮겨야 함

**후보3: 웹이 로컬 서버를 통해 직접 파일 수정**

- 장점: 가장 편함
- 단점: 브라우저에서 온 요청이 사용자 홈 디렉터리의 세션 파일을 수정하게 됨. 로컬 바인딩이어도 CSRF·확장프로그램 등 표면이 생김

## Decision

웹 뷰어는 읽기 전용으로 한정하고, 파일을 수정하는 모든 동작은 CLI 명령으로만 수행한다. 웹과 CLI 사이에 중간 파일 포맷을 두지 않는다.

## Rationale (선택 이유)

패치 파일은 "웹에서 계획하고 CLI가 적용한다"는 핸드오프를 전제로만 정당화된다. 웹이 읽기 전용이면 **그 핸드오프 자체가 존재하지 않으므로**, 패치 파일은 CLI가 써서 CLI가 다시 읽는 파일이 된다. 직렬화했다 역직렬화하는 순수 왕복 비용이고, 적용 전 검토 목적이라면 `--dry-run` 출력으로 충분하다.

웹이 담당하는 것은 "어디가 끊겼는가"를 보여주는 일이고, 그 결과를 CLI로 옮기는 매개는 클립보드로 충분하다. 뷰어는 각 절단 지점에 **복사 가능한 CLI 명령어**를 함께 표시한다.

세션 파일에는 자격증명과 개인정보가 들어 있다. 이 파일을 수정할 권한을 브라우저에서 도달 가능한 경로에 두지 않는 것이 기본값으로 옳다.

## Consequences

### 장점

- 웹 서버가 읽기만 하므로 파일을 훼손할 경로가 없다
- 유지보수할 포맷이 하나 줄어든다
- 수술 이력이 셸 히스토리와 수술 로그에 남아 재현 가능하다

### 단점 & 트레이드오프

- 대상 uuid를 웹에서 CLI로 사람이 옮겨야 한다 (클립보드)
- 여러 지점을 한 번에 고르는 작업이 CLI 인자 나열이 된다

### 향후 기능이 따를 원칙

- `src/web/`은 파일 쓰기 API를 갖지 않는다. 서버는 `localhost`에만 바인딩한다
- 쓰기 명령은 기본 `--dry-run`이고 `--commit`이 있어야 실제로 쓴다
- 수술 실행 시 `{세션}.surgery.log`에 append-only 한 줄을 남긴다 — 무엇을 왜 바꿨고 백업이 어디인지. 이 로그는 파싱해서 되먹이는 포맷이 아니라 사람이 읽는 기록이다

## 언제 이 결정을 다시 검토할 것인가?

- 한 번에 수십 개 지점을 이어야 하는 사용 패턴이 실제로 생겨 CLI 인자 나열이 한계에 부딪힐 때
- 여러 기기에서 같은 수술을 재현해야 하는 요구가 생길 때
