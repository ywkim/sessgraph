# ADR-0007: 직접 구현과 기존 도구 도입을 "다져진 엣지 케이스"로 판별한다

## Status

Accepted

## Context

이 리포는 런타임 의존성이 0개다. 그런데 `package.json`에 `dependencies` 키가 없는 것은 **결정이 아니라 현재 상태**였다 — ADR 6건과 `src/web/CLAUDE.md`를 전수 확인했을 때 의존성 정책을 다룬 문서가 없었다. [ADR-0001](ADR-0001-typescript-single-language.md)의 "새 언어를 도입하지 않는다"는 언어에 대한 제약이지 라이브러리에 대한 제약이 아니다.

정책이 비어 있으면 두 방향의 실패가 모두 열린다. 근거 없이 "이 리포는 바닐라로 간다"고 단정해 이미 여러 해 다져진 문제를 다시 밟거나, 반대로 브라우저가 이미 네이티브로 제공하는 기능 위에 불필요한 의존성을 얹는다.

이 공백은 모바일 반응형 작업에서 실제로 드러났다. 390px 뷰포트에서 노드 목록의 본문 미리보기가 위 노드의 uuid와 겹치는 버그를 발견했고, 원인은 `src/web/app.ts`의 `ROW_HEIGHT = 52`가 `.node`의 CSS 높이와 암묵적으로 동기화되어 있는데 좁은 폭에서 uuid 36자가 여러 줄로 감기면서 그 가정이 깨진 것이었다. 이때 "브레이크포인트마다 행 높이 상수를 하나씩 준다"는 안이 나왔는데, 이것은 가변 높이 가상 스크롤을 조악하게 흉내내는 것이었다.

## 후보 기술 & 각 선택지

**후보1: 의존성 0개를 원칙으로 명문화 (전면 직접 구현)**

- 장점: 빌드 파이프라인이 `tsc` 둘 + `copy-web-assets.js` 하나로 유지된다. 공급망 위험이 없다
- 단점: 가변 높이 가상 스크롤처럼 **실사용으로만 발견되는 엣지 케이스**를 직접 다시 밟는다. 관측된 것만 해도 미측정 행 추정으로 인한 스크롤 튐, 위로 스크롤 시 앵커 흔들림(scroll anchoring), `ResizeObserver` 타이밍, 빠른 스크롤 시 overscan 오차가 있다. 이 실패들은 첫 구현에서 대개 드러나지 않고 나중에 사용자 리포트로 발견된다

**후보2: 프런트엔드 프레임워크·유틸리티 라이브러리를 폭넓게 도입 (React + Tailwind + 가상 스크롤 라이브러리)**

- 장점: 검증된 해법을 그대로 쓴다
- 단점: 번들러가 없는 현재 빌드에 Vite 등이 따라 들어오고, `scripts/copy-web-assets.js`가 하던 일과 `serve`의 정적 서빙 루트 가정이 통째로 바뀐다. 그리고 도입 대상 중 상당수는 재발명 회피가 아니다 — CSS 커스텀 프로퍼티·`clamp()`·`@container`는 브라우저 벤더가 직접 검증한 네이티브 스펙이고, 그 위의 라이브러리는 네이밍 레이어를 한 겹 더할 뿐 회피할 엣지 케이스가 애초에 없다

**후보3: "다져진 엣지 케이스가 실재하는가"를 판별 기준으로 삼는다**

- 장점: 두 실패를 모두 막는다. 판별이 도구 인기도나 취향이 아니라 관찰 가능한 질문 하나로 환원된다
- 단점: 케이스마다 판단이 필요해 기계적으로 적용되지 않는다

## Decision

직접 구현과 기존 도구 도입은 **"그 문제에 여러 해에 걸쳐 다져진 엣지 케이스가 실재하는가"**로 판별한다. 실재하면 기존 도구를 쓰고, 문제의 본체가 이미 플랫폼(브라우저·Node 표준)에 있으면 직접 쓴다.

## Rationale (선택 이유)

후보1과 후보2는 같은 오류의 두 얼굴이다 — 판별 없이 한쪽을 기본값으로 두는 것이다. "직접 구현이 낫다"는 Not Invented Here에 빠지고, "라이브러리가 낫다"는 이미 해결된 것 위에 레이어를 쌓는다.

판별 기준이 "인기 있는가"나 "의존성이 적은가"가 아니라 **엣지 케이스의 실재 여부**여야 하는 이유는, 그것만이 직접 구현의 비용을 실제로 예측하기 때문이다. 가변 높이 가상 스크롤은 정상 경로가 짧고 예외 경로가 길다 — 그래서 첫 구현이 동작해도 틀렸을 수 있다. 반대로 `clamp()`는 예외 경로가 브라우저 안에 있고 호출부에는 없다.

이 구분은 [ADR-0004](ADR-0004-schema-drift-defense.md)가 다룬 실패 모드와 같은 종류다 — **조용히 틀리는 것**이 시끄럽게 실패하는 것보다 비싸다. 직접 구현한 virtualization은 조용히 틀린다(스크롤이 약간 튈 뿐 예외를 던지지 않는다). 그래서 여기서는 검증 비용을 외부화하는 편이 낫다.

의존성 0개 자체는 목표가 아니다. 다만 의존성을 늘릴 때 이 리포에서 실제로 지불하는 비용은 번들러 부재라는 구조적 사실에서 온다 — 이는 취향이 아니라 관찰이므로 후보2의 단점에 그대로 남긴다.

## Consequences

### 장점

- 의존성 논쟁이 "바닐라 대 프레임워크"가 아니라 "이 문제에 다져진 엣지 케이스가 있는가"라는 답할 수 있는 질문이 된다
- 브라우저 네이티브 기능(CSS 커스텀 프로퍼티, `clamp()`, `@container`, 논리적 속성)을 라이브러리 없이 쓰는 것이 이 기준에서 정당화된다 — 회피할 엣지 케이스가 없기 때문이다
- 반대로 가변 높이 가상 스크롤이 실제 요구가 되면, 직접 구현하지 않고 기존 도구를 도입할 근거가 미리 마련된다

### 단점 & 트레이드오프

- "엣지 케이스가 실재하는가"는 조사를 요구한다. 모르는 영역에서는 **엣지 케이스가 없다고 단정하지 말고 "확인 안 됨"으로 두고 조사한다**
- 이 기준은 도입 시점의 비용만 다루고 유지 비용(버전 업, 폐기된 라이브러리)은 다루지 않는다. 그것은 도입을 결정한 뒤의 별도 판단이다

### 향후 기능이 따를 원칙

- 직접 구현을 제안하기 전에 "이 문제에 다져진 엣지 케이스가 있는가"를 먼저 답한다. 답이 "있다"면 기존 도구를 검토한 근거를 남긴다
- 라이브러리 도입을 제안하기 전에 "문제의 본체가 이미 플랫폼에 있는가"를 먼저 답한다. 플랫폼 기능 위의 네이밍 레이어는 도입 근거가 되지 않는다
- 런타임 의존성을 처음 추가할 때는 번들러 부재와 `serve`의 정적 서빙 구조에 미치는 영향을 함께 평가한다
- 제약을 설계로 격상시켜 문제를 없앨 수 있으면 그쪽을 먼저 본다 — 예: 행 높이를 콘텐츠와 무관한 상수로 만들면 가변 높이 virtualization 자체가 필요 없어진다

## 언제 이 결정을 다시 검토할 것인가?

- 번들러를 도입하게 되어 후보2의 전환 비용 계산이 달라질 때
- 런타임 의존성이 여러 개로 늘어 개별 판단만으로는 전체 표면을 통제할 수 없을 때
