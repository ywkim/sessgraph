# ADR-0006: CLI 출력에 응답 봉투와 안정 오류 코드를 도입한다

## Status

Accepted

## Context

이 도구를 실행하는 주체가 사람만이 아니게 됐다. 대화 도우미가 명령을 구성하고 결과를 해석해 다음 조치를 정하는 경로가 실사용에서 이미 일어난다.

지금까지 각 명령의 `--json`은 "사람이 읽는 문장 대신 기계가 읽는 JSON을 낸다"고만 명세돼 있었고(`inspect`/`verify` Spec), 실패를 어떻게 표현할지, 명령마다 형태가 같을지는 정의되지 않았다. 실제로 이미 어긋난 지점이 있다: `reattach`는 중복 오류에서 "먼저 `inspect --json`으로 확인하세요"라고 자연어로 안내하는데, `inspect`는 이 시점까지 구현되지 않아 그 안내를 따르면 반드시 실패한다.

자연어 실패 메시지를 분기 근거로 쓰면, 메시지 문구를 다듬는 것과 호출자를 깨뜨리는 것이 같은 행위가 된다. 이 도구는 되돌리기 어려운 쓰기 작업(`reattach --commit`)을 수행하므로([ADR-0002](ADR-0002-record-preserving-reattach.md)), 실패 사유를 잘못 분류한 채 다음 조치를 취하는 비용이 크다.

## 후보 기술 & 각 선택지

**후보1: 자연어 출력을 유지하고 호출자가 해석하게 둔다 (현재 상태)**

- 장점: 추가 구현 없음
- 단점: 실패 분기가 메시지 문구에 묶인다. 메시지를 못 고치는 상태로 굳는다. 존재하지 않는 조치를 안내해도 아무 검사도 막지 못한다 — 실제로 이미 발생

**후보2: 명령마다 자유 형식 JSON을 낸다**

- 장점: 명령별로 최적화된 형태 가능
- 단점: 호출자가 명령마다 다른 파싱 규칙을 익혀야 한다. "성공했는가"라는 가장 기본적인 판정조차 명령별 분기가 된다 — ADR-0004가 다룬 "같은 사실이 여러 형태로 갈리는" 실패의 재현

**후보3: 공통 응답 봉투(envelope) + 안정 오류 코드 열거 + 명령 레지스트리 단일화**

- 장점: 성공/실패 판정이 `ok` 필드 하나로 모든 명령에서 동일. 실패 사유는 문자열 코드로 구분되어 메시지 문구 변경에 영향받지 않는다. `nextActions`가 가리키는 명령이 실재하는지 테스트로 강제 가능(레지스트리가 단일 진실이므로)
- 단점: 새 타입(`CommandEnvelope`, `ErrorCode` 등)을 `src/core/types.ts`에 추가해야 하고, 기존 `reattach` 에러 메시지와 코드를 대응시키는 유지보수 지점이 하나 늘어난다

## Decision

CLI의 모든 명령이 `--json`에서 공통 `CommandEnvelope<T>` 형태로 응답하고, 실패 사유는 안정 `ErrorCode` 문자열로 구분한다. 명령 정의(`positionals`/`options`/설명)는 `src/cli/registry.ts` 한 곳에 두고, 인자 파싱·디스패치·`schema` 명령 출력이 모두 이 정의에서 파생된다. 정확한 타입과 규칙은 [Spec: 기계 판독 출력 규약](../spec/20260903-1218-machine-readable-output.spec.md)이 정의한다.

## Rationale (선택 이유)

후보1은 이미 실패로 관측됐다(존재하지 않는 명령 안내). 후보2는 ADR-0004가 이미 거부한 실패 형태(같은 사실의 다중 표현)를 응답 계층에서 재현한다. 후보3만이 "실패 사유 구분"과 "다음 조치 안내"를 메시지 문구에서 분리해, 문서가 아니라 타입과 테스트로 강제할 수 있게 한다 — 루트 CLAUDE.md "규칙 추가 게이트"가 요구하는 기계 검사로의 전환과 같은 방향이다.

## Consequences

### 장점

- 실패 판정과 사유 구분이 문구 변경에 영향받지 않는다
- `nextActions`가 존재하지 않는 명령을 가리키는 것을 테스트가 막는다 — 이번에 실제로 발생한 실패 유형에 대한 직접적 방어
- 명령 정의가 한 곳(`registry.ts`)에만 있어, 새 플래그 추가 시 발견 경로(`schema`)가 자동으로 갱신된다

### 단점 & 트레이드오프

- 미구현 명령(`inspect` 등)은 레지스트리에 등록할 수 없으므로, `reattach`의 기존 안내 문제는 이 결정만으로 즉시 해소되지 않는다 — `inspect` 구현이 선행 조건이다
- `CommandEnvelope`가 감싸는 명령 고유 결과 타입(`IndexResult` 등)은 변경하지 않는다는 전제이므로, 봉투 도입이 기존 골든 픽스처 테스트에 영향을 주지 않아야 한다는 제약이 추가된다

### 향후 기능이 따를 원칙

- 새 명령을 추가할 때는 레지스트리에 먼저 등록하고, 그 등록에서 인자 파싱·`schema` 출력·디스패치를 파생시킨다. 세 곳을 따로 유지보수하지 않는다
- 실패를 안내할 때 자연어 문장에만 다음 조치를 적지 않는다. `nextActions`에 실행 가능한 명령 문자열로 넣고, 그 명령이 레지스트리에 실재하는지 테스트로 검증한다
- 새 실패 유형이 생기면 `ErrorCode`에 새 값을 추가한다. 기존 코드 값의 의미를 바꾸지 않는다(값 추가는 하위 호환, 의미 변경은 아님)

## 언제 이 결정을 다시 검토할 것인가?

- `inspect`/`verify`/`revert`/`serve` 구현 과정에서 봉투 형태가 특정 명령의 요구를 충족하지 못하는 것이 발견될 때
- `ErrorCode` 열거가 명령마다 겹치지 않는 별도 열거가 필요할 만큼 커질 때
- `serve`의 HTTP 응답에도 이 봉투를 적용할지 판단할 때 — 현재는 미결정([Design "향후 확장 고려사항"](../design/20260903-1218-machine-readable-output.tdd.md))
