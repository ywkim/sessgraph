# ADR-0002: 끊긴 체인은 레코드를 삭제하지 않고 parentUuid만 재연결한다

## Status

Accepted

## Context

Claude Code 세션이 컴팩트될 때 기록되는 경계 레코드(`type: system`, `subtype: compact_boundary`)는 `parentUuid`가 `null`이다. 그 결과 컴팩트를 여러 번 거친 세션은 하나의 연결된 체인이 아니라 **경계마다 끊긴 여러 조각**이 된다.

실측한 한 세션(86,668줄)은 컴팩트 경계 315건을 포함하고, 최종적으로 39개의 비연결 조각으로 나뉘어 있었다. 세션 마지막 레코드에서 부모를 거슬러 올라가면 13개 노드 만에 멈춘다 — 그 이전 대화 전체가 재개 시 로드되지 않는다.

이를 잇는 방법은 두 가지다.

## 후보 기술 & 각 선택지

**후보1: 경계 레코드를 삭제하고 자식을 조부모에 재연결**

- 장점: 체인이 깔끔해짐. 경계 레코드가 사라지므로 재개 시 재컴팩트 트리거를 피할 것으로 기대
- 단점: 경계 레코드에 담긴 `compactMetadata`·`preservedMessages` 필드가 함께 사라짐
- 관측: 체인 길이는 정상화되고 재개 시 "Summarized N messages" 표시까지 나왔으나, **모델이 되살아난 내용을 실제로는 기억하지 못했다**. 도구 호출을 금지한 채 질문하자 "제 대화 요약에는 해당 내용이 없습니다"라고 직접 확인. 재개 시 자동 재컴팩트가 복원된 내용을 다시 손실 압축한 것으로 추정 (메커니즘 미확인)

**후보2: 경계 레코드는 그대로 두고 `parentUuid`만 직전 조각의 leaf로 변경**

- 장점: `compactMetadata`·`preservedMessages` 보존
- 단점: 경계 레코드가 체인에 남음
- 관측: 동일 세션에서 도구 호출을 금지한 순수 회상 질문에 파일 경로·문서 행 번호·커밋 해시·작업 경위까지 정확히 답변. **실질 회상 성공**

## Decision

끊긴 체인을 이을 때 `compact_boundary` 레코드를 삭제하지 않고, 해당 레코드의 `parentUuid`만 직전 조각의 leaf uuid로 변경한다.

## Rationale (선택 이유)

두 방식 모두 "체인 길이"라는 구조적 지표는 정상화시켰다. 갈린 것은 재개 후 모델이 실제로 그 내용을 기억하는가였고, 레코드를 보존한 쪽만 성공했다.

원인은 `compactMetadata`·`preservedMessages` 보존 여부로 추정되나 **메커니즘은 확인되지 않았다**. 따라서 이 결정은 "왜 작동하는지 아는" 결정이 아니라 "관측된 성공률이 높은" 결정이다. 이 불확실성 자체가 기록되어야 한다.

부수적으로 레코드 보존형은 되돌리기 쉽다 — 삭제는 정보를 없애지만 `parentUuid` 변경은 값 하나를 바꿀 뿐이다.

## Consequences

### 장점

- 재개 후 실질 회상 성공률이 높다 (관측 기준)
- 원본 정보가 사라지지 않아 되돌리기가 값 복원으로 끝난다
- 경계 레코드가 남아 있어 "어디가 컴팩트 지점이었나"를 사후에도 볼 수 있다

### 단점 & 트레이드오프

- 왜 작동하는지 설명하지 못한다. Claude Code가 경계 레코드를 다루는 방식이 바뀌면 이 결정의 근거가 무너질 수 있다
- 체인에 경계 레코드가 남으므로 렌더링 시 이를 걸러낼 책임이 뷰어에 생긴다

### 향후 기능이 따를 원칙

- 수술은 `parentUuid` 값 변경만 수행한다. 레코드 삭제·삽입은 하지 않는다
- 쓰기 전 반드시 타임스탬프 붙은 백업을 만든다. 기존 백업을 덮어쓰지 않는다
- **구조적 성공(체인 길이)을 실질 성공으로 보고하지 않는다.** 도구는 체인 길이까지만 보고하고, 회상 검증은 사람이 재개 후 직접 수행해야 함을 안내한다

## 언제 이 결정을 다시 검토할 것인가?

- 레코드 보존형에서도 회상 실패 사례가 관측될 때
- Claude Code가 컴팩트 경계 기록 방식을 바꿀 때
- 재컴팩트가 복원 내용을 다시 압축하는 메커니즘이 규명되어, 더 정확한 대응이 가능해질 때
