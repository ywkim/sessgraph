# ADR-0009: 본문 서식 보기는 marked의 토큰 분해만 쓰고 DOM은 허용 목록으로 직접 만든다

## Status

Accepted

## Context

[본문 전체 보기 PRD](../prd/20260907-1500-node-body-full-text.prd.md)가 대화 글의 서식 보기를 요구한다. 글의 출처는 대화이고 그 안에는 도구 출력·외부 문서·웹 페이지에서 온 글이 섞인다. 서식 보기는 그 글을 해석해 화면에 그리므로, 글이 화면에서 코드를 실행하거나 외부로 요청을 보내게 해서는 안 된다.

[ADR-0007](ADR-0007-hand-roll-vs-existing-solution.md)의 기준을 적용한다. 마크다운 해석에는 여러 해에 걸쳐 다져진 엣지 케이스가 실재한다(중첩 목록, 표, 코드 펜스, 강조 기호의 짝, 이스케이프). 직접 구현한 변환기는 조용히 틀리므로 도입 쪽으로 결정한다.

남은 질문은 두 가지다: 어떤 도구를 쓰는가, 번들러가 없는 이 저장소에서 브라우저에 어떻게 전달하는가. 이 저장소의 웹은 `tsc`가 만든 ES 모듈을 `serve`가 정적으로 응답하고, 번들러가 없다.

## 후보 기술 & 각 선택지

**후보1: marked로 HTML 문자열을 만들고 DOMPurify로 거른다**

- 장점: 가장 흔한 조합이다
- 단점: 의존성이 둘이다. 문자열 HTML을 `innerHTML`로 넣는 순간 안전이 거름 설정 하나에 달린다. 허용 목록을 거름 도구의 설정으로 표현하면, 새 요소가 생길 때 막는 쪽이 아니라 여는 쪽이 기본값이 된다

**후보2: marked의 토큰 분해(`Lexer`)만 쓰고, 토큰에서 DOM을 직접 만든다**

- 장점: 해석(다져진 부분)은 도구에 맡기고, 출력은 우리 코드의 허용 목록 하나로 결정된다. `createElement`·`textContent`만 쓰므로 만들 수 있는 요소가 코드에 적힌 것뿐이고 `innerHTML`이 없다. 의존성이 하나이고 그 자체의 의존성이 없다. 한 파일짜리 ES 모듈(`lib/marked.esm.js`)이라 번들러 없이 전달된다. 토큰의 글은 이스케이프되지 않은 원문이라 `textContent`에 그대로 넣는다
- 단점: 토큰 종류마다 DOM 매핑을 직접 쓴다. 도구의 새 토큰 종류는 매핑이 없으면 글자로 보인다(조용히 사라지지 않는다)

**후보3: markdown-it의 토큰 흐름에서 DOM을 만든다**

- 장점: 후보2와 같은 방식이 가능하다. 설정으로 raw HTML을 끌 수 있다
- 단점: 브라우저용 산출물이 UMD 전역(`<script>`)이라 이 저장소의 ES 모듈 구조와 맞지 않는다. 의존 패키지가 여럿이다

**후보4: micromark·remark 계열(mdast)**

- 장점: 구문 트리가 가장 정형이다
- 단점: 패키지가 수십 개로 쪼개져 있어 번들러 없는 전달이 어렵다

## Decision

`marked`를 `dependencies`에 정확한 버전(`18.1.2`)으로 고정해 넣는다. 화면은 `Lexer`로 토큰만 얻고, 토큰에서 허용 목록의 요소만 `createElement`로 만든다. `marked`의 HTML 출력 기능과 거름 도구는 쓰지 않는다.

브라우저 전달: 빌드(`copy-web-assets.js`)가 `node_modules/marked/lib/marked.esm.js`를 `dist/web/vendor/`로 복사하고, `index.html`의 `importmap`이 `marked`를 그 경로로 잇는다. 소스는 `from "marked"`로 쓰므로 Node 테스트와 타입 검사가 같은 이름으로 풀린다.

버전은 배포 후 2주 이상 지난 것을 고른다(2026-10-26 배포, 결정 시점에 16일 경과).

## Rationale (선택 이유)

서식 보기의 위험은 해석이 아니라 출력이다. 해석은 틀려도 글이 어색하게 보일 뿐이지만, 출력이 열려 있으면 글이 코드를 실행한다. 그래서 두 층을 갈라, 해석은 다져진 도구에 맡기고(ADR-0007) 출력은 허용 목록으로 우리가 닫는다. 후보1은 출력을 거름 설정에 맡겨 이 구분을 흐리고, 후보2는 구조로 막는다. "허용 목록 밖은 만들 수 없다"가 설정이 아니라 코드의 모양이다.

후보3·4는 도구의 질이 아니라 전달 형태 때문에 밀린다. 번들러를 들이면 [ADR-0007](ADR-0007-hand-roll-vs-existing-solution.md)이 후보2의 단점으로 적은 비용을 치른다.

## Consequences

### 장점

- 만들 수 있는 요소와 속성이 한 곳(허용 목록)에 있고, 그 밖은 테스트로 막는다(`<script>`, 이벤트 속성, `javascript:` 링크, `<img>`)
- 도구를 바꿀 때 토큰 매핑만 다시 쓰면 된다

### 단점 & 트레이드오프

- 런타임 의존성이 0개에서 1개가 된다. 공급망 위험은 정확한 버전 고정과 배포 후 2주 대기로 줄이지만 없애지는 못한다
- 새 토큰 종류가 생기는 도구 갱신은 매핑을 확인해야 한다. 버전을 올릴 때 토큰 테스트가 그 확인을 맡는다
- 서식 보기의 렌더 비용은 본문 길이에 비례한다. 상한은 구현 단계의 실측으로 정하고 Spec에 적는다
