# ADR-0008: 본문 검색은 내장 SQLite(FTS5 trigram)의 영속 색인으로 한다

## Status

Accepted

## Context

본문 검색은 요청마다 세션 파일 원문을 바이트 단위로 훑는다 ([Design](../design/20260906-0900-body-search.tdd.md) 대안1). 그 설계는 "확인하려고 한두 번 찾아본다"는 사용 형태와 세션 하나를 전제로 색인을 기각했다(같은 Design 대안4).

전제가 바뀌었다. 실사용은 `serve`에 등록한 세션 전체를 한꺼번에 찾는 것이다. 실측(2026-10-15, 실제 세션 1,693개, 6.74GB):

| 항목                             | 값                                                                    |
| -------------------------------- | --------------------------------------------------------------------- |
| 가장 큰 파일(863MB) 원시 스캔    | 432ms                                                                 |
| 전체 원시 스캔 (위 속도로 외삽)  | 약 4초, 그동안 이벤트 루프 블로킹                                     |
| 같은 파일에서 사람이 찾을 텍스트 | 46MB (나머지는 base64 첨부 555MB, `toolUseResult` 중복 사본 222MB 등) |

원시 스캔은 대소문자 무시(바이트 비교라 비ASCII에서 성립하지 않음)와 JSON 이스케이프된 문구(따옴표·역슬래시·개행)도 풀지 못한다. 순위를 매기려면 매치마다 줄을 파싱해야 해서 스캔 시간에 비용이 더 붙는다.

## 후보 기술 & 각 선택지

**후보1: 원시 스캔 유지 + worker_threads 병렬화 + 결과 스트리밍**

- 장점: 저장소 없음, 무효화 문제 없음
- 단점: 6.74GB를 매번 읽는다. 디스크 대역폭이 하한이라 병렬화해도 1초 아래로 내려간다는 근거가 없다(미실측). 대소문자·이스케이프·순위 문제는 그대로 남는다

**후보2: 직접 만든 역색인 (JSON 파일 등)**

- 단점: 부분 문자열 매치, 유니코드 대소문자 접기, 증분 갱신, 원자적 쓰기를 모두 직접 구현한다. [ADR-0007](ADR-0007-hand-roll-vs-existing-solution.md) 기준으로 다져진 엣지 케이스가 실재하는 영역이다

**후보3: Node 내장 `node:sqlite`의 FTS5 + `trigram` 토크나이저**

- 장점: 런타임 의존성이 늘지 않는다(플랫폼 내장). trigram은 부분 문자열 매치를 하고, 기본 설정(`case_sensitive 0`)이 유니코드 대소문자를 접는다(`école`로 `ÉCOLE` 매치 확인). 색인에는 JSON을 풀어 낸 텍스트가 들어가므로 따옴표·개행도 그대로 찾는다. 트랜잭션과 WAL로 원자적 쓰기와 동시 읽기가 된다
- 단점: 디스크에 세션 텍스트 사본이 생긴다. 3글자 미만 검색어는 trigram이 처리하지 못해 `LIKE` 전체 스캔으로 대신한다. `node:sqlite`는 Node 22.13부터 플래그 없이 쓸 수 있으나 25.7 이전에는 실험 단계라 `ExperimentalWarning`을 낸다([Node 문서](https://nodejs.org/api/sqlite.html))
- 실측 (텍스트 92MB 표본): 원문을 저장하는 기본 방식 310MB(3.4배), 질의 0~1ms, `LIKE` 결과와 건수 일치. `detail=none`/`detail=column`은 3글자 초과 검색어에서 "phrase queries are not supported" 오류가 나 쓸 수 없다. contentless(`content=''`)는 205MB지만 2글자 검색이 불가능하다
- Node 22.23.3(SQLite 3.51.3)과 Node 26(SQLite 3.53.4) 모두에서 FTS5 trigram 동작 확인

## Decision

본문 검색은 Node 내장 `node:sqlite`의 FTS5 `trigram` 색인으로 하고, 원문을 저장하는 기본 방식(contentless 아님)을 쓴다. 색인은 세션 파일에서 파생된 캐시이며 사용자 캐시 디렉터리에 영속한다.

## Rationale (선택 이유)

검색 대상 6.74GB 중 사람이 찾을 텍스트는 일부뿐이고, 그 일부도 요청마다 다시 읽을 이유가 없다. 세션 파일은 뒤에 덧붙기만 하므로 증분 갱신이 단순하다(파일별로 색인한 위치만 기억하면 된다).

부분 문자열 매치·유니코드 대소문자 접기·원자적 쓰기는 직접 구현하면 조용히 틀리는 영역이고, 그 본체가 이미 플랫폼에 있다. ADR-0007의 두 질문("다져진 엣지 케이스가 있는가", "본체가 플랫폼에 있는가")에 모두 "그렇다"이므로 직접 구현하지 않고 내장 기능을 쓴다.

contentless 대신 원문 저장 방식을 고른 이유는 2글자 검색이다. 한국어는 2글자 낱말이 흔한데, contentless에서는 `LIKE`로 대신 찾을 원문이 없다. 크기 차이(표본 기준 1.5배)는 사용자가 디스크 사본을 받아들인 범위 안이다.

[ADR-0003](ADR-0003-cli-writes-web-reads.md)과 충돌하지 않는다. 그 결정이 막는 것은 브라우저에서 도달 가능한 경로가 **세션 파일**을 수정하는 것이다. 색인 쓰기는 세션 파일을 건드리지 않고, `src/web/`에 쓰기 API를 추가하지도 않는다. 색인은 지워도 다시 만들 수 있는 파생물이다.

## Consequences

### 장점

- 전 세션 검색이 원시 스캔 시간과 무관해진다
- 대소문자 무시, 이스케이프 문구 검색이 별도 구현 없이 성립한다
- 색인에 등급·시각을 같이 저장하므로 순위를 매기는 데 줄 파싱이 필요 없다

### 단점 & 트레이드오프

- 세션 텍스트 사본이 사용자 캐시 디렉터리에 생긴다. 자격증명이 섞인 텍스트도 들어간다. 파일 권한을 소유자 전용으로 둔다
- 첫 색인 생성 비용이 크다 (전체 코퍼스 실측 236초, 범위를 줄이기 전 기준). 그동안 결과가 불완전하다는 것을 화면에 알려야 한다
- 색인이 무엇을 담는지는 세션 레코드 구조에 의존한다. 필드가 바뀌면 색인이 조용히 비어 "0건"이 될 수 있다 — [ADR-0004](ADR-0004-schema-drift-defense.md)의 실패 모드와 같다
- `engines`를 `>=22.13`으로 올린다. 22.13~25.6에서는 `serve`가 `ExperimentalWarning`을 낸다

### 향후 기능이 따를 원칙

- 색인은 캐시다. 색인과 세션 파일이 어긋나면 세션 파일이 옳다. 색인 파일은 언제 지워도 다음 기동에서 다시 만들어져야 한다
- 색인에 넣는 범위는 허용 목록이 아니라 **제외 목록**으로 정한다. 모르는 레코드·블록 타입은 가장 낮은 등급으로 넣는다 — 새 타입이 조용히 검색에서 사라지지 않게 한다
- `node:sqlite`는 `serve` 경로에서만 불러온다. 다른 CLI 명령의 출력에 경고가 섞이지 않게 한다
- 색인 쓰기는 `src/cli/`가 한다. `src/core/`는 레코드에서 색인할 텍스트를 꺼내는 순수 함수만 둔다 ([src/core/CLAUDE.md](../../src/core/CLAUDE.md) "파일 쓰기" 금지)

## 언제 이 결정을 다시 검토할 것인가?

- 색인 크기가 사용자 디스크에 부담이 될 만큼 커질 때 (contentless 전환과 2글자 검색 포기를 다시 저울질한다)
- `node:sqlite`의 API가 호환되지 않게 바뀌거나, Node 번들 SQLite에서 FTS5가 빠질 때
- 뜻 기반 검색(임베딩)처럼 trigram으로 표현할 수 없는 요구가 생길 때
