# Spec: serve 세션 목록 화면

## 개요

`sessgraph serve`에 세션이 둘 이상 주어졌을 때 여는 목록 화면(`renderSessionList`, `GET /api/sessions`)의 설계 공백 9개를 정의한다. 각 항목은 **문제 여부 · 근거 · 결정 또는 열린 이슈** 순서로 적는다.

9개 중 8개는 문제로 확정됐다. 7번(규모)은 현재 측정 범위에서 문제가 없다고 판정했다. 3번은 전제가 틀렸다 — 세션을 열지 않아도 본문 검색이 된다. 문제는 검색의 **비용과 블로킹**이다.

설계 문서(`20260905-0641-multi-session-serve.tdd.md`)는 목록에 "명시적으로 지정한 소수"의 세션이 온다고 가정했다. 실사용은 약 1,600개이므로 그 가정 위에서 내린 결정들을 이 Spec에서 다시 판정한다. "목록 단계에서 인덱싱하지 않는다"는 원칙은 유지한다.

## 검증 범위

**검증한 것** — 실제 `serve` 프로세스와 Chromium(데스크톱 1280px)으로 합성 세션 1,600개에 대해 측정했다. 조건은 맨 아래 "측정 조건"에 있다.

- 목록의 DOM 구조와 최초 렌더 시간, 필터 입력 처리 시간
- 필터·스크롤을 설정하고 세션을 열었다 뒤로 간 뒤의 상태
- 노드 수가 나타나는 시점, 시각 없는 항목의 위치
- 기동 뒤 추가된 파일과 삭제된 파일의 목록 반영
- 목록 화면의 헤더 검색 동작과 전 세션 검색의 요청 블로킹

또한 **실제 세션 파일 1개**(작업 중인 세션, 구조 필드만 확인, 값은 기록하지 않음)에서 레코드 타입·키 이름·제목 레코드의 바이트 위치를 확인했다.

**검증하지 않은 것**

- 실제 약 1,600개 코퍼스. 이 환경에 없다. 아래 수치는 모두 합성 코퍼스이므로 **기준선이 아니다.** 실사용 시 "112개"는 기존 Spec의 2026-10-09 실측을 인용한 값이다.
- 제목 레코드의 값 품질, 등장 빈도, 재기록 간격의 일반성. 실제 파일 1개에서만 관찰했다.
- `custom-title` 레코드와 요약 줄(`summary`)의 필드 구조. 이 환경에 실물이 없다.
- 좁은 화면(모바일 폭), 스크롤 중 프레임 드롭, 긴 한글 제목의 줄바꿈. 1280px에서만 측정했다.

## 1. 식별성 — 제목 표시

**문제 여부: 확정.**

- 근거: 라벨은 `labelOf()`가 만든 `부모디렉터리/파일명`이다 (`src/cli/serve.ts`). 목록은 이것만 보여준다. 현재 코드베이스 어디에도 `ai-title`·`custom-title`·`aiTitle`을 읽는 코드가 없다.
- 관찰 (실제 세션 파일 1개, 구조만):
  - 제목 후보는 `ai-title`(필드 `aiTitle`)과 `last-prompt`(필드 `lastPrompt`)이다. `custom-title`은 타입 목록에만 있고 이 파일에는 없다. `ai-title`은 `RecordType` 목록에 없다.
  - `ai-title`은 대화 중 여러 번 기록된다. 이 파일에서 7회였고, 첫 기록은 바이트 129,364(파일의 약 17.6% 지점), 마지막 기록은 파일 끝에서 약 12.6KB 앞이었다.
  - 첫 `user` 메시지는 바이트 4,302, 즉 앞 64KB 창 안에 있다.
  - 따라서 **앞 64KB만으로는 맞는 제목을 고를 수 없다.** 첫 제목 레코드가 창 밖에 있고, 현재 제목은 "마지막 발생"이라 파일 뒤쪽을 읽어야 찾는다.

**결정: 제목 출처 우선순위와 읽기 창**

| 우선 | 출처                           | 읽기 창                 | 표시                              |
| ---- | ------------------------------ | ----------------------- | --------------------------------- |
| 1    | `custom-title`의 마지막 레코드 | 뒤 64KB, 없으면 앞 64KB | 제목                              |
| 2    | `ai-title`의 마지막 레코드     | 파일 끝 64KB            | 제목                              |
| 3    | 첫 `user` 메시지 텍스트        | 파일 앞 64KB            | 제목 아님 — "첫 메시지" 출처 라벨 |
| 4    | 없음                           | —                       | 라벨만 표시                       |

- 뒤 창은 파일 끝에서 시작한다. 잘린 첫 줄은 버린다. 파일이 64KB 이하면 앞 창과 뒤 창은 같은 내용이다.
- `custom-title`은 사용자가 직접 지은 이름이라 앞 창에 있어도 `ai-title`보다 우선한다. 이름을 바꾸면 새 레코드가 뒤에 추가되므로 뒤 창을 먼저 보고, 없을 때만 앞 창의 마지막 레코드를 쓴다. `ai-title`은 대화 중 갱신되므로 앞 창의 값은 오래된 제목일 수 있어 쓰지 않는다.
- 우선 1·2가 없으면 우선 3으로 떨어진다. 떨어졌을 때는 출처 라벨로 드러낸다. 오래된 제목이나 질문 텍스트를 현재 제목처럼 내지 않는다.
- 첫 `user` 메시지: `message.content`가 문자열이면 그 값, 배열이면 첫 `type: "text"` 부분을 쓴다. 공백만 있거나, `isMeta: true`이거나, 텍스트가 `<`로 시작하는(명령 envelope·시스템 주입) 레코드는 건너뛰고 다음 `user` 레코드로 넘어간다. 앞 64KB 안에서만 찾는다.
- 정규화: 개행과 연속 공백을 한 칸으로 줄이고, 앞뒤 공백을 자른다. 200자를 넘으면 `…`로 자른다. 전체 텍스트는 `title` 속성에 남긴다.
- 캐시: 메타는 세션별로 캐시하되, 파일 지문 `{ino, size, mtimeMs}`가 바뀌면 다시 읽는다. 제목은 파일 끝에 기록이 추가될 때 바뀌므로 지문 무효화가 필요하다.

**기준 변경 기록.** 설계 문서는 "기동 시에는 아무것도 인덱싱하지 않는다. 세션 목록은 파일 상태 조회만으로 만든다"고 적었다. 현재 구현은 이미 `firstTimestamp` 때문에 파일 앞 64KB를 읽으므로 이 문장과 다르다. 이 Spec은 기준 쪽을 다음과 같이 명시적으로 좁힌다: **"인덱싱은 하지 않는다. 파일당 64KB 이하의 앞·뒤 창만 읽는다."** 근거는 앞 창 읽기가 이미 쓰이고 있고, 같은 크기의 뒤 창 읽기가 같은 종류의 비용이며 측정으로 확인할 수 있다는 점이다. 이 기준 없이는 식별성 문제를 풀 수 없다.

**비용.** 파일당 최대 2회 읽기. 실제 파일 1개에서 64KB 역방향 읽기는 웜 캐시 기준 0.05ms였다. 1,600개 전체 비용은 실제 코퍼스에서 측정해야 한다 (미측정).

**열린 이슈**

- `custom-title`의 필드명은 `customTitle`이다 (실물 확인).
- `ai-title` 재기록 간격은 관찰 1건에서 나왔다. 뒤 64KB 창에 제목이 없는 파일 비율은 실측 전에는 모른다.
- 제외 규칙(`isMeta`, `<` 시작)은 구조만으로 판정한다. 실제 질문이 `<`로 시작하는 드문 경우는 건너뛰어 다음 메시지가 쓰인다. 실측: 첫 user 텍스트가 있는 869개 중 286개의 첫 레코드가 `isMeta`, 88개가 `<` 시작이었다.

## 2. 그룹화

**문제 여부: 확정.** `renderSessionList`는 모든 항목을 하나의 `div.session-list`에 평평하게 넣는다. 그룹 키가 없다. 약 1,600개가 시각순 한 줄이면 특정 프로젝트의 세션은 필터 입력에 기대서만 찾을 수 있다.

관찰된 디렉터리명은 `-home-user-proj0`처럼 경로 구분자가 `-`로 바뀐 형태다 (추정 — 관찰된 라벨 형태에 근거). 원래 이름에 하이픈이 있으면 되돌릴 수 없으므로, **디렉터리명을 원문 그대로 쓰고 경로로 복원하지 않는다.**

**결정**

- 그룹 키: 라벨의 `/` 앞부분. 라벨에 `/`가 없으면 `(기타)`.
- 그룹 헤더: `그룹명 · 세션 N개 · 최신 시작 시각`. 헤더는 `button`이며 `aria-expanded`로 접힘 상태를 알린다.
- 기본은 펼침. 접힘 상태는 제8항의 메모리 상태에 함께 둔다.
- 그룹 안의 순서는 현재 정렬 기준(제4항)을 따른다. 그룹의 순서는 그룹 안 첫 항목의 값 내림차순이다.
- 필터: 그룹 안에 일치하는 항목이 없으면 그룹 전체를 숨긴다.
- 구현: `src/web/format.ts`의 순수 함수 `groupByProject(sessions)`. 라벨에서 파생하므로 core 타입은 바뀌지 않는다.

**대안 비교**

- (a) 디렉터리 그룹 — **채택.** 라벨로 바로 만들 수 있고 추가 읽기가 없다.
- (b) 평면 목록을 유지하고 프로젝트 드롭다운 필터 추가 — 기각. 필터 대상 목록을 따로 관리해야 하고 구조가 보이지 않는다.
- (c) 디렉터리명을 경로로 디코딩해 표시 — 기각. 하이픈 모호성 때문에 틀린 경로를 보일 수 있다. 틀린 답을 조용히 내는 것은 ADR-0004가 막으려는 실패다.

**열린 이슈:** 그룹 수가 많을 때 기본을 접힘으로 할지는 실제 디렉터리 분포를 본 뒤 정한다.

## 3. 내용 검색

**전제 정정.** 세션을 열지 않아도 본문 검색은 된다. 헤더 검색창(`#search-input`, placeholder "본문에서 찾기…")은 `currentSessionId`가 `null`인 목록 화면에서 `/api/search`를 호출해 전 세션을 훑는다 (`src/web/app.ts`의 `runSearch`). 합성 코퍼스의 목록 화면에서 "NEEDLE"을 검색하면 매치가 있는 세션 32개 블록이 나왔다. 기대값(1,600 중 1/50 = 32)과 같다.

**문제 여부: 기능 부재는 아니다. 비용과 블로킹이 확정.** 측정 (합성 1,600개, 총 113MB):

- 첫 검색 (인덱스 없음): **1,938ms.** 같은 시점에 보낸 `/api/sessions`는 **1,890ms** 뒤에 응답했다.
- 이후 검색 (인덱스 있음): **433ms.** 검색마다 모든 파일을 다시 스캔한다.
- 원인: `/api/search` 핸들러는 세션 전체를 `await` 없이 동기로 인덱싱하고 스캔한다. Node의 이벤트 루프가 그 시간 동안 다른 요청을 처리하지 못한다.
- `app.ts`의 주석은 이 블로킹을 "혼자 쓰는 도구이고 실측 1초대~2.14초라 지금은 감수한다"고 적었다. 그 판단은 세션이 소수라는 전제에 기댄다. 1,600개에서는 같은 전제가 성립하지 않으므로 다시 판정한다.
- 목록 필터(라벨 부분 일치)와 헤더 검색(본문)은 같은 화면에 있지만 대상이 다르다. 두 입력을 구분하는 문구가 없다.

**결정**

- 헤더 검색을 유지한다. 목록 화면에서 본문 검색이 된다는 것은 현재 placeholder로 알 수 있으므로 그대로 둔다.
- 세션 필터의 placeholder를 `제목·경로로 목록 거르기`로 바꾼다. 필터 대상은 제목을 포함한다 (제1항).
- 블로킹: 세션 하나를 처리할 때마다 이벤트 루프에 양보한다 (`await new Promise(setImmediate)`). 응답 형식(`SessionSearchResult[]`)은 바꾸지 않는다.

**대안 비교**

- (a) 세션 사이 양보 — **채택.** 가벼운 요청의 대기가 세션 하나의 인덱싱 시간 정도로 줄어든다. 총 검색 시간은 그대로다.
- (b) 워커 스레드 — 근본적이지만 인덱서 코드를 워커에서 돌리는 비용과 코드 증가가 크다. 지금 규모에는 과하므로 기각.
- (c) 세션별 매치 캐시 (파일 지문 기준) — 두 번째 검색 이후를 빠르게 한다. 메모리를 쓰고 무효화 규칙이 필요하다. 실측 후 재검토.

**열린 이슈:** 진행 표시(세션 N/M)와 세션별 결과의 스트리밍 방식은 이 Spec의 범위 밖이다.

## 4. 정렬 기준

**문제 여부: 확정 (기능 공백).** `sortByRecency`는 `firstTimestamp`만 쓴다. `SessionSummary`에는 마지막 활동을 나타내는 값이 없다. 재개된 세션은 생성 시각 자리에 머문다. 이것이 얼마나 자주 문제인지는 측정하지 않았다 (빈도 미검증).

**해결안 비교**

- (a) 마지막 수정 시각(`mtime`) 추가 — **채택.** `stat`만 쓴다. 읽기가 없고 실패 세션을 빼면 항상 존재한다. 단점: `reattach`·`revert`와 파일 복사가 `mtime`을 바꾼다. 수술한 세션이 위로 올라가는 것은 실제 마지막 변경과 일치하므로 허용한다.
- (b) 파일 끝의 마지막 레코드 시각 — 의미는 더 정확하다. 단점: 시각 없는 세션(제5항)에서 null이 되고 읽기가 늘어난다.
- (c) 기본 정렬만 바꾸기 — 기각. 기본값을 바꿀 사용 근거를 아직 모으지 않았다.

**결정**

- 정렬 기준은 두 가지다: `시작 시각`(기본)과 `마지막 수정`. 목록 상단의 `select`로 고른다.
- 기본값은 `시작 시각`을 유지한다. 기본값을 바꾸려면 사용 근거를 먼저 남긴다.
- 동점과 null은 입력 순서를 유지한다 (기존 `sortByRecency` 규칙).
- `lastModifiedAt`이 null인 것은 실패 세션뿐이며, 실패 세션은 항상 맨 뒤에 둔다.

## 5. 시각 없는 세션

**문제 여부: 확정.** `summary` 줄만 있는 세션(실사용 112개, 기존 Spec의 2026-10-09 실측)은 `firstTimestamp`가 null이다. 합성 코퍼스에서 같은 구조를 재현했을 때 112행이 목록 끝에 연속으로 놓였고, 그 행의 `.session-meta`는 빈 문자열이었다. 아무 표시가 없어 사용자는 정렬이 깨졌다고 읽는다.

**결정**

- 메타 자리에 `시각 없음`(`.muted`)을 쓴다.
- 시작 시각 정렬에서는 맨 뒤에 둔다. 마지막 수정 정렬에서는 `mtime`이 있으므로 일반 위치에 둔다.
- 이 세션들의 제목 후보(`summary` 줄의 텍스트)는 필드명을 확인한 뒤 정한다 (열린 이슈).

**대안 비교**

- (a) "시각 없음" 표시 — **채택.**
- (b) `mtime`을 시작 시각 대신 표시 — 기각. 마지막 수정을 생성 시각으로 오인하게 만든다.

**읽기 실패와 구분 (이 항목에서 함께 정하는 것).** 현재 `readFirstTimestamp`는 열기·읽기 오류를 `null`로 삼킨다. 권한 오류가 난 파일도 "시각 없음"과 같아진다. 이 Spec은 **읽기 오류를 세션 실패로 올린다** (`status: "failed"`, `failure`에 사유). 값이 없는 것과 읽을 수 없는 것을 구분하는 것이 ADR-0004의 "조용한 오답 금지"에 맞다.

## 6. 노드 수 표시

**문제 여부: 확정.** 세 가지가 맞물린다.

- `filteredNodeCount`는 인덱싱된 세션만 값을 가진다 (`src/cli/serve.ts`의 `summaryOf`). 기동 직후 1,600개가 모두 `null`이다 (측정).
- 클라이언트는 `/api/sessions`를 기동 시 한 번만 받아 캐시한다 (`main()`). 세션을 열어 인덱싱해도 목록은 갱신되지 않는다. 측정: 세션 하나를 열고 뒤로 가도 그 세션은 시각만 보인다. 새로고침 후에야 열어본 세션만 노드 수가 나타났다 (측정: 1개).
- 같은 단어, 다른 값: 목록의 `N개 노드`는 기본 접힘이 아닌 노드 수이고, 헤더의 `노드 N개`는 전체 노드 수다.

**결정**

- 목록에서 노드 수 표시를 중단한다. 헤더의 `노드 N개`(전체)는 유지한다.
- `SessionSummary.filteredNodeCount` 필드 제거는 인터페이스 게이트 절차를 따르는 별도 PR에서 한다. 그때까지 서버는 값을 계속 보내고, 웹은 렌더하지 않는다.

**대안 비교**

- (a) 목록 단계에서 전 세션 인덱싱 — 기각. 제3항의 블로킹을 목록 진입마다 만든다. 설계 문서의 "목록 단계에서 인덱싱하지 않는다" 원칙에 어긋난다.
- (b) "열어본 세션만" 표시 — 기각. 값이 탐색 순서에 따라 달라지고, 같은 목록이 새로고침 전후로 다르다.

## 7. 규모 — 가상 스크롤

**문제 여부: 현재 규모에서는 없음 (측정).** 합성 1,600개, Chromium, 1280px.

| 측정                                        | 결과  |
| ------------------------------------------- | ----- |
| DOM 요소 수 (문서 전체)                     | 4,823 |
| 최초 렌더 (fetch 포함 wall 시간)            | 264ms |
| 필터 1회 입력 처리 (핸들러 + 강제 레이아웃) | 8.8ms |
| 필터 결과 (`proj3`, 기대 178)               | 178   |

**결정**

- 가상 스크롤을 도입하지 않는다. 제목 두 줄을 넣으면 행 높이가 가변이 되므로, 현재 `ROW_HEIGHT = 52` 고정 가정은 목록에 맞지 않는다. 가상 스크롤이 필요해지기 전에 행 구조를 먼저 정한다.
- 재검토 기준: 실제 코퍼스에서 최초 렌더 wall > 1s, 또는 필터 1회 입력 > 50ms 중 하나.
- 기존 Spec의 "초기 렌더 < 100ms" 목표는 fetch를 떼어 잰 값이 없어서 판정하지 않는다 (열린 이슈).

## 8. 상태 유지

**문제 여부: 확정 (측정).** 필터에 `proj3`을 입력하고 스크롤을 3,000px로 둔 뒤 세션을 열었다가 뒤로 가면, 필터는 빈 값으로, 스크롤은 0으로 돌아간다.

- 원인: `openSession()`이 `timelineEl`을 비우면서 목록과 필터 입력도 함께 사라진다. `renderSessionList()`는 입력을 새로 만든다.

**결정: 모듈 메모리 상태로 복원**

- `app.ts`의 모듈 변수 `listViewState = { filter: string; scrollY: number; collapsedGroups: Set<string> }`에 보관한다.
- 세션을 열기 직전에 현재 값을 저장한다. 뒤로 돌아오면 필터 입력에 값을 넣고 필터를 적용한 뒤, 접힘 상태를 적용하고, 레이아웃이 끝난 뒤 `window.scrollTo(0, scrollY)`를 호출한다.
- `sessionStorage`와 `localStorage`는 쓰지 않는다. 해시 이동으로 같은 페이지 안에서만 돌아오므로 메모리로 충분하다. 새로고침 후 초기화는 허용한다.

**대안 비교**

- (a) 메모리 상태 — **채택.**
- (b) `sessionStorage` — 기각. 같은 탭 안의 이동에는 필요 없고, 저장이 실패하는 경로(프라이빗 창, 차단)만 늘어난다.
- (c) 목록을 `hidden`으로 숨겨 DOM을 유지 — 기각. 세션 타임라인과 목록 DOM이 함께 살아 있게 된다.

## 9. 갱신과 파일 변화

**문제 여부: 확정 (측정).**

- 기동 시 `registerSessions`가 등록 경로를 한 번 확인한다. 기동 뒤 추가된 파일은 목록에 없다. 새로고침 후에도 없다 (측정: 1,600 → 1,600).
- 기동 뒤 삭제된 파일은 목록에서 `ready`로 남는다 (측정). 열면 `ENOENT` 배너가 뜬다. 설계 문서의 "존재하지 않는 경로는 이 시점에 실패로 확정한다"는 기동 시에만 적용되어 있다.

**원칙 확인**

- ADR-0003은 파일 **쓰기**를 금지한다. 디렉터리를 읽어 목록을 갱신하는 것은 쓰기가 아니므로 원칙과 충돌하지 않는다.
- 다만 입력 모델은 "명시적으로 받은 경로만 다룬다"(설계 문서, 대안 기각 항목)다. 디렉터리 탐색은 "어떤 파일이 세션인가"를 판별하는 규칙을 새로 요구하므로 CLI 인터페이스 변경이다. 이 Spec의 범위 밖이다.

**결정**

- (a) 목록 요청마다 등록 경로의 존재를 `existsSync`로 확인한다. 없으면 `status: "failed"`, `failure: "파일을 찾을 수 없습니다: …"`. 1,600개 확인에 2.9ms가 걸렸다 (측정). 기동 시 실패 처리를 기동 뒤 삭제에도 같은 방식으로 적용한다.
- (b) 목록 상단 문구를 `세션 N개 (기동 시점 기준)`으로 바꿔 한계를 드러낸다.
- (c) 자동 감지(디렉터리 인자 모드)는 별도 Design 문서로 다룬다.

**대안 비교**

- (1) 재기동 안내만 — **채택.** 범위 안에서 가장 작은 변경이다.
- (2) 목록 요청마다 디렉터리 재스캔 — 기각. 입력 모델을 바꾸고 판별 규칙이 필요하다.
- (3) 주기적 폴링 — 기각. 목록이 바뀌지 않을 때도 재스캔 비용이 든다. 이득을 측정한 적이 없다.

## 부수 발견: JSONL 파싱 위치

루트 CLAUDE.md는 "`src/cli/`와 `src/web/`은 JSONL을 직접 파싱하지 않는다. 반드시 `src/core/`를 경유한다"고 적는다. 현재 코드는 이를 지키지 않는다.

| 위치                                    | 내용                                          |
| --------------------------------------- | --------------------------------------------- |
| `src/cli/serve.ts` `readFirstTimestamp` | JSONL 줄을 `JSON.parse`                       |
| `src/cli/serve.ts` `rawMatchesUuid`     | 본문 한 줄을 `JSON.parse`                     |
| `src/web/format.ts` `summarizeRaw`      | 본문 한 줄을 `JSON.parse` (표시용)            |
| `src/cli/reattach.ts` 289·294행         | 원본·수정 줄을 `JSON.parse` (이 Spec 범위 밖) |

규칙은 이미 있는데 지켜지지 않았다. 그래서 규칙을 하나 더 쓰지 않고 기계 검사로 옮기는 것을 기본 대응으로 한다.

**결정**

- 이 Spec이 추가하는 제목·첫 시각 탐색은 `src/core/`에 둔다 (Interface 절).
- 기존 `readFirstTimestamp`도 같은 모듈로 옮긴다.
- `summarizeRaw`와 `rawMatchesUuid`는 이번 변경 범위가 아니다. 열린 이슈로 둔다.

**기계 검사 후보 (열린 이슈).** ESLint `no-restricted-syntax`로 `src/cli/`와 `src/web/`의 `JSON.parse` 호출을 막는다. 허용 목록은 수술 로그처럼 세션 JSONL이 아닌 입력에만 준다. **현재 이 규칙은 기계적으로 강제되지 않는다.** 리뷰에서 사람이 막아야 한다.

## 데이터 모델

### SessionSummary 추가 필드 (`src/core/types.ts` — 타입의 단일 진실)

```typescript
export type TitleSource = "custom-title" | "ai-title" | "first-user-message";

// 기존 필드(id, label, status, failure, filteredNodeCount, firstTimestamp)는 그대로 둔다.
// 추가 필드:
readonly title: string | null; // 정규화된 제목, 또는 첫 메시지. 없으면 null
readonly titleSource: TitleSource | null;
readonly lastModifiedAt: string | null; // ISO 8601, 파일 mtime. 실패 세션만 null
```

불변식:

- `title === null` ⇔ `titleSource === null`
- `titleSource === "first-user-message"`이면 `title`은 시작 질문이지 제목이 아니다. UI는 출처를 반드시 표시한다.
- `status === "failed"` ⇔ `lastModifiedAt === null`. 실패 세션은 `firstTimestamp`와 `title`도 모두 null이다.
- `firstTimestamp === null`인 `ready` 세션은 "시각 없음"이다. 읽기 실패는 `status: "failed"`로 표현한다. 둘을 `firstTimestamp` 값만으로 구분하지 않는다.

`core`에 추가할 관측 타입: `RecordType`에 `"ai-title"`을 추가한다 (현재 목록에 없다). `"summary"`는 필드 확인 후 추가 여부를 정한다.

| 뒤 창에 `ai-title` 없음                   | 첫 메시지로 떨어지고 출처 라벨을 붙인다                             |
| 뒤 창에 `custom-title` 없음, 앞 창에 있음 | 앞 창의 마지막 `custom-title`을 쓴다                                |
| 앞 창에도 첫 메시지 없음                  | `title: null`, 라벨만 표시                                          |
| 파일 지문이 바뀜                          | 메타를 다시 읽는다                                                  |
| 필터 일치 0                               | 해당 그룹을 숨긴다. 전체가 0이면 "일치하는 세션 없음"               |
| `마지막 수정` 정렬에서 실패 세션          | 맨 뒤, 입력 순서                                                    |
| 세션 1개                                  | 목록 없이 바로 연다 (기존 동작 유지)                                |
| 레코드에 `message`·`timestamp`가 없음     | 그 레코드만 건너뛴다. 파일 전체에 없으면 null (시각 없음·제목 없음) |
| 읽기 자체가 실패                          | `failed`. 빈 값으로 채우지 않는다                                   |

## 성능 요구사항

## Out of Scope

- 가상 스크롤 (제7항 — 재검토 기준만 정의)
- 디렉터리 자동 탐색과 목록 갱신 (별도 Design 문서)
- 세션별 검색 결과 캐시 (측정 후 결정)
- 제목 편집·이름 변경 (쓰기 금지 — [ADR-0003](../adr/ADR-0003-cli-writes-web-reads.md))
- 좁은 화면(모바일 폭)에서의 목록 레이아웃 검증 (검증 범위 밖)
- `filteredNodeCount` 필드 제거 (인터페이스 게이트를 거치는 별도 PR)
- 세션 두 개를 나란히 비교하는 화면

## 열린 이슈

1. `custom-title`의 필드명과 값 구조 — 실물 확인 필요
2. `summary` 줄의 텍스트 필드 — 실물 확인 필요, `RecordType` 추가 여부
3. `ai-title` 재기록 간격과 뒤 창 미포함 비율 — 실제 코퍼스에서 측정
4. 첫 `user` 메시지의 시스템 주입 블록 제외 규칙
5. 실제 코퍼스 측정: 총 바이트, 메타 읽기 비용, 최초 렌더 (fetch 분리)
6. 검색 블로킹 해소 방식의 확정 — 진행 표시·스트리밍 포함
7. 기계 검사 도입: `JSON.parse` 제한과 허용 목록 (부수 발견)
8. 그룹 기본 접힘 여부 — 실제 디렉터리 분포 확인 후
9. 정렬 기본값을 `마지막 수정`으로 바꿀지 — 사용 근거 확인 후
10. `summarizeRaw`와 `rawMatchesUuid`의 파싱 위치 이동 여부

## 측정 조건

- 합성 세션 1,600개, 세션당 약 70KB. 구조 필드(`type`, `uuid`, `parentUuid`, `isSidechain`, `timestamp`, `file-history-snapshot`의 `snapshot.timestamp`, `summary`, `ai-title`)만 흉내 냈다. 본문은 무작위 라틴 단어다.
- 프로젝트 디렉터리 9개. 시작 시각 없는 `summary` 전용 세션 112개, 스냅샷 시각만 있는 세션 650개, 나머지는 메시지 시각이 있다.
- 실제 파일 관찰 1개: 작업 중인 세션 파일 (스냅샷 시점 약 733KB, 102줄). 레코드 타입·키 이름·바이트 위치만 기록했고 값은 기록하지 않았다.
- 측정 스크립트와 합성 생성기는 작업 디렉터리에 두었고 리포에는 커밋하지 않았다. 픽스처 정책에 따라 합성 데이터도 리포에 넣지 않는다.
