# Spec: 본문 검색

## Interface

### HTTP 엔드포인트

`serve`가 제공하는 읽기 전용 엔드포인트 두 개를 추가한다 ([`serve` Spec](20260902-0420-serve-command.spec.md#http-엔드포인트)의 규약을 그대로 따른다 — `GET`만, 쓰기 메서드는 `405`).

| 경로                               | 응답                                                   |
| ---------------------------------- | ------------------------------------------------------ |
| `/api/session/:id/search?q=<문구>` | `SearchResult` — 한 세션 안의 매치 목록                |
| `/api/search?q=<문구>`             | `SessionSearchResult[]` — 등록된 모든 세션에 대한 결과 |

- `q`: 필수. UTF-8 문자열. 빈 문자열이면 `400`
- `:id`: `/api/sessions`가 응답한 `id`. 일치하는 항목이 없으면 `404`

`/api/search`는 `/api/sessions`와 **같은 순서로** 세션당 한 항목씩 돌려준다. 세션을 순차 처리하며, 한 세션의 실패가 다른 세션의 결과를 지우지 않는다.

### 코어 함수

스캔은 `src/core/search.ts`에 둔다. 파일을 읽지만 쓰지 않으므로 `src/core/`의 책임 경계 안이다 (`buildIndexFromFile`과 같은 위치).

```ts
/** 1단계 원시 바이트 스캔 + 2단계 줄 해석. 인덱스를 보지 않는다. */
export function scanFile(
  filePath: string,
  query: string,
  maxMatches: number,
): { readonly matches: readonly RawMatch[]; readonly truncated: boolean };

/** 3단계 — 인덱스와 결합. 순수 함수. */
export function attributeMatches(
  index: IndexResult,
  nodes: ReadonlyMap<string, NodeIndex>,
  raw: readonly RawMatch[],
): readonly SearchMatch[];
```

세 단계의 경계는 유지한다 — 스캔 시간이 문제가 되면 `scanFile`의 1단계만 외부 도구로 교체할 수 있어야 한다 ([Design](../design/20260906-0900-body-search.tdd.md) 대안2).

`src/core/segment.ts`에 비throw 변형을 추가한다:

```ts
/** 세그먼트에 속하지 않으면 null. 기존 findSegmentForUuid는 이 함수를 쓰고 null일 때 throw한다 */
export function tryFindSegmentForUuid(
  index: IndexResult,
  nodes: ReadonlyMap<string, NodeIndex>,
  uuid: string,
): Segment | null;
```

필요한 이유: orphan의 하위 노드는 부모 체인을 거슬러도 어떤 세그먼트 root에도 닿지 않아 현재 `findSegmentForUuid`가 throw한다 (`src/core/segment.ts:30`). 검색에서 이것은 예외가 아니라 **결과로 보고해야 할 상태**다. `findSegmentForUuid`의 기존 동작(throw)은 바꾸지 않는다.

## 데이터 모델

`IndexResult`, `Segment`, `NodeIndex`는 [`src/core/types.ts`](../../src/core/types.ts)를 그대로 쓴다. 아래 타입을 그 파일에 추가한다.

```ts
/** 스캔 1·2단계의 산출 — 인덱스를 아직 보지 않은 상태. */
interface RawMatch {
  /** 매치가 시작하는 파일 바이트 오프셋 */
  readonly byteOffset: number;
  /** 매치가 든 줄에서 얻은 uuid. 줄이 JSON이 아니거나 uuid가 없으면 null */
  readonly uuid: string | null;
  /** 매치 주변 발췌 (아래 "발췌" 참고) */
  readonly excerpt: string;
}

/**
 * 매치를 어느 노드에 귀속시켰는지.
 *
 * `unindexed`가 이 설계의 존재 이유다 — 인덱스가 의도적으로 제외한 레코드
 * (unresolvedDuplicates 등) 안의 매치이며, 결과에서 빼지 않는다
 * (Design "매치를 노드에 귀속시키기", ADR-0004).
 */
type MatchAttribution =
  /** uuid가 인덱스에 있고 어떤 세그먼트에 속한다 */
  | {
      readonly kind: "segment";
      readonly uuid: string;
      readonly segmentRootUuid: string;
      readonly lineNo: number;
    }
  /** uuid가 인덱스에 있으나 어떤 세그먼트에도 속하지 않는다 (orphan 하위) */
  | { readonly kind: "orphan"; readonly uuid: string; readonly lineNo: number }
  /** 줄에 uuid가 있으나 인덱스에 없다 (중복 미해소 등) */
  | { readonly kind: "unindexed"; readonly uuid: string }
  /** 줄에 uuid가 없거나 줄을 해석하지 못했다 */
  | { readonly kind: "none" };

interface SearchMatch {
  readonly byteOffset: number;
  readonly excerpt: string;
  readonly attribution: MatchAttribution;
}

interface SearchResult {
  readonly query: string;
  readonly matches: readonly SearchMatch[];
  /** 매치 상한에 걸려 스캔을 중단했으면 true */
  readonly truncated: boolean;
  readonly durationMs: number;
}

/** `/api/search`의 항목 하나. result와 failure는 정확히 한쪽만 non-null이다 */
type SessionSearchResult = { readonly sessionId: string } & (
  | { readonly result: SearchResult; readonly failure: null }
  | { readonly result: null; readonly failure: string }
);
```

### 불변식

- `attribution.kind`가 `"segment"`/`"orphan"`일 때만 `lineNo`가 존재한다 — 인덱스 노드에서 가져온 값이다. 스캔은 줄 번호를 세지 않는다 (개행을 세려면 전체 바이트를 한 번 더 훑어야 하고, 인덱스에 없는 매치에는 어차피 대응할 노드가 없다)
- `matches`는 `byteOffset` 오름차순이다
- `truncated === true` ⟺ `matches.length === maxMatches`
- 매치는 **겹치지 않는다** — 한 매치를 찾으면 다음 탐색은 그 매치의 끝부터 시작한다. `"aa"`를 `"aaa"`에서 찾으면 1건이다

### 검색 대상은 저장된 JSONL 원문이다

매치 판정은 파일에 있는 바이트 그대로에 대해 이뤄진다. 렌더된 대화 텍스트가 아니다. 따라서:

- 구조 필드에도 매치된다 — `uuid`, `type`, 도구 호출에 담긴 파일 경로 등. `"user"`를 찾으면 거의 모든 줄이 걸린다
- JSON 이스케이프가 적용된 부분은 저장 형태와 입력 문구가 다르다. 큰따옴표·역슬래시·개행이 포함된 문구는 **매치 0건이 나온다** (파일에는 `\"`, `\\`, `\n`으로 들어 있다)
- 비ASCII는 이스케이프되지 않으므로(`JSON.stringify` 기본 동작) 한글·CJK는 그대로 매치된다

### 발췌

매치 지점의 바이트 창에서 만든다 — 줄 전체를 문자열로 만들지 않는다 (줄 하나가 수 MB일 수 있다).

- 창: `[매치시작 - 128, 매치끝 + 128]`, 해당 줄의 경계로 자른다
- UTF-8로 디코드하고, 양 끝의 불완전한 바이트 시퀀스는 버린다
- 줄 경계보다 창이 먼저 잘렸으면 그쪽에 `…`를 붙인다

## 엣지 케이스 & 에러 처리

**요청**

- `q` 누락 또는 빈 문자열 → `400`, "검색어가 필요합니다". 빈 검색을 전체 매치로 해석하지 않는다
- `:id`가 목록에 없음 → `404`
- 쓰기 메서드 → `405` ([`serve` Spec](20260902-0420-serve-command.spec.md))

**스캔**

- 매치가 청크 경계에 걸침 → 청크마다 `검색어 바이트 길이 - 1`을 겹쳐 읽어 반드시 찾는다
- 겹쳐 읽은 구간에서 같은 매치가 두 번 보임 → 직전 청크에서 이미 보고한 오프셋은 건너뛴다. 같은 `byteOffset`이 결과에 두 번 나오지 않는다
- 매치 0건 → `200`, 빈 배열. 오류가 아니다
- 매치가 상한(1,000건)에 도달 → 그 지점에서 스캔을 중단하고 `truncated: true`. 상한이 없으면 흔한 문구 하나로 수천만 건이 나와 메모리가 무너진다. 상한은 파일 순서(byteOffset)로 채워지므로, 앞부분의 흔한 구조 필드 매치가 상한을 다 쓰면 뒤쪽의 `unindexed`/`orphan` 매치가 결과에서 빠질 수 있다 — `kind`별 우선순위 없이 발견 순서를 그대로 쓰는 절충이며, 실제로 문제가 되면 재검토한다
- 빈 파일(0바이트) → `200`, 매치 0건
- 파일 마지막 줄이 개행 없이 끝남 → 파일 끝을 줄 끝으로 본다

**귀속**

- 매치가 든 줄이 JSON 파싱 실패 → `kind: "none"`. 결과에서 빼지 않는다
- 줄에 `uuid` 필드가 없음(메타데이터성 레코드) → `kind: "none"`
- 줄의 uuid가 인덱스에 없음 → `kind: "unindexed"`. **이 매치를 버리는 것이 이 설계가 막으려는 실패다** — 실측에서 `unresolvedDuplicates`에 든 레코드 1건이 여기 해당했다 (Design)
- uuid가 인덱스에 있으나 세그먼트에 속하지 않음 → `kind: "orphan"`
- 줄이 32MB를 초과 → 파싱하지 않고 `kind: "none"`. 발췌는 바이트 창에서 만들므로 그대로 제공한다. 32MB는 실측이 아니라 방어적 상한이다(확인 안 됨) — Design 대안3의 문자열화 비용(823MB에 2,306ms, 약 2.8ms/MB)을 선형 외삽하면 32MB 줄 하나를 파싱하는 데만 약 90ms가 들어, 매치 상한(1,000건)까지 갈 필요 없이 그 한 줄만으로 성능 목표(1초)를 위협한다. 실제 최장 줄 길이는 측정하지 않았다 — 그런 크기의 단일 레코드는 도구 호출 결과처럼 드물게만 관측된다

**파일 변경**

- 요청 처리 시작 시 기존 `ensureFresh`로 인덱스 최신성을 맞춘다 (`src/cli/serve.ts`)
- 스캔 직전과 직후의 `{ino, size, mtimeMs}`가 다르면 → `409`, "파일이 변경되었습니다. 잠시 후 다시 시도하세요". **부분 결과를 정상인 것처럼 돌려주지 않는다.** 스캔이 수백 ms 걸리므로 이 창은 `/body`의 단일 seek보다 넓다
- 스캔 도중 파일이 사라짐 → `409`, 같은 처리

**여러 세션**

- 한 세션의 스캔·인덱싱이 실패 → 그 항목만 `failure`를 채우고 나머지 세션 결과는 그대로 반환한다 ([다중 세션 Spec](20260902-0420-serve-command.spec.md#엣지-케이스--에러-처리)과 같은 규칙)
- `status: "failed"`인 세션 → 스캔하지 않고 `failure`에 기존 실패 사유를 그대로 담는다

**화면**

- 결과는 세그먼트별로 묶어 보여주고, 선택하면 기존 조각 열기 경로로 이동한다
- `kind`가 `"unindexed"`/`"orphan"`/`"none"`인 매치는 **목록에서 빼지 않고** 별도 묶음으로 표시하되 클릭할 수 없게 한다 — 실패한 세션 항목과 같은 처리다 (`.session-item.failed`, `src/web/app.css`). 조용히 사라지면 사용자가 그 매치의 존재를 모른다
- `truncated: true` → "매치가 너무 많아 앞의 1,000건만 표시합니다"를 결과 상단에 표시한다
- 검색어에 큰따옴표·역슬래시·개행이 포함됨 → 매치 0건이라도 "찾지 못했습니다"로만 끝내지 않고, 저장 형태가 달라 찾지 못할 수 있다는 안내를 함께 표시한다. 확신에 찬 0건이 가장 위험한 답이다 (ADR-0004)

## 성능 요구사항

기준선은 [Design](../design/20260906-0900-body-search.tdd.md)이 실측한 파일(823MB, 노드 9,083개)이다. 실측값을 그대로 기준으로 삼지 않고 여유를 둔다.

- 단일 세션 검색 응답: **1초 이내** (실측 1단계 174–305ms + 2단계 82건 24ms. 상한 1,000건이면 2단계는 약 300ms로 늘어 총 600ms 수준)
- 검색 1건이 늘리는 상주 메모리: **16MB 이내** (실측 heap 5MB. 1MB 청크 버퍼 하나를 재사용하고 파일을 문자열로 만들지 않으므로 파일 크기에 비례하지 않아야 한다)
- 청크 크기: 1MB
- 매치 상한: 1,000건
- `/api/search`의 총 시간은 세션 수에 비례한다. 세션 수를 늘려 병렬화하지 않는다 (Design "향후 확장 고려사항")

메모리 상한은 `serve` 전체 기준선(300MB, [`serve` Spec](20260902-0420-serve-command.spec.md#성능-요구사항)) 안에서 소화되어야 한다.

## Out of Scope

- **대소문자 구분 없는 검색** — 2단계에서 `String.prototype.toLowerCase()`로 확장할 수 있도록 단계 경계를 남겨두지만 이번 범위가 아니다 (Design "향후 확장 고려사항")
- 뜻이 비슷한 말·오탈자 보정 검색, 정규식 (PRD Non-Goals)
- 대화 본문 텍스트만 골라 검색하는 기능 — 줄마다 전체 파싱이 필요해 실측 8배 느린 경로다 (Design 대안3). 구조 필드에도 매치된다는 사실을 화면에서 숨기지 않는 쪽을 택한다
- 검색 전용 색인 (Design 대안4)
- `sessgraph search` CLI 명령 — PRD의 Why와 성공 기준이 모두 `serve` 화면 위에서 성립한다. 코어 함수를 `src/core/`에 두므로 나중에 명령을 추가할 때 스캔 로직을 다시 만들 필요는 없다
- 인덱스에 없는 매치(`unindexed`/`orphan`/`none`)의 전체 원문을 조회하는 엔드포인트, 그리고 그 매치를 화면에서 선택했을 때의 이동 경로 (Design "향후 확장 고려사항" — 조각 열기 경로가 인덱스를 전제한다)
- 파일 변경을 감지해 검색 결과를 자동 갱신하는 기능 (`409`로 알리고 재시도를 안내할 뿐)
- 검색 결과를 파일로 내보내거나 통계를 내는 기능 (PRD Non-Goals)
