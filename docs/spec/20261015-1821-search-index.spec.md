# Spec: 영속 검색 색인

## Interface

### HTTP 엔드포인트

경로는 [본문 검색 Spec](20260906-0900-body-search.spec.md)과 같고, 응답 형식이 바뀐다. `GET`만 허용하고 쓰기 메서드는 `405`다 ([`serve` Spec](20260902-0420-serve-command.spec.md#http-엔드포인트)).

| 경로                                             | 응답                                                 |
| ------------------------------------------------ | ---------------------------------------------------- |
| `/api/search?q=<문구>`                           | `SearchResponse` — 등록된 모든 세션                  |
| `/api/session/:id/search?q=<문구>`               | `SessionSearchResponse` — 세션 하나                  |
| `/api/session/:id/attribution?uuid=<uuid>`       | `MatchAttribution` — 레코드 하나가 속한 조각         |
| `/api/search/feedback?searchId=<id>&kind=<종류>` | `{recorded: true}` — "이게 답"·"못 찾았다"·이유 기록 |

- `q`: 필수. 앞뒤 공백을 자르지 않고 그대로 쓴다. 빈 문자열이면 `400` "검색어가 필요합니다". 1,000자(코드 포인트)를 넘으면 `400` "검색어가 너무 깁니다"
- `since`·`until`·`tiers`: 선택. 두 검색 경로에서 쓴다. 규칙은 아래 "검색 조건"
- `source`: 선택. 두 검색 경로와 `/attribution`에서 쓴다. 값은 `llm`뿐이고 LLM이 API로 부르는 호출이 싣는다. 다른 값(빈 문자열 포함)은 `400` "source는 llm만 받습니다"이고 아무것도 기록하지 않는다. 화면은 싣지 않는다. 기록에서만 쓰이고 응답은 같다
- `uuid`: 필수. 없거나 빈 문자열이면 `400` "uuid가 필요합니다"
- `/attribution`의 `q`·`rank`와 `since`·`until`·`tiers`·`searchId`: 선택. 화면이 전 세션 결과에서 누른 이동에만 싣는다. 응답은 같고 "검색 기록"에만 쓰인다. `searchId`가 서버가 발급한 형식(16자리 16진수)이 아니면 `open`에 싣지 않는다
- `/api/search/feedback`: `searchId`와 `kind`(`answer`·`notfound`·`reason`)가 필수고, `answer`는 `sessionId`와 `uuid`, `reason`은 `reason`(`src/core/notfound-reasons.ts`의 코드)도 필요하다. `GET`만 받고 `HEAD`는 `405`다. 서버가 `SearchResponse`로 내보낸 최근 100개 전 세션 검색만 안다. 발급하지 않았거나 밀려난 `searchId`, 그 검색의 결과에 없는 `sessionId`·`uuid`는 `404`, 잘못된 `kind`와 목록에 없는 `reason`은 `400`, 검색 기록이 꺼져 있으면 `503`이고 이때는 아무것도 기록하지 않는다
- `:id`가 목록에 없으면 `404`
- `/attribution`에서 세션 인덱스 구축이 실패하면 다른 세션 경로와 같이 `500`

### `serve` 옵션

- `--cache-dir <dir>`: 색인 파일과 검색 기록을 둘 디렉터리. 기본값은 `$XDG_CACHE_HOME/sessgraph`, `XDG_CACHE_HOME`이 없으면 `~/.cache/sessgraph`. 테스트는 임시 디렉터리를 넘긴다

### 코어 함수

`src/core/search-text.ts` — 파일 I/O 없는 순수 함수.

```ts
export type SearchTier = "conversation" | "tool" | "meta";

export interface SearchRow {
  readonly tier: SearchTier;
  readonly text: string;
  /** 레코드의 uuid. 없으면 null. 색인에 저장만 하고 검색 대상은 아니다 */
  readonly uuid: string | null;
  /** 레코드의 timestamp(ISO 문자열). 없으면 null */
  readonly timestamp: string | null;
  /** true면 세션 단위로 값마다 한 번만 색인한다 (cwd, gitBranch) */
  readonly perSession: boolean;
}

export interface ExtractedLine {
  readonly rows: readonly SearchRow[];
  /** type이 "user" 또는 "assistant"인 레코드였는가 (아래 "불변식"의 드리프트 감지용) */
  readonly conversationRecord: boolean;
}

/** JSONL 한 줄. JSON 파싱 실패면 { rows: [], conversationRecord: false } */
export function extractSearchRows(line: string): ExtractedLine;
```

`src/core/search.ts`의 `scanFile`과 관련 상수·테스트는 삭제한다. 매치를 조각에 귀속시키는 로직(`attributeOne`)은 남겨 `uuid → MatchAttribution`으로 쓴다.

## 데이터 모델

### 추출 규칙 (`extractSearchRows`)

레코드 `r`에 대해 아래 순서로 적용한다.

1. `r.cwd`, `r.gitBranch`가 문자열이면 각각 `{tier: "meta", perSession: true}` 행
2. `r.type`이 `"file-history-snapshot"` 또는 `"progress"`면 여기서 끝
3. `r.type === "attachment"`이고 `r.attachment.type === "file"`이면 여기서 끝
4. `r.type`이 `"user"`/`"assistant"`이고 `r.message.content`가 있으면:
   - 문자열 → `conversation` 행 하나
   - 배열 → 블록마다: `text`는 `.text`를, `thinking`은 `.thinking`을 `conversation` 행으로. `tool_use`/`tool_result`는 문자열 값 모음을 `tool` 행으로. 그 밖의 블록 타입은 문자열 값 모음을 `meta` 행으로
5. 그 밖의 레코드는 레코드 전체의 문자열 값 모음을 `meta` 행으로

**문자열 값 모음**: 객체를 재귀로 훑어 문자열 값을 `\n`으로 잇는다. 다음은 건너뛴다.

- 키: `uuid`, `parentUuid`, `logicalParentUuid`, `sessionId`, `requestId`, `messageId`, `leafUuid`, `id`, `tool_use_id`, `timestamp`, `signature`, `toolUseResult`
- `type === "base64"`이고 `data`가 문자열인 객체 전체

빈 문자열 행은 만들지 않는다.

### 색인 파일

`<cache-dir>/search-v1.sqlite`. 디렉터리는 `0700`, 파일은 `0600`으로 만든다. WAL 모드.

```sql
CREATE TABLE meta (key TEXT PRIMARY KEY, value TEXT NOT NULL);
-- ('schema_version', '2')

CREATE TABLE files (
  path TEXT PRIMARY KEY,
  ino INTEGER NOT NULL,
  indexed_offset INTEGER NOT NULL,   -- 마지막으로 색인한 완결 줄의 다음 바이트
  conversation_records INTEGER NOT NULL,
  conversation_rows INTEGER NOT NULL,
  failure TEXT                       -- 마지막 동기화 실패 사유, 성공하면 NULL
);

CREATE TABLE per_session_seen (path TEXT NOT NULL, value TEXT NOT NULL, PRIMARY KEY (path, value));

CREATE VIRTUAL TABLE rows USING fts5(
  path UNINDEXED, tier UNINDEXED, uuid UNINDEXED, ts UNINDEXED, body,
  tokenize = 'trigram'
);

-- 2글자 검색용 보조 색인. rowid는 rows의 rowid와 같다
CREATE VIRTUAL TABLE bigrams USING fts5(
  t, content = '', contentless_delete = 1, detail = none,
  tokenize = 'unicode61'
);

-- 세션 하나 검색용. rows의 FTS5 내용 테이블에서 경로 열(c0)로 그 세션의 행만 고른다
CREATE INDEX IF NOT EXISTS rows_content_path ON rows_content(c0);
```

- `rows_content_path` 인덱스는 기동 때 한 번 만든다(색인 7GB에서 약 12초, 인덱스 크기 약 174MB). 만들지 못하면 쓰지 않고 FTS 경로로 찾는다. 이 인덱스를 만들었다고 색인 파일을 지우고 다시 만들지 않는다. 내용 테이블의 열 순서는 `rows` 선언 순서(path, tier, uuid, ts, body = c0..c4)다. 내용 테이블은 FTS5의 내부 테이블이라 SQLite가 직접 수정을 권하지 않는다. 인덱스는 추가만 하므로 이전 버전도 그대로 읽는다. 끄는 길은 이 변경을 되돌리는 것뿐이다 — 돌고 있는 서버에서 인덱스만 지우면 서버는 인덱스가 있다고 믿어 그 테이블 전체를 `c0` 조건으로 훑어 결과는 같고 느려지며, 기동마다 다시 만들기 때문이다. `DROP INDEX rows_content_path`는 되돌린 뒤 인덱스 공간(약 174MB)을 거두는 단계다
- `tier`는 정수로 저장한다: `conversation` 0, `tool` 1, `meta` 2
- `path`는 `serve`가 등록한 세션 파일의 절대 경로다
- `bigrams.t`는 본문을 유니코드 소문자로 접은 뒤 인접한 코드 포인트 쌍마다 토큰 하나(`x` + 코드 포인트 16진수 6자리 두 개, 중복 제거)를 공백으로 이은 문자열이다. 코드 포인트가 2개 미만인 본문은 넣지 않는다. 토큰이 16진수라 `unicode61`이 자르거나 접지 않는다

### 동기화

파일 하나의 동기화는 하나의 트랜잭션이다.

1. `stat`. 실패하면 `files.failure`에 사유를 쓰고 끝
2. `files`에 행이 없거나, `ino`가 다르거나, 크기 < `indexed_offset` → 그 `path`의 `rows`·`bigrams`·`per_session_seen` 행을 지우고 `indexed_offset = 0`, 카운터 0에서 다시 시작
3. `indexed_offset`부터 파일 끝까지 읽어 마지막 개행까지의 줄만 처리한다. 개행으로 끝나지 않은 마지막 조각은 다음 동기화로 미룬다
4. 줄마다 `extractSearchRows`. `perSession` 행은 `per_session_seen`에 없을 때만 넣는다. 넣은 `rows` 행마다 같은 `rowid`로 `bigrams`에도 넣는다
5. `indexed_offset`, 카운터, `failure = NULL`을 갱신하고 커밋

### 검색 조건

`src/core/types.ts`의 `SearchFilters`로 두고, `serve`가 쿼리 문자열에서 만들어 워커에 넘긴다.

```ts
interface SearchFilters {
  /** 이 시각 이상(포함). null이면 제한 없음 */
  readonly since: string | null;
  /** 이 시각 미만(미포함). null이면 제한 없음 */
  readonly until: string | null;
  /** 이 등급만. null이면 모든 등급 */
  readonly tiers: readonly SearchTier[] | null;
}
```

- `since`·`until`: ISO 8601 시각 문자열. `new Date(값).toISOString()`으로 정규화해(UTC, 밀리초, `Z`) 색인의 `ts`와 문자열로 비교한다. 해석하지 못하면 `400` "시작 시각 형식이 올바르지 않습니다" / "끝 시각 형식이 올바르지 않습니다". 둘 다 있고 `since >= until`이면 `400` "기간이 비어 있습니다"
- `tiers`: 쉼표로 이은 `conversation`, `tool`, `meta`의 부분집합. 모르는 값이 있거나 빈 문자열이면 `400` "종류가 올바르지 않습니다". 셋을 모두 적으면 `null`과 같다. 중복은 하나로 본다
- 값이 없는 조건은 제한하지 않는다. `since`나 `until`이 하나라도 있으면 `ts`가 null인 행은 결과에서 빠진다 (시각을 모르므로 기간에 속하는지 판단할 수 없다)
- 조건은 순위·묶음·상한보다 먼저 적용한다. `matchCount`, `bestTier`, `latestAt`, 세션 선정은 모두 조건에 맞는 행만으로 계산한다

### 질의

#### 검색어의 낱말

검색어를 공백(`\s+`)으로 나눈 낱말(중복 제거)을 **모두** 담은 행이 매치다. 낱말의 순서와 거리는 보지 않는다. 예외:

- 검색어 전체가 큰따옴표로 감싸여 있으면(3글자 이상, 첫 글자가 `"` 또는 `“`, 끝 글자가 `"` 또는 `”`) 안쪽을 공백까지 포함해 낱말 하나로 본다. 정확한 구절을 찾는 방법이다. 문서나 메신저에서 복사하면 따옴표가 둥글게 들어오므로 둥근 쌍도 같게 본다. 한쪽에만 있거나 검색어의 일부만 감싼 따옴표는 구절이 아니라 낱말의 글자다
- 공백뿐인 검색어는 그대로 낱말 하나다

낱말마다 길이(코드 포인트)로 경로를 고르고, 모든 경로를 `AND`로 잇는다.

- 3 이상: 낱말마다 `'"' || replace(t, '"', '""') || '"'`를 공백으로 이어 `rows MATCH ?` 하나로 묻는다(FTS5의 암묵적 `AND`). trigram 기본 설정이라 유니코드 대소문자를 구분하지 않는다
- 정확히 2: 낱말을 유니코드 소문자로 접어 토큰으로 만들고, 토큰들을 공백으로 이어 `bigrams MATCH ?` 하나로 묻는다. 3 이상 낱말이 있으면 `rows.rowid IN (SELECT rowid FROM bigrams WHERE …)`로, 없으면 `rowid`로 `rows`를 잇는다. 대소문자는 비ASCII도 구분하지 않는다. 접은 뒤 코드 포인트가 2개가 아니면(예: `İ`) 아래 `LIKE`로 대신한다
- 1, 또는 위의 대신하는 경우: 낱말마다 `body LIKE '%' || esc(t) || '%' ESCAPE '\'` (`%`, `_`, `\`를 이스케이프). 다른 경로의 낱말이 없으면 전체를 훑는다. SQLite `LIKE`는 ASCII만 대소문자를 구분하지 않는다
- 대상은 이번 `serve`에 등록된 `path`로 한정한다
- 위 세 경로 모두 같은 `WHERE`에 검색 조건을 붙인다: `ts >= ?`, `ts < ?`, `tier IN (…)`(정수 등급). 경로마다 조건 적용 방식이 갈리지 않는다

### 순위와 상한

정렬 키는 `(tier 오름차순, ts 내림차순)`이다. `ts`가 null인 행은 같은 등급의 맨 뒤에 둔다.

워커는 매치의 `(path, tier, ts, rowid)`만 한 번 가져와 JS에서 정렬·묶음·상한을 적용하고, 반환할 행의 `body`만 `rowid`로 다시 읽는다. 순위를 SQL의 CTE·상관 서브쿼리로 계산하지 않는다 (Design "순위").

- 세션 하나(`/api/session/:id/search`): 정렬 순 상위 1,000건. `matchCount`는 전체 건수. 매치는 `rows_content_path` 인덱스로 그 세션의 행만 골라 낱말마다 `LIKE '%낱말%'`로 거른다. `LIKE`는 ASCII만 대소문자를 접으므로 대소문자가 있는 비ASCII 글자(예: `É`)가 든 낱말이 있거나 인덱스가 없으면 FTS 경로로 찾는다. 조건의 종류·시각 열에는 단항 `+`를 붙여 인덱스 후보에서 빼므로, `rows_content`에 인덱스가 더 있어도 플래너는 경로 인덱스를 고른다. 두 경로의 매치·건수·제외 건수는 같다. 다만 본문에 켈빈 기호(U+212A)나 긴 s(U+017F)가 있으면 FTS는 이를 `k`·`s`로 접어 찾고 `LIKE`는 접지 않아, 그 글자가 든 행은 인덱스 경로에서 ASCII 낱말(`kg`, `laser` 등)로 걸리지 않는다. 검색어에 그 글자가 있는 경우는 위 폴백으로 같다
- 전 세션(`/api/search`): 세션별로 `bestTier = min(tier)`, `latestAt = max(ts)`(그 최고 등급 행 기준)를 구해 `(bestTier 오름차순, latestAt 내림차순)`으로 세션을 정렬하고 상위 50개 세션을 고른다. 세션마다 정렬 순 상위 20건과 전체 `matchCount`를 돌려준다

### 응답 타입

`src/core/types.ts`에 추가한다. 기존 `SearchResult`, `SessionSearchResult`, `RawMatch`는 삭제한다. `MatchAttribution`은 유지한다.

```ts
interface IndexStatus {
  /** 등록된 세션이 모두 한 번 이상 동기화를 마쳤는가 */
  readonly ready: boolean;
  readonly indexedSessions: number;
  readonly totalSessions: number;
  /** 동기화에 실패한 세션 */
  readonly failed: readonly {
    readonly sessionId: string;
    readonly reason: string;
  }[];
  /** 아래 불변식을 어긴 세션 */
  readonly suspect: readonly string[];
}

interface SearchHit {
  readonly tier: SearchTier;
  readonly timestamp: string | null;
  readonly excerpt: string;
  /** 매치가 든 레코드의 uuid. 없으면 null — 조각으로 이동할 수 없다 */
  readonly uuid: string | null;
}

/** 세션 하나 검색의 매치. 조각 귀속까지 포함한다 */
interface SearchMatch extends SearchHit {
  readonly attribution: MatchAttribution;
}

interface SessionHits {
  readonly sessionId: string;
  readonly bestTier: SearchTier;
  readonly latestAt: string | null;
  readonly matchCount: number;
  /** 전 세션 검색은 귀속하지 않는다 (아래 "귀속") */
  readonly matches: readonly SearchHit[];
}

interface SearchResponse {
  readonly query: string;
  /** 이 검색의 식별자. 화면이 `open`·`answer`·`notfound` 기록을 이 검색에 잇는다 */
  readonly searchId: string;
  readonly index: IndexStatus;
  readonly sessions: readonly SessionHits[];
  /** 매치가 있는 세션이 50개를 넘어 잘렸으면 true */
  readonly truncatedSessions: boolean;
    term: string;
    query: string;
    sessionCount: number;
  }[];
  readonly durationMs: number;
}

interface ExcludedResponse {
  readonly query: string;
  /** 종류 조건 때문에 빠진 매치의 수. 종류 조건이 없으면 0 */
  readonly excludedMatchCount: number;
  readonly durationMs: number;
}

interface SessionSearchResponse {
  readonly query: string;
  readonly index: IndexStatus;
  readonly matchCount: number;
  readonly matches: readonly SearchMatch[];
  readonly truncated: boolean;
  /** 종류 조건 때문에 빠진 매치의 수. 종류 조건이 없으면 0 */
  readonly excludedMatchCount: number;
  readonly durationMs: number;
}
```

### 발췌

색인에 저장된 `body`에서 만든다. 파일을 다시 읽지 않는다.

- 위치: 낱말마다 `body.toLowerCase().indexOf(t.toLowerCase())`를 구해 가장 앞선 것. 하나도 못 찾으면(대소문자 접기에서 길이가 바뀌는 문자) `body` 앞부분을 쓴다
- 창: 매치 앞뒤 120자(코드 포인트), 잘린 쪽에 `…`

### 귀속

귀속의 목적은 매치를 눌렀을 때 그 조각으로 이동하는 것이다. 조각 안의 위치는 귀속이 아니라 화면이 조각 상세(`SegmentDetail.nodes`)에서 `uuid`를 찾아 정한다 (아래 "화면"). 세션 인덱스가 제외한 레코드의 매치도 결과에 남는다는 보장은 색인이 한다 — 색인 행은 세션 인덱스와 무관하게 레코드에서 뽑는다. 따라서 귀속은 이동에 필요한 시점에만 한다.

- **세션 하나 검색**: 그 세션이 열려 있어 세션 인덱스가 있으므로 응답에서 귀속한다. `uuid`가 null이면 `{kind: "none"}`, 아니면 `ensureFresh`로 구한 인덱스에 `attributeOne`을 적용한다. 세션 인덱스 구축이 실패하면 매치는 모두 `none`이고 `index.failed`에 사유를 더한다
- **전 세션 검색**: 귀속하지 않고 `uuid`만 돌려준다. 세션 인덱스를 만들지 않는다
- **이동**: 전 세션 결과의 매치를 누르면 그 세션을 연 뒤 `/api/session/:id/attribution?uuid=`로 조각을 찾는다. 이 API는 `ensureFresh` + `attributeOne`이다

전 세션 응답에서 귀속하지 않는 근거는 실측이다 — 반환할 세션(최대 50개)마다 메인 스레드에서 세션 인덱스를 만들면, 처음 보는 세션들에 대한 검색이 5.9초 걸렸고 그동안 `/api/sessions`가 최대 5.6초 기다렸다 (아래 "성능 요구사항"의 100ms 위반).

### 검색 기록

검색 품질(순위) 평가에 쓸 질의와 정답 후보를 모은다. `--cache-dir` 아래 `search-log.jsonl`에 한 요청당 한 줄을 덧붙인다. 실제 세션 내용이 담기므로 파일은 `0600`, 디렉터리는 `0700`이다.

- `search`: `/api/search`·`/api/session/:id/search`가 200으로 답할 때. `{at, kind, query, filters, sessionId, results, matchCount, indexReady, durationMs, workerMs?, syncMs?, syncedFiles?, searchId?}` — `filters`는 `{since, until, tiers}`(`SearchFilters`와 같은 값, 안 건 조건은 `null`). `sessionId`는 세션 하나 검색이면 그 id, 전 세션이면 `null`. `results`는 전 세션 응답의 세션 id를 순위 순으로, 세션 하나 검색이면 `[]`. `searchId`는 전 세션 검색에만 있고 응답의 `searchId`와 같다. `workerMs`는 검색 워커가 요청을 받아 답을 만드는 데 쓴 시간, `syncMs`·`syncedFiles`는 그 안에서 질의 앞에 바뀐 파일을 가려(등록 세션의 지문 확인) 동기화한 시간과 동기화한 파일 수다. `durationMs - workerMs`가 워커 밖(대기·전달·귀속)에서 쓴 시간이라, 느린 검색이 대기·동기화·질의 중 어디서 느렸는지 가른다. 전 세션 검색의 `durationMs`·`workerMs`는 `/api/search/excluded`가 빠진 종류의 건수를 세는 시간을 포함하지 않고 그 요청은 기록에 남기지 않는다(이 변경이 배포되기 전의 전 세션 줄은 그 시간을 포함한다). 이 필드가 없는 줄은 그것을 재기 전의 기록이다
- `open`: `/attribution`에 `q`와 1 이상의 정수 `rank`가 있을 때. `{at, kind, query, filters, sessionId, rank, uuid, searchId?}`. 화면이 전 세션 결과에서 매치를 누르면 그 세션의 순위와 검색어, 그 검색에 걸었던 조건, 검색 id를 싣는다. `rank`는 조건을 적용한 결과의 순위라서, 같은 검색어를 다른 조건으로 찾은 기록과 섞이지 않게 `filters`를 함께 남긴다. `/attribution`의 조건이 올바르지 않으면 응답은 그대로 하고 `open`만 남기지 않는다. 새로 고침·주소 직접 입력은 싣지 않아 남지 않는다
- `answer`: `/api/search/feedback`이 `kind=answer`로 200을 답할 때. `{at, kind, searchId, query, filters, sessionId, rank, snippetIndex, uuid, shown}`. 화면은 `searchId`·`sessionId`·`uuid`만 보내고 나머지는 서버가 그 검색에 내보낸 목록에서 채운다. `rank`는 그 세션의 순위, `snippetIndex`는 그 세션이 보여 준 매치 중 이 매치의 위치(둘 다 1부터), `shown`은 그 세션이 보여 준 매치의 `uuid`를 화면 순서로 담고 `uuid`가 없는 매치는 `null`이다. 한 검색에서 여러 번 남을 수 있다
- `notfound`: `kind=notfound`로 200을 답할 때. `{at, kind, searchId, query, filters, matchCount}`. `matchCount`는 그 검색의 전체 매치 수다
- `notfound-reason`: `kind=reason`으로 200을 답할 때. `{at, kind, searchId, query, filters, reason}`. `reason`은 `wrong-term`(낱말을 잘못 골랐다)·`not-in-results`(결과에 그 내용이 없다)·`below-fold`(결과에 있는데 아래쪽이라 못 봤다)·`filtered`(기간·종류 조건에 걸렸다)·`other` 중 하나다. `notfound`와 같은 `searchId`로 잇는다. 이유를 고르지 않아도 `notfound`는 남는다
- `filters`가 없는 줄은 조건이 없는 검색으로 읽는다
- 모든 줄은 선택 필드 `source`를 가질 수 있다. `search`·`open`은 요청의 `source`를, `answer`·`notfound`·`notfound-reason`은 그 `searchId`를 발급한 검색의 `source`를 싣는다. 필드가 없는 줄은 사람이 화면에서 한 것이다
- 쓰기에 실패하면 표준 에러에 알리고 응답은 그대로 한다

`GET`이 기록을 남기는 것은 접근 로그와 같아 안전한 메서드의 의미를 바꾸지 않는다 ([RFC 9110 §9.2.1](https://www.rfc-editor.org/rfc/rfc9110#section-9.2.1)). 세션 파일은 쓰지 않는다 ([ADR-0003](../adr/ADR-0003-cli-writes-web-reads.md)).

서버는 전 세션 검색마다 `searchId`(무작위 8바이트의 16진수)를 발급하고, 그 검색이 보여 준 세션과 매치의 `uuid`를 메모리에 최근 100개만 둔다. `answer`의 순위·위치·표시 목록을 화면이 보낸 값이 아니라 이 목록에서 채우는 것은 같은 검색에서도 화면에 보인 목록과 기록이 어긋나지 않게 하고, 임의의 줄이 기록에 남지 않게 하려는 것이다. 서버를 다시 시작하면 목록이 사라져 이전 화면의 버튼은 `404`를 받는다.

`source=llm`인 줄은 사람의 `answer`·`notfound`·재검색 신호와 섞지 않고 따로 센다. LLM의 검색은 사람이 화면에서 버튼을 누르지 않으면 `answer`·`notfound`가 붙지 않으므로 `source=llm`에서 찾았는지는 기록만으로 알 수 없다.

`open`은 정답 표시가 아니라 후보다 — 누른 결과가 찾던 것이라는 보장이 없다. `answer`는 사용자가 직접 답이라고 표시한 매치고, `notfound`는 못 찾았다고 표시한 검색이다. `reason`은 사용자의 자기 판단이라 실제 원인과 다를 수 있고, "결과에 그 내용이 없다"와 "있는데 알아보지 못했다"를 가르지 못한다. 표시를 하지 않은 검색은 정보가 없다: 결과 요약만 읽고 답을 얻은 경우와 포기한 경우를 가르지 못하고, 열었지만 오답이었던 경우도 `open`만으로는 알 수 없다.

### 불변식

- `conversation_records > 0`인데 `conversation_rows = 0`인 파일은 `suspect`다 — 대화 레코드가 있는데 색인할 대화 텍스트가 하나도 없다면 세션 형식이 바뀌었을 가능성이 높다 ([ADR-0004](../adr/ADR-0004-schema-drift-defense.md))
- `rows.body`는 SQLite가 실제로 저장하는 글자다 — 첫 NUL 앞까지, 짝 없는 서로게이트는 U+FFFD. `bigrams`는 같은 글자로 만든다. 그래서 2글자 결과 건수는 `LIKE`로 센 건수와 같다
- 같은 `path`에 대해 `rows`의 행들은 `indexed_offset` 이전 바이트에서만 나왔다
- `bigrams`의 `rowid`는 모두 `rows`의 `rowid`다. 코드 포인트가 2개 이상인 `rows` 행은 `bigrams`에 있다
- `matches`는 정렬 키 순이다
- `truncated === true` ⟺ `matchCount > matches.length`
- `excludedMatchCount`는 같은 검색어·기간·범위(전 세션이면 등록된 세션, 세션 하나면 그 세션)에서 종류 조건이 고르지 않은 종류에 속한 매치의 수다. `tiers`가 `null`이거나 세 종류를 모두 고르면 0이다. 매치가 있는 세션이 50개를 넘어도 세션 수 상한 없이 센다. 세션 하나 검색은 응답에 싣고, 전 세션 검색은 싣지 않는다
- `GET /api/search/excluded?q=…`(같은 기간·종류 조건 쿼리)는 `{ query, excludedMatchCount, durationMs }`를 돌려준다. 전 세션 검색이 빠진 종류의 매치를 세는 값이다. 흔한 낱말을 섞은 검색에서는 본 검색보다 오래 걸려(실제 색인에서 `git PR` 본 검색 3.1초, 건수 8–10초) 전 세션 검색 응답에 싣지 않고, 화면이 종류를 일부만 골랐을 때 결과를 그린 뒤 따로 부른다
- `GET /api/search/relaxed?q=…`(같은 기간·종류 조건 쿼리)는 `{ query, relaxed, durationMs }`를 돌려준다. `relaxed`는 검색어의 낱말(`searchTerms`)이 2~6개일 때 낱말 하나를 뺀 검색어(`query`)마다 등록된 세션 중 걸리는 수(`sessionCount`)를 센 목록이다. 0인 것은 넣지 않고 세션 수가 많은 순이다. 구(phrase) 검색, 낱말이 하나이거나 7개 이상인 검색은 빈 배열이다. 남은 낱말이 흔하면 수 초가 걸려(실제 색인에서 `the` 하나를 남긴 검색 11초) 전 세션 검색 응답에 싣지 않고, 화면이 0건일 때만 따로 부른다

## 엣지 케이스 & 에러 처리

**기동과 첫 생성**

- 색인 파일이 없음 → 만들고 등록 세션을 `mtime` 내림차순으로 동기화한다
- `schema_version`이 2가 아님, 또는 SQLite가 파일을 열지 못함(손상) → 파일(`-wal`, `-shm` 포함)을 지우고 새로 만든다
- 첫 생성 도중 검색 → 그때까지 색인된 세션만으로 답하고 `index.ready: false`. 화면은 "색인 중 (N/M 세션) — 결과가 일부일 수 있습니다"를 결과 위에 표시한다
- 캐시 디렉터리를 만들 수 없음 → `serve`는 기동하되 검색 요청은 `503` "검색 색인을 만들 수 없습니다: {사유}". 다른 기능은 영향받지 않는다

**검색 요청 시 갱신**

- 요청마다 이미 한 번 동기화를 마친 등록 세션의 지문(`ino`, `size`)을 확인하고, 바뀐 파일만 동기화한 뒤 질의한다. 아직 첫 동기화 전인 세션은 백그라운드 생성에 맡긴다
- 동기화 실패한 세션 → 결과에서 빠지고 `index.failed`에 나온다. 화면은 실패 세션을 제목(없으면 라벨)과 사유로 표시한다

**질의**

- 매치 0건이고 `index.ready && failed.length === 0` → "찾지 못했습니다". 조건이 걸려 있으면 "조건을 걸고 찾았습니다 — 조건 때문일 수 있습니다"를 덧붙인다
- 매치 0건이지만 색인 중이거나 실패 세션이 있음 → "찾지 못했습니다"에 그 사실을 덧붙인다. 확신에 찬 0건을 내지 않는다
- 따옴표·역슬래시·개행이 든 검색어 → 색인 텍스트는 JSON에서 풀린 문자열이므로 그대로 찾는다. 이전의 "저장 형태가 달라 찾지 못할 수 있습니다" 안내는 삭제한다
- `"`가 든 검색어 → FTS5 구문에서 `""`로 이스케이프한다. 검색어는 언제나 하나의 구(phrase)로 취급한다 (`AND`, `*` 등 FTS5 연산자로 해석하지 않는다)

**화면**

- 전 세션 결과의 세션 머리글은 `title`을 쓰고, 없으면 `label`을 쓴다
- 매치마다 등급 표시: "대화" / "도구" / "기타"
- 매치의 발췌 안에서 검색어의 낱말과 일치하는 부분을 `<mark>`로 칠한다(`highlightSegments`, `src/core/search-terms.ts`). 낱말은 서버가 발췌를 고를 때 쓰는 `searchTerms`와 같은 규칙이다: 공백으로 나눈 낱말을 각각 대소문자 무시 부분 문자열로 찾고, 검색어 전체가 큰따옴표면 구절 하나로 찾는다. 겹치거나 맞닿은 일치는 하나로 합친다. 소문자로 바꾸면 길이가 달라지는 글자가 발췌에 있으면 칠하지 않는다(서버도 그때는 위치를 못 잡고 본문 앞부분을 발췌로 쓴다). 글은 DOM의 텍스트로만 넣는다
- 상태 메시지는 화면 읽기 프로그램에 알린다(WCAG 4.1.3). 처음 마크업에 있는 `#live`(`role="status"`)의 글을 바꿔 검색이 끝난 결과("세션 N개에서 찾았습니다"·"이 세션에서 N건을 찾았습니다"·0건 문구(색인 중·실패 세션 단서 포함, 화면과 같은 글))와 "이게 답"·"못 찾았다" 기록의 성공·실패, 화면에 오류 줄을 띄우는 검색 실패·종류 미선택·조각 불러오기 실패를 알린다. `#summary`는 `role="status"`, `#banner`는 `role="alert"`다. 같은 글이 연달아 나오면 글이 바뀌지 않아 다시 알리지 않는다
- 검색 입력은 `role="search"`, 결과 영역은 `role="region"`(이름 "검색 결과")로 두어 모든 내용이 랜드마크 안에 있게 한다. 색인 경고(`#warnings`)는 경고가 있을 때만 `role="region"`(이름 "색인 경고")을 갖는다. 헤더와 `main`(조각 목록·타임라인) 밖에 있던 요소가 axe-core의 `region` 규칙을 어겼다
- 전 세션 결과에서 `uuid`가 있는 매치를 누르면 `#session/{id}/uuid/{uuid}`로 이동한다. 세션을 연 뒤 귀속 결과가 `segment`면 그 조각을 펼치고 조각 안의 그 레코드로 간다(아래 "조각 안 위치"). `orphan`·`unindexed`면 "이 레코드는 조각에 속하지 않습니다"를 알린다. `uuid`가 null인 매치는 누를 수 없다
- 같은 매치를 다시 눌러 주소가 그대로여도 이동을 다시 실행한다 (주소 변경 이벤트에 기대지 않는다)
- 세션 하나 결과는 귀속이 `segment`인 매치만 누를 수 있고, 나머지는 "조각으로 이동할 수 없는 매치"로 따로 묶는다
- 전 세션 결과가 비어 있지 않으면 결과 위에 "못 찾았다" 버튼을 하나 둔다. 누르면 `kind=notfound`를 기록하고 "기록했습니다"로 바뀌어 눌린 채로 남는다. 그 아래에 이유 선택지(`NOTFOUND_REASONS`)가 나타나며, 하나를 고르면 `kind=reason`을 기록하고 나머지는 눌리지 않게 된다. 고르지 않아도 된다
- 전 세션 결과의 `uuid`가 있는 매치 옆에 "이게 답" 버튼을 둔다. 매치 줄 자체가 버튼이라 그 안에 넣지 않고 같은 줄의 옆에 둔다. 누르면 `kind=answer`를 기록하고 "답으로 기록함"으로 바뀌어 눌린 채로 남는다. 기록하지 못하면 사유를 보이고 다시 누를 수 있다. 두 버튼 모두 결과를 보는 데 영향을 주지 않는다
- `matchCount > matches.length`면 "N건 중 M건"을 머리글에 표시한다. `truncatedSessions`면 "매치가 있는 세션이 많아 상위 50개만 표시합니다"
- 요청마다 순번을 붙이고, 마지막 요청이 아닌 응답은 버린다. 세션을 열거나 목록으로 돌아가면 진행 중인 응답도 버린다

**조각 안 위치**

귀속이 `segment`일 때, 화면은 `attribution.segmentRootUuid`의 조각 머리를 찾아 다음 순서로 이동한다.

1. 조각 머리가 없으면 "조각을 찾지 못했습니다 ({segmentRootUuid})"를 알린다. 조용히 끝내지 않는다
2. 접혀 있으면 펼친다. 이미 펼쳐져 있으면 접지 않는다. 펼칠 때 시작되는 조각 상세 불러오기가 끝날 때까지 기다린다. 불러오기가 실패하면 그 오류 표시가 그대로 남고 이동은 끝난다
3. 조각 상세의 `nodes`에서 `uuid`가 같은 노드의 위치(`index`)를 찾는다. 없으면 "조각 안에서 레코드를 찾지 못했습니다 ({uuid})"를 알린다
4. 조각 본문 영역(`.viewport`)의 `scrollTop`을 `index * ROW_HEIGHT`에서 영역 높이의 절반만큼 되돌린 값(0 미만이면 0)으로 둔다. 레코드가 영역 가운데에 온다. 그다음 조각 본문 영역이 화면 가운데에 오게 한다
5. 그 노드 행에 강조 표시(`.revealed`)를 붙인다. 가상 스크롤이 행을 다시 만들어도 유지되도록 강조할 `uuid`를 모듈 상태로 두고 행을 만들 때 대조한다. 다른 매치로 이동하거나, 세션을 바꾸거나, 목록으로 돌아가면 지운다

행 높이(`ROW_HEIGHT`)는 바꾸지 않는다 — 위치는 `index * ROW_HEIGHT`로 계산된다. 새 API를 추가하지 않는다.

**검색 조건 입력**

- 검색창 옆에 종류(대화·도구·기타 체크박스 셋, 처음에는 대화만 선택)와 기간(선택 목록: 전체·최근 7일·30일·90일, 기본 전체)을 둔다. 전 세션 검색과 세션 하나 검색에 같은 조건을 쓴다
- 최근 N일은 브라우저의 로컬 시간대로 해석한다: 오늘을 포함해 N일 전 0시가 `since`가 되고 `until`은 싣지 않는다([표시 시각의 시간대 Design](../design/20260904-1600-timezone-display.tdd.md)과 같은 기준). 날짜를 직접 고르는 입력은 두지 않는다 — 값이 비어 있을 때 형식 안내를 그리지 않는 브라우저(아이폰)에서 칸이 비어 보였다. 서버의 `since`·`until`은 그대로 열어 둔다
- 종류를 모두 해제하면 검색하지 않고 "종류를 하나 이상 고르세요"를 알린다
- 조건 중 하나라도 기본값과 다르면 결과 위에 걸린 조건을 한 줄로 보여준다 ("조건: 기간 최근 30일 · 종류 대화, 도구"). 종류의 기본값은 대화만이라, 셋 모두 고른 경우에도 조건 줄에 보인다
- 종류를 일부만 골랐고 `excludedMatchCount`가 0보다 크면 결과 위(조건 줄이 있으면 그 아래)에 "도구·기타에도 N건 더 있습니다"와 "함께 보기" 버튼을 보인다(결과가 0건이어도 보인다). 전 세션 검색에서는 결과를 먼저 그리고 건수를 따로 받는다. 세는 동안은 "<빠진 종류> 건수를 세는 중…" 줄을 두고(종류 이름은 안내 문구와 같이 체크하지 않은 종류다), 도착하면 안내로 바꾸며(0건이면 줄을 지운다), 요청이 실패하면 "<빠진 종류> 건수를 세지 못했습니다"로 바꾼다. 그 사이 다른 검색이 시작됐으면 버린다. 버튼은 빠진 종류를 체크하고 다시 찾는다. 대화만으로 찾은 결과가 도구 출력에만 남은 내용을 가리지 않게 하려는 안내다
- 전 세션 검색이 0건이면 검색 결과와 따로 `/api/search/relaxed`를 받아, 비어 있지 않을 때 "찾지 못했습니다" 아래에 "‘낱말’ 빼고 찾기 (세션 N개)" 버튼을 보인다. 버튼은 그 낱말을 뺀 검색어로 입력줄을 바꾸고 다시 찾는다. 오타나 한 낱말 때문에 0건이 된 검색의 다음 시도를 알려 주려는 안내다
- 조건을 바꾸면 검색어가 있을 때 다시 찾는다. 검색어가 비어 있으면 찾지 않는다
- 조건은 이 화면 안에서만 유지한다. 새로 고침하면 기본값으로 돌아간다

**파일 변경**

- 세션 파일 교체(`ino` 변경)나 잘림 → 그 파일만 처음부터 다시 색인
- 등록 세션 파일이 사라짐 → 동기화 실패로 처리. 그 파일의 기존 행은 지우지 않지만 질의에서 제외된다
- 등록되지 않은 `path`의 행 → 지우지 않는다(다른 `serve` 호출이 등록할 수 있다). 질의 대상이 아닐 뿐이다

**여러 프로세스**

- 두 `serve`가 같은 색인 파일을 씀 → `busy_timeout` 5초. 넘으면 그 동기화는 실패로 기록하고 다음 요청에서 다시 시도한다

## 성능 요구사항

기준선은 [Design "기준선"](../design/20261015-1821-search-index.tdd.md#기준선)의 실측(실제 세션 1,693개, 6.74GB)이다.

- 전 세션 검색, 3글자 이상, 색인 완료 상태: **1초 이내** (실측 7~417ms, 최악은 매치 164,731건인 `the`)
- 전 세션 검색, 2글자, 색인 완료 상태: **1초 이내를 목표로 한다.** 실측 한국어 24~~372ms(`고아`·`비용`·`에러` 등). 매치가 수십만 건인 영어 쌍(`pr` 428,781건)은 1.5~~2.9초로 미충족 — 색인 조회가 아니라 매치 정렬·묶음 비용이다(3글자 `the`도 같은 경향)
- 전 세션 검색, 3글자 이상과 2글자 낱말을 섞은 경우: 비용은 3글자 이상 낱말이 좁힌 행 수에 비례해야 한다. 2글자 낱말은 좁혀진 행마다 `bigrams`를 rowid로 조회한다(서브쿼리로 만들면 2글자 낱말의 모든 행을 훑어 `Be ambitous`가 455초, `PR “노드 링크”`가 110초 걸렸다). 같은 데이터에서 각각 49ms, 7ms
- 전 세션 검색, 1글자: 기준 없음. `LIKE` 전체 스캔이라 색인 크기에 비례한다. 워커에서 돌아 다른 요청을 막지는 않는다
- 검색 중이나 색인 생성 중에 `/api/sessions` 응답: **100ms 이내** — DB 작업은 모두 워커에서 한다
- 첫 색인 생성: 기준 없음. 실측 417초(같은 데이터·기기에서 보조 색인 없는 코드는 215초). 진행 상태를 화면에 표시한다
  - 2026-11-25 다시 쟀다. 같은 기기이고 빈 캐시 디렉터리로 `serve`를 띄웠다. 대상은 `find ~/.claude/projects -maxdepth 2 -name "*.jsonl" ! -name "agent-*"`가 고른 세션 1,771개(합계 8.83GB)이고, 요청은 보내지 않았다. 끝은 서버 프로세스의 CPU 사용 시간이 15초 간격 표본에서 1초 미만으로 늘기를 4번 연속 한 시점에서 60초를 뺀 값이다. 약 570초였다(마지막으로 CPU가 늘어난 표본이 570초 시점). 색인 본 파일은 서버를 닫은 뒤 6,806MB(바이트÷10^6)였다. 아래 비교용 4,914MB가 같은 단위인지는 확인하지 않았다
  - 위 417초와 견주어 느려졌는지는 정하지 않는다. 417초는 2026-11-10에 세션 1,747개로 잰 값이고 그때의 코퍼스 크기는 기록이 없다. 세션 파일은 뒤에 덧붙기만 하므로(ADR-0008) 2026-10-15 기준선(세션 1,693개, 6.74GB)의 파일이 지금도 모두 있다(10-15 이전에 생긴 파일이 정확히 1,693개다)면 그때 코퍼스는 6.74GB 이상이다. 11-11 이전에 만들어진 파일 1,748개의 현재 크기 합이 8.73GB라 그때 코퍼스는 그 이하이고, 그러면 코퍼스는 +1% ~ +31% 늘었다. 시간은 +37%라 데이터 증가만으로는 설명되지 않을 수 있다. 그래도 느려졌다고 적지 않는다. 두 값 모두 단일 실행이라 오차가 있고(위 Design), 측정 중 CPU 부하를 통제하지 않았고, 생성 시간이 바이트에 비례한다는 근거가 없다. 세션 수는 +1.4% 늘었다
  - 첫 생성 중에 검색을 보내면 요청 하나가 0.06~37초 걸렸다(30초 간격으로 보낸 한 번의 시험, 513초 시점에 1,064개 세션이 색인됨). 요청이 색인과 같은 자원을 두고 다투는 것으로 보이나(추정) 원인은 확인하지 않았다. 캐시가 있으면 기동 1.1초 안에 준비되고 검색은 0.3초였다
- 색인 크기: 기준 없음. 실측 4,914MB(같은 데이터에서 보조 색인 없는 코드 4,657MB, 보조 색인이 +257MB)

## Out of Scope

- 관련도(`bm25`) 순위 — 측정 후 결정 (Design "향후 확장 고려사항")
- 색인 범위 밖 데이터(base64 첨부, `toolUseResult`, `file-history-snapshot`, `progress`, 파일 첨부 원문)의 검색
- uuid로 찾는 기능
- 뜻이 비슷한 말·오탈자 보정, 정규식
- 1글자 검색을 빠르게 하는 것, 1글자 비ASCII 대문자 검색의 대소문자 무시
- 색인 파일 크기 상한과 오래된 세션 정리
- 검색 기록의 회전·크기 상한과 화면에서 보는 기능
- 세션 하나 검색 결과에서의 "이게 답"·"못 찾았다" 기록. 전 세션 검색 결과에만 둔다
- 스니펫을 화면에서 읽었는지(스크롤 위치·머문 시간·선택·복사)를 재는 것. 표시는 버튼으로만 받는다
- 검색어 없이 조건만으로 목록을 보는 기능, 조건의 저장, 조건을 새로 고침 뒤에도 남기는 것
- 매치 낱말을 레코드 본문 안에서 강조하는 것 — 낱말 강조는 결과의 발췌 줄 안에서만 하고, 이동한 레코드는 노드 행 하나를 강조한다
- 결과 스트리밍 — 색인 질의가 1초 안에 끝나므로 필요 없다
