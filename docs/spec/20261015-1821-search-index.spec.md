# Spec: 영속 검색 색인

## Interface

### HTTP 엔드포인트

경로는 [본문 검색 Spec](20260906-0900-body-search.spec.md)과 같고, 응답 형식이 바뀐다. `GET`만 허용하고 쓰기 메서드는 `405`다 ([`serve` Spec](20260902-0420-serve-command.spec.md#http-엔드포인트)).

| 경로                                       | 응답                                         |
| ------------------------------------------ | -------------------------------------------- |
| `/api/search?q=<문구>`                     | `SearchResponse` — 등록된 모든 세션          |
| `/api/session/:id/search?q=<문구>`         | `SessionSearchResponse` — 세션 하나          |
| `/api/session/:id/attribution?uuid=<uuid>` | `MatchAttribution` — 레코드 하나가 속한 조각 |

- `q`: 필수. 앞뒤 공백을 자르지 않고 그대로 쓴다. 빈 문자열이면 `400` "검색어가 필요합니다". 1,000자(코드 포인트)를 넘으면 `400` "검색어가 너무 깁니다"
- `uuid`: 필수. 없거나 빈 문자열이면 `400` "uuid가 필요합니다"
- `/attribution`의 `q`·`rank`: 선택. 화면이 전 세션 결과에서 누른 이동에만 싣는다. 응답은 같고 "검색 기록"에만 쓰인다
- `:id`가 목록에 없으면 `404`
- `/attribution`에서 세션 인덱스 구축이 실패하면 다른 세션 경로와 같이 `500`

### `serve` 옵션

- `--cache-dir <dir>`: 색인 파일과 검색 기록을 둘 디렉터리. 기본값은 `$XDG_CACHE_HOME/sessgraph`, `XDG_CACHE_HOME`이 없으면 `~/.cache/sessgraph`. 테스트는 임시 디렉터리를 넘긴다

### 코어 함수

`src/core/search-text.ts` — 파일 I/O 없는 순수 함수.

```ts
export type SearchTier = "conversation" | "tool" | "meta";

export interface SearchRow {
  readonly tier: SearchTier;
  readonly text: string;
  /** 레코드의 uuid. 없으면 null. 색인에 저장만 하고 검색 대상은 아니다 */
  readonly uuid: string | null;
  /** 레코드의 timestamp(ISO 문자열). 없으면 null */
  readonly timestamp: string | null;
  /** true면 세션 단위로 값마다 한 번만 색인한다 (cwd, gitBranch) */
  readonly perSession: boolean;
}

export interface ExtractedLine {
  readonly rows: readonly SearchRow[];
  /** type이 "user" 또는 "assistant"인 레코드였는가 (아래 "불변식"의 드리프트 감지용) */
  readonly conversationRecord: boolean;
}

/** JSONL 한 줄. JSON 파싱 실패면 { rows: [], conversationRecord: false } */
export function extractSearchRows(line: string): ExtractedLine;
```

`src/core/search.ts`의 `scanFile`과 관련 상수·테스트는 삭제한다. 매치를 조각에 귀속시키는 로직(`attributeOne`)은 남겨 `uuid → MatchAttribution`으로 쓴다.

## 데이터 모델

### 추출 규칙 (`extractSearchRows`)

레코드 `r`에 대해 아래 순서로 적용한다.

1. `r.cwd`, `r.gitBranch`가 문자열이면 각각 `{tier: "meta", perSession: true}` 행
2. `r.type`이 `"file-history-snapshot"` 또는 `"progress"`면 여기서 끝
3. `r.type === "attachment"`이고 `r.attachment.type === "file"`이면 여기서 끝
4. `r.type`이 `"user"`/`"assistant"`이고 `r.message.content`가 있으면:
   - 문자열 → `conversation` 행 하나
   - 배열 → 블록마다: `text`는 `.text`를, `thinking`은 `.thinking`을 `conversation` 행으로. `tool_use`/`tool_result`는 문자열 값 모음을 `tool` 행으로. 그 밖의 블록 타입은 문자열 값 모음을 `meta` 행으로
5. 그 밖의 레코드는 레코드 전체의 문자열 값 모음을 `meta` 행으로

**문자열 값 모음**: 객체를 재귀로 훑어 문자열 값을 `\n`으로 잇는다. 다음은 건너뛴다.

- 키: `uuid`, `parentUuid`, `logicalParentUuid`, `sessionId`, `requestId`, `messageId`, `leafUuid`, `id`, `tool_use_id`, `timestamp`, `signature`, `toolUseResult`
- `type === "base64"`이고 `data`가 문자열인 객체 전체

빈 문자열 행은 만들지 않는다.

### 색인 파일

`<cache-dir>/search-v1.sqlite`. 디렉터리는 `0700`, 파일은 `0600`으로 만든다. WAL 모드.

```sql
CREATE TABLE meta (key TEXT PRIMARY KEY, value TEXT NOT NULL);
-- ('schema_version', '2')

CREATE TABLE files (
  path TEXT PRIMARY KEY,
  ino INTEGER NOT NULL,
  indexed_offset INTEGER NOT NULL,   -- 마지막으로 색인한 완결 줄의 다음 바이트
  conversation_records INTEGER NOT NULL,
  conversation_rows INTEGER NOT NULL,
  failure TEXT                       -- 마지막 동기화 실패 사유, 성공하면 NULL
);

CREATE TABLE per_session_seen (path TEXT NOT NULL, value TEXT NOT NULL, PRIMARY KEY (path, value));

CREATE VIRTUAL TABLE rows USING fts5(
  path UNINDEXED, tier UNINDEXED, uuid UNINDEXED, ts UNINDEXED, body,
  tokenize = 'trigram'
);

-- 2글자 검색용 보조 색인. rowid는 rows의 rowid와 같다
CREATE VIRTUAL TABLE bigrams USING fts5(
  t, content = '', contentless_delete = 1, detail = none,
  tokenize = 'unicode61'
);
```

- `tier`는 정수로 저장한다: `conversation` 0, `tool` 1, `meta` 2
- `path`는 `serve`가 등록한 세션 파일의 절대 경로다
- `bigrams.t`는 본문을 유니코드 소문자로 접은 뒤 인접한 코드 포인트 쌍마다 토큰 하나(`x` + 코드 포인트 16진수 6자리 두 개, 중복 제거)를 공백으로 이은 문자열이다. 코드 포인트가 2개 미만인 본문은 넣지 않는다. 토큰이 16진수라 `unicode61`이 자르거나 접지 않는다

### 동기화

파일 하나의 동기화는 하나의 트랜잭션이다.

1. `stat`. 실패하면 `files.failure`에 사유를 쓰고 끝
2. `files`에 행이 없거나, `ino`가 다르거나, 크기 < `indexed_offset` → 그 `path`의 `rows`·`bigrams`·`per_session_seen` 행을 지우고 `indexed_offset = 0`, 카운터 0에서 다시 시작
3. `indexed_offset`부터 파일 끝까지 읽어 마지막 개행까지의 줄만 처리한다. 개행으로 끝나지 않은 마지막 조각은 다음 동기화로 미룬다
4. 줄마다 `extractSearchRows`. `perSession` 행은 `per_session_seen`에 없을 때만 넣는다. 넣은 `rows` 행마다 같은 `rowid`로 `bigrams`에도 넣는다
5. `indexed_offset`, 카운터, `failure = NULL`을 갱신하고 커밋

### 질의

- 검색어 길이(코드 포인트)가 3 이상: `rows MATCH '"' || replace(q, '"', '""') || '"'`. trigram 기본 설정이라 유니코드 대소문자를 구분하지 않는다
- 정확히 2: 검색어를 유니코드 소문자로 접어 토큰 하나로 만들고 `bigrams MATCH '"' || token || '"'`의 `rowid`로 `rows`를 잇는다. 대소문자는 비ASCII도 구분하지 않는다. 접은 뒤 코드 포인트가 2개가 아니면(예: `İ`) 아래 `LIKE`로 대신한다
- 1, 또는 위의 대신하는 경우: `body LIKE '%' || esc(q) || '%' ESCAPE '\'` (`%`, `_`, `\`를 이스케이프). 전체를 훑는다. SQLite `LIKE`는 ASCII만 대소문자를 구분하지 않는다
- 대상은 이번 `serve`에 등록된 `path`로 한정한다

### 순위와 상한

정렬 키는 `(tier 오름차순, ts 내림차순)`이다. `ts`가 null인 행은 같은 등급의 맨 뒤에 둔다.

워커는 매치의 `(path, tier, ts, rowid)`만 한 번 가져와 JS에서 정렬·묶음·상한을 적용하고, 반환할 행의 `body`만 `rowid`로 다시 읽는다. 순위를 SQL의 CTE·상관 서브쿼리로 계산하지 않는다 (Design "순위").

- 세션 하나(`/api/session/:id/search`): 정렬 순 상위 1,000건. `matchCount`는 전체 건수
- 전 세션(`/api/search`): 세션별로 `bestTier = min(tier)`, `latestAt = max(ts)`(그 최고 등급 행 기준)를 구해 `(bestTier 오름차순, latestAt 내림차순)`으로 세션을 정렬하고 상위 50개 세션을 고른다. 세션마다 정렬 순 상위 20건과 전체 `matchCount`를 돌려준다

### 응답 타입

`src/core/types.ts`에 추가한다. 기존 `SearchResult`, `SessionSearchResult`, `RawMatch`는 삭제한다. `MatchAttribution`은 유지한다.

```ts
interface IndexStatus {
  /** 등록된 세션이 모두 한 번 이상 동기화를 마쳤는가 */
  readonly ready: boolean;
  readonly indexedSessions: number;
  readonly totalSessions: number;
  /** 동기화에 실패한 세션 */
  readonly failed: readonly {
    readonly sessionId: string;
    readonly reason: string;
  }[];
  /** 아래 불변식을 어긴 세션 */
  readonly suspect: readonly string[];
}

interface SearchHit {
  readonly tier: SearchTier;
  readonly timestamp: string | null;
  readonly excerpt: string;
  /** 매치가 든 레코드의 uuid. 없으면 null — 조각으로 이동할 수 없다 */
  readonly uuid: string | null;
}

/** 세션 하나 검색의 매치. 조각 귀속까지 포함한다 */
interface SearchMatch extends SearchHit {
  readonly attribution: MatchAttribution;
}

interface SessionHits {
  readonly sessionId: string;
  readonly bestTier: SearchTier;
  readonly latestAt: string | null;
  readonly matchCount: number;
  /** 전 세션 검색은 귀속하지 않는다 (아래 "귀속") */
  readonly matches: readonly SearchHit[];
}

interface SearchResponse {
  readonly query: string;
  readonly index: IndexStatus;
  readonly sessions: readonly SessionHits[];
  /** 매치가 있는 세션이 50개를 넘어 잘렸으면 true */
  readonly truncatedSessions: boolean;
  readonly durationMs: number;
}

interface SessionSearchResponse {
  readonly query: string;
  readonly index: IndexStatus;
  readonly matchCount: number;
  readonly matches: readonly SearchMatch[];
  readonly truncated: boolean;
  readonly durationMs: number;
}
```

### 발췌

색인에 저장된 `body`에서 만든다. 파일을 다시 읽지 않는다.

- 위치: `body.toLowerCase().indexOf(q.toLowerCase())`. 못 찾으면(대소문자 접기에서 길이가 바뀌는 문자) `body` 앞부분을 쓴다
- 창: 매치 앞뒤 120자(코드 포인트), 잘린 쪽에 `…`

### 귀속

귀속의 목적은 매치를 눌렀을 때 그 조각으로 이동하는 것이다. 세션 인덱스가 제외한 레코드의 매치도 결과에 남는다는 보장은 색인이 한다 — 색인 행은 세션 인덱스와 무관하게 레코드에서 뽑는다. 따라서 귀속은 이동에 필요한 시점에만 한다.

- **세션 하나 검색**: 그 세션이 열려 있어 세션 인덱스가 있으므로 응답에서 귀속한다. `uuid`가 null이면 `{kind: "none"}`, 아니면 `ensureFresh`로 구한 인덱스에 `attributeOne`을 적용한다. 세션 인덱스 구축이 실패하면 매치는 모두 `none`이고 `index.failed`에 사유를 더한다
- **전 세션 검색**: 귀속하지 않고 `uuid`만 돌려준다. 세션 인덱스를 만들지 않는다
- **이동**: 전 세션 결과의 매치를 누르면 그 세션을 연 뒤 `/api/session/:id/attribution?uuid=`로 조각을 찾는다. 이 API는 `ensureFresh` + `attributeOne`이다

전 세션 응답에서 귀속하지 않는 근거는 실측이다 — 반환할 세션(최대 50개)마다 메인 스레드에서 세션 인덱스를 만들면, 처음 보는 세션들에 대한 검색이 5.9초 걸렸고 그동안 `/api/sessions`가 최대 5.6초 기다렸다 (아래 "성능 요구사항"의 100ms 위반).

### 검색 기록

검색 품질(순위) 평가에 쓸 질의와 정답 후보를 모은다. `--cache-dir` 아래 `search-log.jsonl`에 한 요청당 한 줄을 덧붙인다. 실제 세션 내용이 담기므로 파일은 `0600`, 디렉터리는 `0700`이다.

- `search`: `/api/search`·`/api/session/:id/search`가 200으로 답할 때. `{at, kind, query, sessionId, results, matchCount, indexReady, durationMs}` — `sessionId`는 세션 하나 검색이면 그 id, 전 세션이면 `null`. `results`는 전 세션 응답의 세션 id를 순위 순으로, 세션 하나 검색이면 `[]`
- `open`: `/attribution`에 `q`와 1 이상의 정수 `rank`가 있을 때. `{at, kind, query, sessionId, rank, uuid}`. 화면이 전 세션 결과에서 매치를 누르면 그 세션의 순위와 검색어를 싣는다. 새로 고침·주소 직접 입력은 싣지 않아 남지 않는다
- 쓰기에 실패하면 표준 에러에 알리고 응답은 그대로 한다

`GET`이 기록을 남기는 것은 접근 로그와 같아 안전한 메서드의 의미를 바꾸지 않는다 ([RFC 9110 §9.2.1](https://www.rfc-editor.org/rfc/rfc9110#section-9.2.1)). 세션 파일은 쓰지 않는다 ([ADR-0003](../adr/ADR-0003-cli-writes-web-reads.md)).

`open`은 정답 표시가 아니라 후보다 — 누른 결과가 찾던 것이라는 보장이 없고, 끝내 찾지 못한 검색은 `open` 없이 남는다.

### 불변식

- `conversation_records > 0`인데 `conversation_rows = 0`인 파일은 `suspect`다 — 대화 레코드가 있는데 색인할 대화 텍스트가 하나도 없다면 세션 형식이 바뀌었을 가능성이 높다 ([ADR-0004](../adr/ADR-0004-schema-drift-defense.md))
- `rows.body`는 SQLite가 실제로 저장하는 글자다 — 첫 NUL 앞까지, 짝 없는 서로게이트는 U+FFFD. `bigrams`는 같은 글자로 만든다. 그래서 2글자 결과 건수는 `LIKE`로 센 건수와 같다
- 같은 `path`에 대해 `rows`의 행들은 `indexed_offset` 이전 바이트에서만 나왔다
- `bigrams`의 `rowid`는 모두 `rows`의 `rowid`다. 코드 포인트가 2개 이상인 `rows` 행은 `bigrams`에 있다
- `matches`는 정렬 키 순이다
- `truncated === true` ⟺ `matchCount > matches.length`

## 엣지 케이스 & 에러 처리

**기동과 첫 생성**

- 색인 파일이 없음 → 만들고 등록 세션을 `mtime` 내림차순으로 동기화한다
- `schema_version`이 2가 아님, 또는 SQLite가 파일을 열지 못함(손상) → 파일(`-wal`, `-shm` 포함)을 지우고 새로 만든다
- 첫 생성 도중 검색 → 그때까지 색인된 세션만으로 답하고 `index.ready: false`. 화면은 "색인 중 (N/M 세션) — 결과가 일부일 수 있습니다"를 결과 위에 표시한다
- 캐시 디렉터리를 만들 수 없음 → `serve`는 기동하되 검색 요청은 `503` "검색 색인을 만들 수 없습니다: {사유}". 다른 기능은 영향받지 않는다

**검색 요청 시 갱신**

- 요청마다 이미 한 번 동기화를 마친 등록 세션의 지문(`ino`, `size`)을 확인하고, 바뀐 파일만 동기화한 뒤 질의한다. 아직 첫 동기화 전인 세션은 백그라운드 생성에 맡긴다
- 동기화 실패한 세션 → 결과에서 빠지고 `index.failed`에 나온다. 화면은 실패 세션을 제목(없으면 라벨)과 사유로 표시한다

**질의**

- 매치 0건이고 `index.ready && failed.length === 0` → "찾지 못했습니다"
- 매치 0건이지만 색인 중이거나 실패 세션이 있음 → "찾지 못했습니다"에 그 사실을 덧붙인다. 확신에 찬 0건을 내지 않는다
- 따옴표·역슬래시·개행이 든 검색어 → 색인 텍스트는 JSON에서 풀린 문자열이므로 그대로 찾는다. 이전의 "저장 형태가 달라 찾지 못할 수 있습니다" 안내는 삭제한다
- `"`가 든 검색어 → FTS5 구문에서 `""`로 이스케이프한다. 검색어는 언제나 하나의 구(phrase)로 취급한다 (`AND`, `*` 등 FTS5 연산자로 해석하지 않는다)

**화면**

- 전 세션 결과의 세션 머리글은 `title`을 쓰고, 없으면 `label`을 쓴다
- 매치마다 등급 표시: "대화" / "도구" / "기타"
- 전 세션 결과에서 `uuid`가 있는 매치를 누르면 `#session/{id}/uuid/{uuid}`로 이동한다. 세션을 연 뒤 귀속 결과가 `segment`면 그 조각을 펼치고, `orphan`·`unindexed`면 "이 레코드는 조각에 속하지 않습니다"를 알린다. `uuid`가 null인 매치는 누를 수 없다
- 세션 하나 결과는 귀속이 `segment`인 매치만 누를 수 있고, 나머지는 "조각으로 이동할 수 없는 매치"로 따로 묶는다
- `matchCount > matches.length`면 "N건 중 M건"을 머리글에 표시한다. `truncatedSessions`면 "매치가 있는 세션이 많아 상위 50개만 표시합니다"
- 요청마다 순번을 붙이고, 마지막 요청이 아닌 응답은 버린다. 세션을 열거나 목록으로 돌아가면 진행 중인 응답도 버린다

**파일 변경**

- 세션 파일 교체(`ino` 변경)나 잘림 → 그 파일만 처음부터 다시 색인
- 등록 세션 파일이 사라짐 → 동기화 실패로 처리. 그 파일의 기존 행은 지우지 않지만 질의에서 제외된다
- 등록되지 않은 `path`의 행 → 지우지 않는다(다른 `serve` 호출이 등록할 수 있다). 질의 대상이 아닐 뿐이다

**여러 프로세스**

- 두 `serve`가 같은 색인 파일을 씀 → `busy_timeout` 5초. 넘으면 그 동기화는 실패로 기록하고 다음 요청에서 다시 시도한다

## 성능 요구사항

기준선은 [Design "기준선"](../design/20261015-1821-search-index.tdd.md#기준선)의 실측(실제 세션 1,693개, 6.74GB)이다.

- 전 세션 검색, 3글자 이상, 색인 완료 상태: **1초 이내** (실측 7~417ms, 최악은 매치 164,731건인 `the`)
- 전 세션 검색, 2글자, 색인 완료 상태: **1초 이내를 목표로 한다.** 실측 한국어 24~~372ms(`고아`·`비용`·`에러` 등). 매치가 수십만 건인 영어 쌍(`pr` 428,781건)은 1.5~~2.9초로 미충족 — 색인 조회가 아니라 매치 정렬·묶음 비용이다(3글자 `the`도 같은 경향)
- 전 세션 검색, 1글자: 기준 없음. `LIKE` 전체 스캔이라 색인 크기에 비례한다. 워커에서 돌아 다른 요청을 막지는 않는다
- 검색 중이나 색인 생성 중에 `/api/sessions` 응답: **100ms 이내** — DB 작업은 모두 워커에서 한다
- 첫 색인 생성: 기준 없음. 실측 417초(같은 데이터·기기에서 보조 색인 없는 코드는 215초). 진행 상태를 화면에 표시한다
- 색인 크기: 기준 없음. 실측 4,914MB(같은 데이터에서 보조 색인 없는 코드 4,657MB, 보조 색인이 +257MB)

## Out of Scope

- 관련도(`bm25`) 순위 — 측정 후 결정 (Design "향후 확장 고려사항")
- 색인 범위 밖 데이터(base64 첨부, `toolUseResult`, `file-history-snapshot`, `progress`, 파일 첨부 원문)의 검색
- uuid로 찾는 기능
- 뜻이 비슷한 말·오탈자 보정, 정규식
- 1글자 검색을 빠르게 하는 것, 1글자 비ASCII 대문자 검색의 대소문자 무시
- 색인 파일 크기 상한과 오래된 세션 정리
- 검색 기록의 회전·크기 상한과 화면에서 보는 기능
- 결과 스트리밍 — 색인 질의가 1초 안에 끝나므로 필요 없다
