# Technical Design: 본문 검색

## Context

> 📋 출처: [PRD: 기록 본문에서 특정 내용 찾기](../prd/20260906-0900-body-search.prd.md)
>
> 목표: 사용자가 낱말·문구를 입력하면 그 내용이 등장하는 위치를 찾고, 해당 조각을 열어 맥락을 확인할 수 있다.

이 기능은 지금까지의 기능들과 전제가 하나 다르다. `inspect`·`serve`가 다루는 대상은 **구조**(`uuid`/`parentUuid`/`type`/`timestamp`)이고, 이 값들은 전부 인덱스에 상주한다. 반면 본문은 상주하지 않는다 — `src/core/CLAUDE.md` "인덱스는 본문을 담지 않는다"가 그렇게 정한 이유는 노드 수와 본문 크기의 비대칭 때문이다(실측: 노드 9,083개 / 파일 823MB).

따라서 본문 검색은 기존 인덱스 조회로는 답이 나오지 않는다. **파일을 다시 읽어야 하는 최초의 조회 기능**이며, 이 설계의 대부분은 "다시 읽는 비용"과 "매치를 어느 노드에 귀속시킬 것인가" 두 문제에 관한 것이다.

## 적용하는 기존 ADR

- [ADR-0004: 스키마 드리프트와 암묵 정책은 골든 픽스처와 시끄러운 실패로 방어한다](../adr/ADR-0004-schema-drift-defense.md) — 이 설계의 핵심 결정(매치 귀속 방식)이 전적으로 이 원칙에서 나온다. 아래 "매치를 노드에 귀속시키기" 참고
- [ADR-0003: 웹은 읽기 전용이고 쓰기는 CLI가 단독으로 수행한다](../adr/ADR-0003-cli-writes-web-reads.md) — 검색은 읽기 전용 조회이므로 화면에서 제공해도 이 경계를 넘지 않는다
- [ADR-0001: TypeScript 단일 스택](../adr/ADR-0001-typescript-single-language.md) — 스캔 로직은 `src/core/`에 두고 화면과 명령줄이 같은 함수를 쓴다. 화면에서 별도 구현하지 않는다
- [ADR-0007: 직접 구현과 기존 도구 도입을 "다져진 엣지 케이스"로 판별한다](../adr/ADR-0007-hand-roll-vs-existing-solution.md) — 이 ADR의 기준은 오히려 "직접 만들지 말라" 쪽을 가리킨다. 그럼에도 직접 소유하기로 한 근거를 아래 대안2에 실측과 함께 남긴다

## 아키텍처 (How)

```
검색 요청 (문구)
  │
  ├─ 1단계  원시 바이트 스캔        파일 전체를 1MB씩 읽으며 Buffer.indexOf
  │          → 매치된 바이트 위치 목록   (문자열 변환 없음, 구문 해석 없음)
  │
  ├─ 2단계  매치된 줄만 귀속        각 위치에서 앞뒤 개행까지 넓혀 그 줄만 해석
  │          → 위치별 uuid            (매치 수만큼만 발생 — 파일 크기와 무관)
  │
  └─ 3단계  기존 인덱스와 결합      uuid → 세그먼트/타입/시각
             → 검색 결과
```

핵심은 **1단계와 2단계의 비용이 분리**된다는 점이다. 파일 크기에 비례하는 것은 1단계뿐이고, 1단계는 바이트를 문자열로 만들지 않는다. 2단계는 매치 건수에만 비례한다.

실측 (823MB, 노드 9,083개):

| 단계              | 비용                |
| ----------------- | ------------------- |
| 1단계 원시 스캔   | 174–305ms, heap 5MB |
| 2단계 귀속 (82건) | 24ms                |
| 3단계 인덱스 조회 | 1ms 미만            |

heap 5MB는 우연이 아니라 설계 결과다 — 1MB 버퍼 하나를 재사용하고 문자열을 만들지 않으므로, 파일이 몇 GB가 되어도 상주 메모리는 늘지 않는다. 이는 `src/core/CLAUDE.md`의 "본문을 메모리에 올리지 않는다"를 검색 경로에서도 유지한다는 뜻이다.

### 매치를 노드에 귀속시키기

이 설계에서 가장 값진 결정이다. 겉보기에 더 단순하고 훨씬 빠른 방법이 있는데, 그 방법이 **조용히 틀린 답을 낸다.**

인덱스는 이미 노드마다 `byteOffset`/`byteLength`를 갖고 있다. 그러니 매치 위치를 `byteOffset` 정렬 배열에 이진 탐색하면 2단계 없이 노드를 찾을 수 있다 — 실측 0.14ms로, 파일을 다시 건드리지도 않는다.

그런데 이 방법은 **인덱스가 의도적으로 제외한 레코드 안의 매치를 통째로 놓친다.** 실측:

| 찾는 문구                         | 위치 기반 | 줄 해석 기반 |
| --------------------------------- | --------- | ------------ |
| `compact_boundary`                | 41개      | 41개         |
| `This session is being continued` | **40개**  | 41개         |

누락된 1건(`e13a7e37…`)을 추적한 결과, 이것은 같은 `uuid`가 **서로 다른 부모**(`a01f5570…` / `85dbad30…`)를 가리키며 두 번 나타나는 레코드였다. `prefer-parent` 정책이 어느 쪽도 고를 수 없어 `unresolvedDuplicates`로 보고하고 인덱스에서 제외한 경우다 — 즉 ADR-0004가 "추측하지 말고 보고하라"고 정한 바로 그 레코드다.

여기서 방향이 뒤집힌다. 그 레코드들은 **가장 덜 중요해서 제외된 것이 아니라, 가장 판단이 필요해서 제외된 것**이다. 사용자가 기록을 이을 지점을 고르려고 검색하는 상황에서 정확히 그 레코드가 결과에서 빠지면, 도구는 "찾는 내용이 거기 없다"는 틀린 답을 확신에 차서 내놓는다. ADR-0004가 `orphans: 0` 오보를 두고 경계한 것과 같은 형태의 실패다.

정리하면 위치 기반 매핑은 **인덱스에 있는 것만 찾을 수 있는데, 검색의 목적은 인덱스가 놓친 것을 찾는 것도 포함한다.** 그래서 약 170배 느린(0.14ms → 24ms) 줄 해석 방식을 택한다. 절대값이 24ms이고 1단계 스캔(283ms)에 묻히는 크기라, 이 트레이드오프는 실질적으로 무료다.

파일 전체 기준으로 노드가 덮는 바이트는 44.5%(366MB/823MB)에 불과하다. 나머지 55%는 중복 탈락 레코드 10,085건과 uuid 없는 줄 5,542건이다 — 위치 기반 매핑이 구조적으로 볼 수 없는 영역이 그만큼이라는 뜻이다.

### 찾지 못하는 경우도 결과에 남긴다

매치가 든 줄이 구문 해석에 실패하거나 `uuid`가 없을 수 있다. 이때 그 매치를 결과에서 빼지 않는다 — 위와 같은 이유로, "몇 건은 어느 조각인지 알 수 없다"는 사실 자체가 사용자에게 필요한 정보다. 조각을 특정할 수 없는 매치는 그렇게 표시해서 남긴다.

## 데이터 흐름

1. 사용자가 화면에서 문구를 입력한다
2. 서버가 해당 세션 파일을 1MB씩 읽으며 `Buffer.indexOf`로 매치 위치를 모은다. 청크 경계에 걸친 매치를 놓치지 않도록 `문구 길이 - 1` 바이트를 겹쳐 읽는다
3. 각 매치 위치에서 앞뒤 개행을 찾아 그 줄만 잘라 해석하고 `uuid`를 얻는다
4. 얻은 `uuid`를 기존 인덱스에서 조회해 소속 세그먼트·타입·시각을 붙인다. 인덱스에 없으면(중복 미해소·orphan 등) 그 사실을 결과에 담는다
5. 화면은 결과를 조각별로 묶어 보여주고, 선택하면 기존 조각 열기 경로로 이동한다

에러 경로:

- 파일이 읽기 중 사라지거나 갱신되면, 기존 staleness 감지(`{ino,size,mtimeMs}`)와 같은 판정을 적용한다 — 검색 도중 파일이 바뀌면 그 결과는 신뢰할 수 없으므로 오류로 보고한다. 부분 결과를 정상인 것처럼 돌려주지 않는다
- 여러 세션이 열려 있을 때 한 세션의 검색이 실패해도 나머지 세션 결과는 반환한다. 실패한 세션은 목록에서 빼지 않고 실패로 표시한다 ([다중 세션 설계](20260905-0641-multi-session-serve.tdd.md)와 같은 규칙)

## 고려한 대안 & 기각 이유

**대안1: 인덱스에 본문을 함께 올린다**

검색이 조회 한 번으로 끝나 가장 빠르다. 기각 이유는 이 저장소의 전제 자체를 뒤집기 때문이다 — `src/core/CLAUDE.md`가 본문 제외를 택한 근거가 "본문이 수백 MB"라는 실측이었고, 실제로 이 파일의 본문은 823MB다. 검색 하나를 위해 상주 메모리를 5MB에서 수백 MB로 올리는 것은 `inspect`·`serve`의 성능 요구사항(Spec: 200MB 이내)을 직접 위반한다.

**대안2: `rg`(ripgrep) 같은 외부 도구를 호출한다**

ADR-0007이 가리키는 방향이고, 실제로 더 빠르다 — 같은 파일·같은 문구에서 `rg` 89ms 대 자체 스캔 283ms로 **3배 빠르다**(메모리 맵과 SIMD 덕분). 자체 구현이 성능에서 이겼다고 주장하지 않는다.

그럼에도 기각한 이유는 성능이 아니라 **결과의 형태**다. `rg`가 돌려주는 것은 줄과 바이트 위치이고, 이 도구에 필요한 것은 "어느 조각의 어느 노드인가"다. 그 변환(2단계 귀속 + 인덱스 결합)은 어차피 직접 해야 하며, 그것이 이 기능의 실질적 내용 전부다. `rg`를 쓰면 얻는 것은 283ms→89ms(194ms 절감)뿐이고, 대신 외부 실행 파일 의존과 그 부재·버전 차이를 다루는 경로가 새로 생긴다.

ADR-0007의 기준은 "다져진 엣지 케이스를 재발명하지 말라"인데, 여기서 엣지 케이스가 몰려 있는 곳은 문자열 탐색이 아니라 **귀속 판정**(중복 미해소, orphan, uuid 없는 줄)이고 그건 `rg`가 대신해 주지 않는다. 이 기각은 되돌릴 수 있다 — 스캔 시간이 실제로 문제가 되면 1단계만 `rg`로 교체해도 2·3단계는 그대로 쓸 수 있는 구조로 둔다.

**대안3: 파일 전체를 문자열로 만들어 훑는다**

가장 쓰기 쉬운 구현이다. 실측 2,306ms로 원시 스캔(283ms)보다 **8배 느리다**. 느린 원인이 매치 탐색이 아니라 바이트→문자열 변환이라는 점이 측정으로 드러났고(매치가 든 82줄만 해석했는데도 2,306ms), 이는 대안1과 같은 이유로 대형 파일에서 메모리도 함께 밀어올린다. 기각.

**대안4: 검색 전용 색인을 미리 만들어 둔다**

역색인을 두면 반복 검색이 빨라진다. 기각 이유는 지금 근거가 없어서다 — 관측된 사용 형태는 "확인하려고 한두 번 찾아본다"이고, 같은 문구를 반복 검색하는 상황은 아직 없었다. 색인은 만드는 비용(전체 파싱)과 파일이 바뀔 때 무효화하는 문제를 새로 들여오는데, 지금 스캔이 283ms라 그 복잡도를 정당화하지 못한다. 반복 검색이 실제로 관측되면 다시 검토한다.

**대안5: 위치 기반 이진 탐색으로 귀속시킨다**

위 "매치를 노드에 귀속시키기"에서 실측과 함께 기각했다. 0.14ms로 압도적으로 빠르지만 `unresolvedDuplicates` 안의 매치를 놓친다. 요약하면 **가장 판단이 필요한 레코드를 결과에서 지운다.**

이 대안을 문서에 남기는 이유는, 구현 중에 "인덱스에 `byteOffset`이 이미 있는데 왜 파일을 또 읽나"라는 판단이 자연스럽게 떠오르기 때문이다. 그 판단은 합리적으로 보이고 측정상으로도 빠르며, 대부분의 문구에서는 같은 답을 낸다(위 표의 `compact_boundary` 41 대 41). 그래서 더 위험하다 — 틀린 경우가 드물어 테스트로 잡히지 않을 수 있다.

## 향후 확장 고려사항

- 여러 세션을 한 번에 검색하는 것은 세션마다 위 흐름을 독립적으로 돌리면 된다. 다만 세션 수가 많아지면 총 시간이 세션 수에 비례하므로, [다중 세션 설계](20260905-0641-multi-session-serve.tdd.md)의 지연 인덱싱과 같은 판단(먼저 열린 것부터 처리)이 필요해질 수 있다. 지금은 명시적으로 지정한 소수를 전제하므로 범위 밖이다
- 대소문자 구분 없이 찾는 기능은 1단계(바이트 단위 원시 스캔)와는 맞지 않는다(비ASCII에서 성립하지 않음). 다만 2단계는 이미 매치된 줄을 문자열로 해석하고 있으므로, 그 지점에서 `String.prototype.toLowerCase()`로 비교하면 된다 — 이는 [ADR-0007](../adr/ADR-0007-hand-roll-vs-existing-solution.md)이 가리키는 네이티브 API이지 직접 구현이 아니다(엔진의 ICU 유니코드 케이스 매핑이 `ß`→`ss`, 그리스어 종성 시그마 같은 다져진 엣지 케이스를 이미 처리한다). 별도 정규화 라이브러리를 들이는 것이 오히려 대안3(대안 목록의 CSS 프레임워크 사례와 같은 논리)과 같은 이유로 기각 대상이다. 로케일 종속 케이스 폴딩(터키어 dotless I 등)은 이 검색이 로케일을 지정하지 않으므로 범위 밖이다
- 스캔 시간이 문제가 되면 1단계만 외부 도구로 교체할 수 있도록 단계 경계를 유지한다 (대안2)
- 이 설계는 "인덱스에 없는 레코드도 검색 결과에 나온다"를 처음으로 성립시킨다. 그 레코드를 화면에서 선택했을 때 어디로 보낼지는 이 문서 범위 밖이며, 조각 열기 경로가 인덱스를 전제하므로 별도 판단이 필요하다
