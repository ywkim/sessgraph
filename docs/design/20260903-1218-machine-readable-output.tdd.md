# Technical Design: 기계 판독 출력과 자기 기술(self-describing) CLI

## Context

> 📋 출처: [PRD: 사람이 아닌 호출자도 결과를 읽을 수 있게 한다](../prd/20260903-1218-machine-readable-output.prd.md)
>
> 목표: 호출자가 도구 사용법을 미리 알지 못해도, 도구에게 물어본 것만으로 명령을 정확히 구성하고 결과·실패를 해석할 수 있게 한다.

이 문서는 개별 명령의 동작을 정의하지 않는다. `inspect`/`verify`/`reattach`/`revert`가 **공통으로 따르는 출력 규약**과, 그 규약을 호출자가 발견하는 경로를 정의한다.

## 적용하는 기존 ADR

- [ADR-0001: 단일 언어(TypeScript) 스택](../adr/ADR-0001-typescript-single-language.md) — 출력 형태를 정의하는 타입은 `src/core/types.ts` 한 곳에 두고 CLI·웹이 공유한다. 명령마다 자기 응답 타입을 따로 만들면 같은 사실이 두 형태로 갈린다
- [ADR-0003: CLI는 쓰고 웹은 읽는다](../adr/ADR-0003-cli-writes-web-reads.md) — 기계 판독 출력은 읽기 통로를 하나 더 여는 것이지 쓰기 권한을 옮기는 것이 아니다. `--json`은 어떤 명령의 쓰기 여부도 바꾸지 않는다 (`--commit` 규약 그대로)
- [ADR-0004: 시끄러운 실패, 같은 계산은 한 곳에서만](../adr/ADR-0004-schema-drift-defense.md) — 이 설계의 중심 근거다. ADR-0004는 사람이 읽는 리포트가 조용히 오답을 내는 상황을 다뤘는데, 기계 판독 출력에서는 같은 위험이 **두 가지 새로운 형태**로 재등장한다: (1) 실패 사유를 자연어 문구로만 구분하면 문구가 바뀌는 순간 호출자가 조용히 오분류한다 (2) 도구가 안내하는 "다음 조치"가 실재하지 않으면 호출자는 반드시 실패하는 경로로 유도된다. 아래 "아키텍처"의 명령 레지스트리와 오류 코드가 이 둘에 대한 기계적 방어다
- [ADR-0006: CLI 출력에 응답 봉투와 안정 오류 코드를 도입한다](../adr/ADR-0006-machine-readable-cli-envelope.md) — 이 설계가 채택하는 새 기술 선택(응답 봉투, 오류 코드 열거, 명령 레지스트리 단일화)의 결정 기록. 아래 "아키텍처"는 이 ADR의 Decision을 구체화한다

## 아키텍처 (How)

### 1. 명령 레지스트리 — 단일 진실

지금은 명령 목록이 세 곳에 흩어져 있다: `src/cli/index.ts`의 `switch`문, 각 명령의 `parseArgs` 설정, 그리고 `README.md`. 여기에 "발견용 설명"을 네 번째 사본으로 추가하면 반드시 어긋난다.

대신 `src/cli/registry.ts`에 명령 정의를 **한 벌만** 둔다:

```
CommandDescriptor  →  ① parseArgs 설정 생성
                   →  ② schema 출력 생성
                   →  ③ 디스패치 테이블
```

세 소비처가 같은 객체를 읽으므로, 새 플래그를 추가하면 발견용 출력도 자동으로 따라온다. 설명이 구현과 갈릴 여지 자체를 없앤다.

### 2. 응답 봉투 (envelope)

모든 명령이 `--json`에서 **같은 최상위 형태**를 낸다. 성공/실패 여부를 종료 코드로만 알 수 있게 두지 않고 본문에도 담는다 — 종료 코드를 잃어버리는 호출 경로(로그 수집, 파이프)에서도 판정이 가능해야 한다.

명령 고유 결과는 `result` 아래에 그대로 넣는다. `inspect`의 `IndexResult`, `verify`의 `VerifyResult`처럼 이미 정의된 타입을 봉투가 감쌀 뿐, 변형하지 않는다 — [`serve` Spec](../spec/20260902-0420-serve-command.spec.md)이 `/api/index`에 `IndexResult`를 그대로 응답하기로 한 것과 같은 이유다.

### 3. 안정 오류 코드

실패 사유는 `ErrorCode` 문자열 열거로 구분한다. 한국어 메시지는 사람용으로 함께 실리되, **분기 근거는 코드**다. 메시지 문구 개선이 호출자를 깨뜨리지 않아야 한다.

코드 열거는 `src/core/types.ts`에 둔다. `src/cli/`와 `src/web/`이 함께 소비할 수 있어야 하고, 타입의 단일 진실은 `src/core/`이기 때문이다 (루트 CLAUDE.md "인터페이스 변경 게이트").

### 4. 다음 조치 (nextActions)

실패 응답은 "무엇을 하면 되는가"를 **실행 가능한 명령 문자열**로 담는다. 지금 `reattach`가 자연어로 안내하는 `inspect --json`이 이 자리로 옮겨온다.

여기가 이 설계에서 가장 조용히 썩기 쉬운 지점이다. 안내 문자열은 자유 텍스트라 존재하지 않는 명령을 가리켜도 아무도 실패하지 않는다 — 실제로 이미 그렇게 됐다. 따라서 **`nextActions`가 가리키는 명령 이름이 레지스트리에 실재하는지 테스트가 검사한다.** 이것은 문서로 지킬 규칙이 아니라 기계 검사로 옮긴 규칙이다 (루트 CLAUDE.md "규칙 추가 게이트" 3항).

### 5. 스트림 분리

`--json`일 때 성공·실패 응답 모두 **stdout에 한 줄**로 쓴다. stderr는 비운다. 호출자가 두 스트림을 합쳐 읽다가 사람용 경고와 JSON이 섞여 파싱이 깨지는 것을 막는다.

지금 `applyReattach`가 `console.warn`으로 내보내는 키 집합 경고는 `--json`에서 `warnings` 배열로 들어간다. 경고를 삼키지 않으면서 스트림도 오염시키지 않는다.

## 데이터 흐름

```
argv
 │
 ├─ "schema" ──────► 레지스트리 직렬화 ──► stdout (JSON)
 │
 └─ 그 외 ──► 레지스트리 조회
              │
              ├─ 없는 명령 ──► 봉투(ok:false, UNKNOWN_COMMAND,
              │                nextActions: ["sessgraph schema"]) ──► 종료 2
              │
              └─ 있음 ──► parseArgs(레지스트리 설정)
                          │
                          ├─ 인자 오류 ──┐
                          │              │
                          └─ core 호출 ──┤
                                         │
                          성공/실패 ─────┴──► 봉투 조립
                                              │
                                    --json ? JSON 한 줄 : 사람용 문장
                                              │
                                              ▼
                                        stdout + 종료 코드
```

에러 경로의 핵심: `ReattachValidationError` 같은 core 예외는 CLI에서 잡아 **코드가 붙은 봉투**로 변환된다. core는 종료 코드도 출력 형태도 알지 못한다 (`src/core/CLAUDE.md` 스코프 경계 유지).

## 고려한 대안 & 기각 이유

**대안1: 자연어 출력을 유지하고 호출자가 해석하게 둔다 (현재 상태)**

- 기각 이유: 실패 분기가 메시지 문구에 묶인다. 문구를 다듬는 것과 호출자를 깨뜨리는 것이 같은 행위가 되어, 메시지를 개선할 수 없는 상태로 굳는다. 이 도구는 되돌리기 어려운 쓰기 작업을 수행하므로(ADR-0002), 실패 사유 오분류의 비용이 특히 크다

**대안2: 사람용 출력을 없애고 JSON만 낸다**

- 기각 이유: 이 도구가 잘못 고쳤을 때 원인을 파악하는 것은 결국 사람이다. 그때 터미널에서 직접 실행해 읽을 형태가 없으면 소스를 읽어야 한다. PRD Non-Goals에 명시

**대안3: `--help` 텍스트만 제공한다**

- 기각 이유: `--help`는 정렬된 사람용 텍스트라 해석 대상이지 파싱 대상이 아니다. 플래그 필수 여부·값 형식·종료 코드 같은 구조 정보가 서식에 녹아 소실된다. 다만 이는 `schema`와 배타적이지 않다 — 같은 레지스트리에서 사람용 텍스트도 생성할 수 있으므로 `--help`는 이번 범위 밖으로 두되 경로는 막지 않는다

**대안4: 명령마다 자유 형식 JSON을 낸다**

- 기각 이유: 호출자가 명령마다 다른 파싱 규칙을 익혀야 하고, 실패 응답 형태가 갈리면 "성공했는가"라는 가장 기본적인 판정조차 명령별 분기가 된다. 같은 사실이 여러 형태로 갈리는 것은 ADR-0004가 다룬 실패 유형 그 자체다

**대안5: 발견을 전담하는 연결 계층(도구 서버)을 별도로 만든다**

- 기각 이유: 명령 실행이라는 기존 통로를 그대로 두고도 발견 문제를 풀 수 있는데, 통로를 하나 더 만들면 그 계층과 CLI가 갈릴 여지가 새로 생긴다. PRD Non-Goals에 명시. 다만 레지스트리를 단일 진실로 두는 이 설계는 나중에 그런 계층을 붙일 때 그대로 재사용된다

## 향후 확장 고려사항

- **아직 구현되지 않은 명령의 취급** — `inspect`/`verify`/`revert`/`serve`는 Spec만 있고 구현이 없다. 레지스트리에 미리 등록해 두면 `schema`가 실행 불가능한 명령을 광고하게 되고, 이는 이 설계가 막으려는 실패(존재하지 않는 조치 안내)와 같은 형태다. 레지스트리에는 **구현된 명령만** 등록한다
- 그 결과 `reattach`의 중복 오류가 안내할 `inspect --json`은 `inspect`가 구현되기 전까지 `nextActions`에 넣을 수 없다. 이 제약은 회피 대상이 아니라 위 4번 기계 검사가 의도대로 작동하는 증거다 — 현재의 잘못된 자연어 안내가 어디서 깨지는지를 드러낸다
- `--help` 사람용 텍스트 생성은 같은 레지스트리에서 파생 가능하다 (대안3)
- `serve`가 노출할 응답도 같은 봉투를 쓸 수 있다. 다만 웹은 읽기 전용이므로 `warnings`/`nextActions`의 의미가 CLI와 같은지는 `serve` 구현 시점에 판단한다
