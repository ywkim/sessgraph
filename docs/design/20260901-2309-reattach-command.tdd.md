# Technical Design: `reattach` 명령

## Context

> 📋 출처: [docs/prd/20260901-2309-reattach-command.prd.md](../prd/20260901-2309-reattach-command.prd.md)
>
> 목표: 사용자가 끊긴 지점 하나를 골라 안전하게 이을 수 있게 한다. 미리보기 가능, 원본 보존, 사유 기록, 그리고 "이어붙인 것처럼 보이는 것"이 아니라 실제로 이전 내용을 기억하는 상태를 성공 기준으로 삼는다.

## 적용하는 기존 ADR

- [ADR-0002: 레코드 보존형 재연결](../adr/ADR-0002-record-preserving-reattach.md) — 이 명령의 핵심 결정을 그대로 구현한다. `compact_boundary` 레코드를 삭제하지 않고 `parentUuid` 값만 바꾼다. 레코드 삭제형이 재개 후 회상에 실패한 실측 사례가 이 명령의 존재 이유다
- [ADR-0003: CLI 단독 쓰기](../adr/ADR-0003-cli-writes-web-reads.md) — `reattach`는 파일을 실제로 수정하는 유일한 경로다. 웹(`serve`)에는 이 기능이 없다. 대상 uuid는 `inspect` 출력에서 클립보드로 옮겨온다
- [ADR-0004: 시끄러운 실패](../adr/ADR-0004-schema-drift-defense.md) — 쓰기 작업은 읽기보다 되돌리기 비용이 크므로, 애매한 상태(정책으로 해소 안 된 중복 등)를 만나면 추측해서 진행하지 않고 중단한다

## 아키텍처 (How)

```
sessgraph reattach <file> --uuid X --parent Y --reason "..."
  → src/core: buildIndex()로 현재 상태 파악 (inspect와 동일 함수)
    → X, Y가 실제로 존재하는 노드인지 확인
    → X → Y로 재연결했을 때 순환이 생기지 않는지 확인
  → 계획 출력 (dry-run 기본): "X(현재 부모: 없음/끊김) → Y로 연결. 이후 체인 길이: N → M"
  → --commit 있으면:
    → src/cli: 원본을 {file}.bak.{timestamp}로 복사 (기존 백업 덮어쓰지 않음)
    → 임시 파일에 전체 내용을 다시 씀 (대상 레코드만 parentUuid 값 교체, 나머지는 원본 그대로)
    → rename으로 원자적 교체
    → {file}.surgery.log에 한 줄 추가 (시각, uuid, 이전/이후 부모, 사유, 백업 경로)
```

`reattach`도 `inspect`와 마찬가지로 `src/core`의 `buildIndex()`를 재사용해 대상 검증을 한다. 그래프 판정을 다시 구현하지 않는다 (루트 CLAUDE.md "인터페이스 변경 게이트").

파일 수정 자체는 `src/core`가 하지 않는다. `src/core`는 순수 함수로 "무엇을 바꿔야 하는가"만 계산하고, 실제 파일 쓰기(백업·임시파일·rename·로그)는 `src/cli`가 수행한다 (`src/core/CLAUDE.md` "이 스코프가 하지 않는 것: 파일 쓰기").

## 데이터 흐름

1. 사용자가 `--uuid`, `--parent`, `--reason`과 함께 실행. `--reason` 없으면 즉시 오류 (사유 없는 수술 금지 — `src/cli/CLAUDE.md`)
2. `buildIndex()`로 현재 상태 계산
3. **사전 검증**:
   - `--uuid`가 가리키는 노드가 실제로 존재하는가 → 없으면 오류
   - `--parent`가 가리키는 노드가 실제로 존재하는가 → 없으면 오류
   - `--parent`를 `--uuid`의 조상으로 거슬러 올라가면 순환이 생기는가 → 순환이면 오류 (자기 자신이나 자손을 부모로 지정하는 경우)
   - `--uuid`가 가리키는 레코드가 애초에 `parentUuid`를 가질 수 있는 대상인가 (예: uuid 없는 메타데이터 레코드는 대상이 될 수 없음) → 아니면 오류
4. 위 검증을 모두 통과하면 계획을 계산: 재연결 전/후 체인 길이, 영향받는 세그먼트
5. **dry-run(기본)**: 계획을 사람이 읽는 형식으로 출력하고 종료. 파일은 건드리지 않는다
6. **`--commit`**: 계획을 실제로 적용
   - 원본을 백업 (덮어쓰지 않는 타임스탬프 파일명)
   - 대상 줄만 `parentUuid` 값을 교체한 새 파일을 임시 경로에 씀 (다른 모든 줄은 바이트 단위로 그대로 복사 — 레코드를 다시 직렬화하지 않는다. 재직렬화는 원본에 없던 필드 순서·공백 변경을 일으킬 수 있다)
   - 임시 파일을 원본 경로로 원자적 교체
   - 수술 로그에 기록
   - 결과 보고: "체인 길이가 N에서 M으로 늘었습니다. 실제로 이전 내용을 기억하는지는 세션을 재개해 직접 확인하세요" (구조적 성공과 실질 성공을 구분 — `src/cli/CLAUDE.md` "보고 규칙")

에러 처리 경로: 대상/부모 노드 없음 → 종료 코드 2. 순환 발생 → 종료 코드 2, "순환이 생겨 적용할 수 없습니다". `--reason` 누락 → 종료 코드 2. 쓰기 중 실패(디스크 공간 등) → 임시 파일만 남고 원본은 훼손되지 않음 (원자적 교체이므로 rename 전 실패는 원본에 영향 없음).

## 고려한 대안 & 기각 이유

**대안1: 레코드를 다시 파싱해서 JSON으로 재직렬화 후 저장**

- 기각 이유: 원본 레코드의 필드 순서, 공백, 이스케이프 방식이 Claude Code 자체 구현에 의존하는데, 이를 재직렬화하면 원본과 바이트 단위로 달라진다. 이 도구가 다루는 필드는 비공개 스키마이므로(ADR-0001) 재직렬화가 예상치 못한 부작용을 낼 위험이 있다. 대신 대상 줄만 문자열 치환하고 나머지는 바이트 그대로 복사한다

**대안2: 여러 지점을 한 번에 잇는 배치 모드를 기본으로 제공**

- 기각 이유: PRD가 명시적으로 범위 밖으로 뒀다. 한 지점씩 검증하고 사유를 남기는 것이 실수를 줄이는 방향이고, 여러 지점을 자동으로 고르는 로직은 "어떤 지점을 이어야 하는가"라는 판단을 도구가 대신하게 되어 위험하다

**대안3: `--commit` 없이 항상 즉시 적용 (dry-run을 옵션으로)**

- 기각 이유: 세션 파일 수정은 되돌리기 어려운 작업이다(README "주의"). 기본값이 안전한 쪽(미리보기)이어야 하고, 실제 적용은 명시적 의도 표현(`--commit`)을 요구해야 한다

**대안4: 순환 검사를 생략 (사용자가 알아서 올바른 대상을 고를 것으로 가정)**

- 기각 이유: 순환이 생기면 이후 `verify`(leaf→root 역추적)가 무한 루프에 빠지거나 잘못된 체인 길이를 보고할 수 있다. 검증 비용이 낮고(조상 경로를 한 번 순회) 실패 시 피해가 크므로 항상 검사한다

## 향후 확장 고려사항

- `verify` 명령은 이 명령이 만든 결과(체인 길이)를 확인하는 역할을 한다. `reattach`가 출력하는 "적용 후 체인 길이" 계산 로직과 `verify`의 계산 로직은 같은 `src/core` 함수를 공유해야 한다 (두 곳에서 따로 구현하면 ADR-0004가 경고한 정책 불일치가 재현된다)
- `revert` 명령은 `reattach`가 남긴 백업과 수술 로그를 소비한다. 수술 로그의 필드(시각, uuid, 이전/이후 부모, 백업 경로)는 `revert`가 무엇을 복원할지 특정할 수 있는 형식으로 지금 정한다
- 여러 지점을 한 번에 처리하는 배치 모드가 실제로 필요해지면(Non-Goals 재검토), 이 명령을 감싸는 상위 명령으로 추가하고 이 명령 자체의 단일 지점 처리 로직은 그대로 재사용한다
