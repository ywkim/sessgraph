# Technical Design: 영속 검색 색인

## Context

> 📋 출처: [PRD](../prd/20261015-1821-search-index.prd.md)
>
> 목표: 등록한 세션 전체를 대상으로, 대소문자를 가리지 않고, 순위가 매겨진 결과를 1초 안에, 서버를 막지 않고 돌려준다.

이 설계는 [본문 검색 Design](20260906-0900-body-search.tdd.md)을 대체한다. 그 Design이 기각한 대안4(검색 전용 색인)를 채택하는 근거는 [ADR-0008](../adr/ADR-0008-persistent-search-index-sqlite-fts5.md)에 있다.

## 적용하는 기존 ADR

- [ADR-0008: 내장 SQLite(FTS5 trigram) 영속 색인](../adr/ADR-0008-persistent-search-index-sqlite-fts5.md) — 저장 기술과 원문 저장 방식
- [ADR-0003: 웹은 읽기 전용](../adr/ADR-0003-cli-writes-web-reads.md) — 색인 쓰기는 세션 파일을 건드리지 않고, 웹에 쓰기 API를 추가하지 않는다
- [ADR-0004: 스키마 드리프트 방어](../adr/ADR-0004-schema-drift-defense.md) — 추출 범위를 제외 목록으로 정하고, 색인이 조용히 비는 경우를 불변식으로 잡는다
- [ADR-0007: 직접 구현 판별](../adr/ADR-0007-hand-roll-vs-existing-solution.md) — 부분 문자열 색인과 대소문자 접기를 직접 구현하지 않는다

## 아키텍처 (How)

```
src/core/search-text.ts   레코드 한 줄 → 색인할 행들 (순수 함수, 파일 I/O 없음)
        │
src/cli/search-index/     worker_threads 워커 하나가 DB 연결을 단독 소유
  ├─ worker.ts            동기화(증분 색인) + 질의 실행
  └─ client.ts            메인 스레드 쪽 Promise 래퍼
        │
src/cli/serve.ts          /api/search, /api/session/:id/search → client 호출
        │
src/web/app.ts            결과 렌더 (등급별 묶음, 진행 상태 표시)
```

**책임 분리.** `src/core/`는 파일을 쓰지 않는다([src/core/CLAUDE.md](../../src/core/CLAUDE.md)). 레코드에서 "무엇을 어느 등급으로 색인하는가"는 세션 스키마 지식이므로 `src/core/`의 순수 함수로 두고, DB 파일 쓰기와 워커는 `src/cli/`에 둔다. `src/cli/`는 JSONL을 직접 해석하지 않는다는 규칙도 지켜진다 — 워커는 줄을 잘라 core 함수에 넘길 뿐이다.

**워커 하나가 DB를 소유한다.** `node:sqlite`는 동기 API다. 첫 색인 생성은 수 분, 1글자 검색의 `LIKE` 전체 스캔은 수 초가 걸리므로 메인 스레드에서 돌리면 PRD의 "다른 동작이 멈추지 않는다"를 어긴다. 워커가 쓰기와 질의를 모두 직렬로 처리하므로 같은 프로세스 안에서 쓰기 경합이 없다. 다른 `serve` 프로세스(예: 상시 인스턴스와 테스트 인스턴스)가 같은 DB를 열면 SQLite 파일 잠금과 WAL이 조정한다.

**색인 범위 — 제외 목록 방식.** [ADR-0008](../adr/ADR-0008-persistent-search-index-sqlite-fts5.md)의 원칙대로, 알려진 소음만 빼고 모르는 것은 가장 낮은 등급으로 넣는다.

| 등급           | 출처                                                                                     |
| -------------- | ---------------------------------------------------------------------------------------- |
| `conversation` | `user`/`assistant` 레코드의 문자열 content, `text` 블록, `thinking` 블록                 |
| `tool`         | `tool_use`, `tool_result` 블록 안의 문자열 값                                            |
| `meta`         | 세션별 `cwd`·`gitBranch`(값마다 한 번), 그 밖의 레코드와 모르는 블록 타입 안의 문자열 값 |

빼는 것: `file-history-snapshot`·`progress` 레코드, `attachment.type === "file"` 레코드, `{type:"base64", data}` 객체, `toolUseResult` 필드, 식별자·시각 필드(`uuid`, `parentUuid`, `sessionId`, `timestamp`, `signature` 등). 근거는 실측이다 — 아래 "기준선".

**증분 갱신.** 세션 파일은 뒤에 덧붙기만 한다. 파일마다 `{ino, 색인한 마지막 완결 줄의 끝 오프셋}`을 저장하고, 행 삽입과 같은 트랜잭션에서 갱신한다. 중간에 죽어도 색인과 오프셋이 어긋나지 않는다. 쓰는 중이라 개행이 아직 없는 마지막 줄은 다음 동기화로 미룬다.

**2글자 검색은 bigram 보조 색인으로 한다.** trigram은 3글자 미만 검색어를 처리하지 못해 `LIKE`가 4.7GB를 통째로 훑었고(실측 2~23초), 색인이 커질수록 느려졌다. 본문의 인접한 코드 포인트 쌍마다 토큰 하나(`x` + 코드 포인트 16진수 두 개)를 만들어 `fts5(detail=none, contentless_delete=1, tokenize=unicode61)` 테이블에 `rows`와 같은 `rowid`로 넣는다. 2글자 검색은 토큰 하나의 조회가 되고, 비ASCII 대소문자도 구분하지 않는다(trigram과 같다). 토큰이 16진수 영문·숫자라 `unicode61`이 자르거나 접지 않는다. `detail=none`은 토큰이 하나뿐인 질의만 하므로 쓸 수 있다 — trigram에서 막힌 이유(구 질의)가 여기엔 없다. 1글자 검색은 보조 색인을 만들 수 없어(모든 글자가 후보) `LIKE`로 남긴다.

**보조 색인은 저장본과 같은 글자로 만든다.** SQLite는 첫 NUL 뒤를 저장하지 않는다. 실제 세션에 바이너리 덤프를 찍은 도구 결과 24행이 있었고, 전체 본문으로 토큰을 만들자 `rows`에 없는 글자까지 찾아 `LIKE` 건수와 2~4건씩 어긋났다. 저장 전에 같은 글자로 맞추자 19개 질의가 모두 일치했다.

**순위.** 색인 행에 등급과 레코드 시각을 함께 저장하므로 순위 계산에 파일을 다시 읽지 않는다. 순위는 SQL이 아니라 워커의 JS에서 계산한다 — 매치의 `(path, tier, ts, rowid)`를 한 번만 가져와 정렬하고, 반환할 행의 본문만 다시 읽는다. 같은 계산을 CTE와 상관 서브쿼리로 SQL에 넣었을 때 `error`(매치 48,402건) 한 번에 57.6초가 걸렸다(CTE가 실체화되지 않아 FTS 질의가 세션마다 다시 돈 것으로 추정, 미확인). JS로 옮긴 같은 질의는 160ms였다. 세션 안에서는 등급 → 최근 순, 세션 사이에서는 그 세션의 최고 등급 → 가장 최근 매치 시각 순이다. FTS5의 `bm25`는 쓰지 않는다 — trigram 토큰에서의 관련도가 실제로 쓸모 있는지 측정하지 않았다.

## 데이터 흐름

```
기동
  serve → 워커 시작 → 등록 세션을 mtime 최근 순으로 동기화
                      (최근 세션이 먼저 검색 가능해진다)

검색 요청
  /api/search?q= → 워커: 등록 세션의 지문 확인 → 바뀐 파일만 끝부분 색인
                        → 질의 (3글자 이상 trigram MATCH, 2글자 bigram MATCH, 1글자 LIKE)
                        → 등급·시각으로 정렬, 세션별로 묶고 상한 적용
                 ← 응답에 매치의 uuid와 색인 상태(완료 여부, 실패 세션) 포함

매치를 누름
  #session/{id}/uuid/{uuid} → 세션 열기(세션 인덱스 구축)
                            → /api/session/:id/attribution?uuid= → 조각 펼침
```

**귀속은 이동할 때만 한다.** 귀속의 목적은 매치에서 조각으로 이동하는 것이고, 세션 인덱스가 제외한 레코드의 매치를 빠뜨리지 않는 일은 색인이 맡는다. 전 세션 응답에서 반환할 세션마다 세션 인덱스를 만들면 메인 스레드가 그동안 멈춘다 — 실측 첫 검색 5.9초, 그동안 `/api/sessions` 최대 5.6초 대기. 세션 하나 검색은 세션이 이미 열려 있어 인덱스가 있으므로 응답에서 귀속한다.

**에러 경로.**

- 파일 읽기 실패 → 그 세션만 실패로 기록하고 응답에 포함한다. 결과에서 조용히 빠지지 않는다
- `ino`가 바뀌었거나 파일이 색인 오프셋보다 짧아짐 → 그 파일의 행을 지우고 처음부터 다시 색인한다
- DB 파일이 손상되거나 스키마 버전이 다름 → 파일을 지우고 처음부터 다시 만든다 (색인은 캐시다)
- 첫 생성 도중 검색 → 그때까지의 결과와 "N/M 세션 색인됨"을 함께 돌려준다

## 고려한 대안 & 기각 이유

**대안1: 원시 스캔 + 워커 병렬화 + 결과 스트리밍.** 저장소와 무효화 문제가 없다. 그러나 매 검색이 6.74GB를 읽고, 대소문자·이스케이프·순위 문제는 그대로 남는다. 1초 목표를 만족한다는 근거가 없다(미실측).

**대안2: contentless 색인 (`content=''`).** 표본에서 크기가 2/3(310MB → 205MB)였다. 2글자 검색을 `LIKE`로 대신할 원문이 없어 기각했다. 한국어는 2글자 낱말이 흔하다.

**대안8: 2글자 검색을 `LIKE`로 두고 일찍 멈추기.** 최근 행부터 훑다 상한에 닿으면 멈추면 빠르다. 그러나 "N건 중 M건"의 N이 부정확해지고 정렬(등급 → 최근 순)이 바뀐다. 기각.

**대안9: 화면에서 느리다고 알리기.** 속도가 그대로라 기각.

**대안3: `detail=none`/`detail=column`.** 가장 작지만(153~217MB) 3글자를 넘는 검색어에서 FTS5가 "phrase queries are not supported" 오류를 낸다. 기각.

**대안4: 세션 파일마다 별도 색인 파일.** 세션 단위 무효화가 단순해지지만, 전 세션 검색이 파일 1,700개를 여는 일이 된다. 기각.

**대안5: 메인 스레드에서 동기 질의, 색인 생성만 워커.** 3글자 이상 질의는 1ms 수준이라 메인에서 돌려도 된다. 그러나 2글자 `LIKE`가 약 1초 걸리고, 같은 DB를 두 연결이 나눠 쓰면 동기화 직후 읽기 시점을 맞추는 규칙이 하나 더 생긴다. 워커 단독 소유가 더 단순하다.

**대안6: 전 세션 응답에서 귀속.** 결과 목록에서 이동할 수 있는 매치와 없는 매치를 미리 나눠 보여줄 수 있다. 그러나 위 "귀속은 이동할 때만 한다"의 실측대로 메인 스레드를 수 초 막는다. 귀속을 워커로 옮기면 막지는 않지만 세션 인덱스를 두 스레드가 따로 들고, 아직 누르지 않은 매치를 위해 첫 검색이 수 초 걸리는 것은 그대로다. 미리 나눠 보여주는 것은 귀속의 부수 효과라 기각했다.

**대안7: 이동할 때 검색 API를 다시 불러 귀속.** API를 늘리지 않는다. 그러나 같은 매치가 다시 나온다는 보장이 없다 — 상한(1,000건) 밖으로 밀리거나 그사이 파일이 바뀌면 이동할 곳을 잃는다. uuid 하나를 조회하는 API(`/attribution`)를 두었다.

## 기준선

실측, 2026-10-15, 이 기기의 실제 세션 1,693개(6.74GB), Node 26.0.0 / SQLite 3.53.4.

| 항목                                      | 값                                                |
| ----------------------------------------- | ------------------------------------------------- |
| 범위를 줄이기 전 전체 색인                | 7,140MB, 236초                                    |
| 줄인 범위(위 표)의 텍스트                 | 775MB (`conversation` 197, `tool` 485, `meta` 93) |
| 줄인 범위의 전체 색인                     | 3,171MB, 141초                                    |
| 가장 오래 걸린 파일 하나 (863MB)          | 15.4초                                            |
| 전 세션 질의, 3글자 이상 (순위·상한 포함) | 7~417ms (최악: 매치 164,731건)                    |
| 전 세션 질의, 2글자 `LIKE`                | 793~1,302ms                                       |

2026-11-10 재측정, 같은 기기·Node 26.0.0, 세션 1,747개(행 132만 개). 단일 실행이라 오차가 있다.

| 전 세션 질의, 2글자 한국어 (보조 색인)              | 24~372ms                                    |

범위를 줄이기 전 `meta` 등급 590MB의 대부분은 `file-history-snapshot`(414MB), `attachment:file`(249MB), `progress`(175MB) 레코드였다. 앞의 둘은 파일 백업 메타데이터와 디스크에 이미 있는 파일 원문이고, `progress`는 최종 `tool_result`에 같은 내용이 다시 나온다.

## 향후 확장 고려사항

- 색인이 너무 커지면 `tool` 등급의 긴 결과를 앞부분만 색인하는 방안을 먼저 검토한다. contentless 전환은 2글자 검색을 포기하는 일이다
- `bm25` 관련도는 순위 개선 요구가 생기면 측정 후 추가한다. 색인 스키마는 그대로 쓸 수 있다
- 세션 목록 필터(제목·경로)를 색인의 `meta` 등급으로 대체할 수 있지만, 지금 필터는 클라이언트에서 즉시 동작하므로 바꿀 이유가 없다
- 뜻이 비슷한 말 검색(임베딩)은 PRD 범위 밖이다. 다시 검토할 때의 기준선은 아래와 같다

### 임베딩 기준선

실측, 2026-10-17, 같은 기기. 대상은 `conversation` 등급 전체(353,299행, 1억 3,826만 자)를 1,000자 단위로 자른 423,516청크다. 무작위 2,000행(2,340청크)을 fastembed(Python, onnxruntime CPU)로 임베딩해 속도를 재고 전체에 곱했다. 모델 로드 시간은 뺐다.

| 모델 (차원)                                   | 전체 생성 | 벡터 (float32) |
| --------------------------------------------- | --------- | -------------- |
| `potion-multilingual-128M` (256)              | 약 36초   | 434MB          |
| `paraphrase-multilingual-MiniLM-L12-v2` (384) | 약 1시간  | 651MB          |
| `multilingual-e5-large` (1024)                | 약 21시간 | 1,735MB        |

`multilingual-e5-large`는 표본 500청크로 쟀다. 재지 않은 것: 검색 품질, 모델 입력 길이 상한에서 잘리는 비율, Node 런타임에서의 속도, 근접 검색 색인의 추가 크기와 질의 시간. 청크는 코드 포인트 단위로 잘라야 한다 — UTF-16 단위로 자르면 서로게이트 쌍이 갈라지고(표본 6건) 토크나이저가 입력을 거부한다.
