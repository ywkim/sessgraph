# Technical Design: `revert` 명령

## Context

> 📋 출처: [docs/prd/20260902-0411-revert-command.prd.md](../prd/20260902-0411-revert-command.prd.md)
>
> 목표: 잇기 작업을 되돌릴 방법이 있어야, 사용자가 안심하고 잇기 작업을 시도할 수 있다. 원본을 훼손하지 않는 방식으로 되돌리고, 되돌린 결과가 잇기 전과 완전히 동일해야 한다.

## 적용하는 기존 ADR

- [ADR-0002: 레코드 보존형 재연결](../adr/ADR-0002-record-preserving-reattach.md) — "레코드 보존형은 되돌리기 쉽다. 삭제는 정보를 없애지만 `parentUuid` 변경은 값 하나를 바꿀 뿐이다"라는 이 ADR의 결론이 `revert`의 설계를 사실상 결정한다. `reattach`가 값만 바꾸고 원본을 백업으로 남겼으므로, `revert`는 새로운 복원 로직을 만들 필요 없이 **백업을 원위치로 되돌리는 문제로 환원**된다
- [ADR-0003: CLI 단독 쓰기](../adr/ADR-0003-cli-writes-web-reads.md) — `revert`도 `reattach`와 마찬가지로 파일을 수정하므로 `src/cli`의 책임이다. 기본 `--dry-run`, 수술 로그 append-only 원칙을 그대로 따른다
- [ADR-0004: 시끄러운 실패](../adr/ADR-0004-schema-drift-defense.md) — 되돌릴 대상을 특정할 수 없는 애매한 상태(백업 누락, 수술 로그와 백업 불일치)를 만나면 추측해서 진행하지 않고 중단한다

## 아키텍처 (How)

```
sessgraph revert <file> [--last | --to <timestamp>]
  → src/cli: {file}.surgery.log 파싱 (append-only, reattach가 남긴 이력)
    → 되돌릴 대상 수술 항목(들)을 시간 역순으로 식별
    → 각 항목의 backupPath가 실제로 존재하는지 확인
  → 계획 출력 (dry-run 기본): "N건의 수술을 되돌립니다. 최종 상태: {backupPath 중 가장 이른 시점}"
  → --commit 있으면:
    → src/cli: 현재 파일을 다시 한번 백업 (되돌리기 자체도 되돌릴 수 있어야 함)
    → 식별된 백업 중 가장 이른 시점의 파일을 원자적으로 원본 위치에 복원
    → {file}.surgery.log에 revert 항목 추가 (일반 수술과 구분되는 subtype)
  → src/core: buildIndex()로 복원 후 상태 재계산 → verify와 동일한 체인 길이 출력 경로 재사용
```

`revert`는 `src/core`에 새 그래프 로직을 추가하지 않는다. 이 명령이 다루는 대상은 그래프가 아니라 **파일 시스템 상태(백업·로그)**이므로 핵심 작업은 `src/cli`에 있다. 복원 후 결과 보고만 `verify`가 정의하는 체인 길이 계산 함수를 재사용한다(PRD "되돌린 뒤에는 정말로 원래 상태로 돌아갔는지 확인할 수 있다 — 연결 상태 확인 기능을 그대로 이용").

## 데이터 흐름

1. 사용자가 `sessgraph revert <file>` 실행. `--last`(기본값) 또는 `--to <timestamp>` 중 하나를 지정
2. `{file}.surgery.log` 파싱. 파일이 없으면 즉시 오류(종료 코드 2) — "되돌릴 수술 이력이 없습니다"
3. **대상 식별**:
   - `--last`: 로그의 마지막 수술 항목 하나만 대상
   - `--to <timestamp>`: 그 시각 이후에 발생한 모든 수술 항목을 대상 (여러 건일 수 있음)
4. 대상 항목들의 `backupPath`가 실제 파일 시스템에 존재하는지 각각 확인. 하나라도 없으면 **중단** — 부분 복원은 원본을 더 알 수 없는 상태로 만들 위험이 있다 (ADR-0004)
5. 복원할 최종 상태 = 대상 항목 중 **가장 이른 시점의 백업** (그 시점이 곧 "그 수술들을 하기 직전" 상태)
6. **dry-run(기본)**: "되돌릴 대상: N건 ({가장 오래된 사유} ~ {가장 최근 사유}). 복원 후 예상 체인 길이: M" 출력, 파일 미변경
7. **`--commit`**:
   - 되돌리기 직전 현재 파일을 다시 백업 (`reattach`와 동일한 명명 규칙, 덮어쓰지 않음) — 되돌리기도 수술이므로 자기 자신도 되돌릴 수 있어야 한다
   - 선택된 백업 파일을 임시 경로로 복사 → 원자적 `rename`으로 원본 교체
   - `{file}.surgery.log`에 한 줄 추가: 일반 `reattach` 항목과 같은 필드(시각, 사유, 백업 경로)를 쓰되 대상 uuid 자리에 "복원 대상 수술 항목 목록"을 기록해 일반 수술과 구분한다
   - 결과 보고: `verify`와 동일한 방식으로 복원 후 체인 길이를 계산해 출력. "구조적으로 N개 노드가 이었던 상태로 돌아갔습니다. 실제 회상 여부는 재개해서 확인하세요" (ADR-0002)

에러 처리 경로: 수술 로그 없음 → 종료 코드 2. `--to` 시각이 로그에 존재하는 어떤 항목보다도 이름(그 이전 수술이 없음) → 종료 코드 2, "해당 시점 이후 수술 이력이 없습니다". 대상 백업 파일 소실 → 종료 코드 2, 어느 백업이 없는지 명시. 쓰기 중 실패 → `reattach`와 동일하게 원자적 교체이므로 rename 전 실패는 원본에 영향 없음.

## 고려한 대안 & 기각 이유

**대안1: 되돌리기 전용 별도 저장소(예: 되돌리기 스택)를 새로 설계**

- 기각 이유: `reattach`가 이미 타임스탬프 백업 + append-only 수술 로그로 모든 상태 전이를 기록하고 있다(ADR-0003). 별도 저장소를 만들면 두 개의 진실 공급원이 생기고, 서로 어긋날 경우(로그는 있는데 백업이 없는 등) 어느 쪽을 믿을지 판단 로직이 또 필요해진다. 기존 백업·로그를 그대로 읽는 쪽이 ADR-0004가 경고한 "정책 불일치"를 반복하지 않는다

**대안2: 특정 uuid 하나의 재연결만 선택적으로 되돌리기**

- 기각 이유: PRD Non-Goals가 명시적으로 범위 밖으로 뒀다. 백업은 특정 시점의 파일 전체 스냅샷이므로, 한 uuid만 골라 되돌리려면 그 시점 이후의 다른 변경과 병합하는 로직이 필요한데 이는 `reattach`가 다루지 않는 새로운 복잡도(3-way merge에 준함)를 요구한다. "한 번의 되돌리기는 작업 전체 단위로"라는 PRD 결정이 이 복잡도를 원천 차단한다

**대안3: `--to`에 수술 로그의 사유(reason) 텍스트나 uuid로 대상을 지정**

- 기각 이유: 사유는 자유 텍스트라 고유성이 보장되지 않고, uuid는 한 수술에 여러 개(대상+부모)가 관여해 모호하다. 시각은 로그에 항상 유일하게 기록되므로(같은 초 충돌은 `reattach` Spec의 백업 파일명 규칙에서 이미 방지) 명확한 식별자다

**대안4: 되돌리기 자체는 백업을 만들지 않음 (어차피 원래 상태로 돌아가는 것이므로)**

- 기각 이유: "원래 상태로 돌아갔다고 생각했는데 실제로는 대상을 잘못 골랐다"는 사용자 실수가 되돌리기에서도 똑같이 발생할 수 있다. 되돌리기 직전 상태를 백업하지 않으면 그 실수를 다시 되돌릴 수단이 없다 — PRD의 "안심하고 시도할 수 있다"는 목표는 되돌리기 자체에도 적용돼야 한다

## 향후 확장 고려사항

- `verify`는 이 명령이 복원한 상태의 체인 길이를 확인하는 데 그대로 재사용된다. `revert`가 별도의 체인 길이 계산을 구현하면 `reattach`/`verify`/`revert` 세 곳의 답이 갈릴 위험이 재현된다(ADR-0004) — 반드시 같은 `src/core` 함수를 호출한다
- 수술 로그의 항목 형식(시각, uuid, 이전/이후 부모, 사유, 백업 경로)은 `reattach` Design에서 이미 고정했다. `revert`가 로그에 남기는 항목도 같은 파서로 읽을 수 있어야 하므로, "복원 대상 목록"을 별도 필드로 추가할 때 기존 파서를 깨지 않는 방식(신규 필드 추가, 기존 필드 형식 유지)을 택한다
- 백업 파일이 누적되며 디스크를 차지하는 문제는 이 Design의 범위 밖이다. 실제로 사용자가 불편을 겪으면 별도 정리 명령을 검토한다 (지금 임의로 만들지 않는다)
