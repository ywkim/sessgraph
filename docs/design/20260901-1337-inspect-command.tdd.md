# Technical Design: `inspect` 명령

## Context

> 📋 출처: [docs/prd/20260901-1337-inspect-command.prd.md](../prd/20260901-1337-inspect-command.prd.md)
>
> 목표: 사용자가 대화 기록에서 끊긴 지점이 몇 군데이고 언제인지, 몇 개 조각까지 도달 가능한지를 몇 초 안에 확인할 수 있게 한다.

## 적용하는 기존 ADR

- [ADR-0001: TypeScript 단일 스택](../adr/ADR-0001-typescript-single-language.md) — 이 명령이 쓰는 파싱·그래프 구축 로직은 `src/core/`에만 있고, `serve` 명령·향후 `reattach`·`verify` 명령이 동일 함수를 재사용한다
- [ADR-0002: 레코드 보존형 재연결](../adr/ADR-0002-record-preserving-reattach.md) — `inspect`는 읽기 전용이라 직접 관련은 없지만, 끊긴 지점 목록의 각 항목은 이후 `reattach` 명령의 입력(대상 uuid)이 되므로 출력 형식이 이를 감안해야 한다
- [ADR-0004: 스키마 드리프트·정책 불일치 방어](../adr/ADR-0004-schema-drift-defense.md) — 이 명령의 핵심 출력(orphan 수, root 수)이 바로 그 ADR이 다룬 "조용한 오답" 위험의 당사자다. 아래 "고려한 대안 & 기각 이유"에서 구체화한다

## 아키텍처 (How)

```
JSONL 파일
  → src/core: 스트리밍 파싱 (1줄씩, 전체를 메모리에 올리지 않음)
    → uuid 인덱스 구축 (구조 필드 + byte offset만 보관, 본문 제외)
    → 중복 레코드 정책 적용 (Spec에 명문화된 정책만 사용)
    → 세그먼트 식별 (parentUuid가 null인 지점을 경계로 분할)
    → root/orphan 판정
  → src/cli: 위 결과를 사람이 읽는 리포트로 포매팅
```

`inspect`는 `src/core`가 노출하는 `buildIndex()` → `IndexResult`를 소비하기만 한다. 그래프 판정 로직을 `src/cli` 안에 재구현하지 않는다 (루트 CLAUDE.md "인터페이스 변경 게이트" 및 `src/cli/CLAUDE.md` "이 스코프가 하지 않는 것" 참고).

`IndexResult`는 세그먼트 목록(각 세그먼트의 시작 root, 끝 leaf, 노드 수, 시작/끝 시각), orphan 목록, 정책으로 해소되지 않은 중복(`UnresolvedDuplicate[]`)을 포함한다. `inspect`는 이 구조체를 그대로 리포트로 옮기며 판정을 새로 하지 않는다.

## 데이터 흐름

1. 사용자가 `sessgraph inspect <file>` 실행
2. 파일 존재 확인. 없으면 즉시 오류 종료 (종료 코드 2)
3. `src/core`가 파일을 1줄씩 스트리밍 파싱하며 인덱스를 구축. 이 과정에서 본문은 읽지 않고 byte offset만 기록
4. 인덱스 구축이 끝나면 세그먼트·root·orphan을 판정
5. **불변식 검사**: uuid를 가진 레코드가 1개 이상인데 parentUuid가 있는 레코드가 0개면 즉시 예외 (스키마 변경 의심 — ADR-0004)
6. 결과를 사람이 읽는 표 형식으로 출력 (`--json` 플래그가 있으면 기계가 읽는 형식으로)
7. 정책으로 해소되지 않은 중복이 있으면 별도 섹션으로 경고 표시 (숨기지 않음)

에러 처리 경로: 파일 없음 → 종료 코드 2. 파싱 중 JSON 파싱 실패한 줄 → 해당 줄 번호와 함께 경고 후 계속 진행(전체 중단 아님, 다만 개수를 최종 리포트에 명시). 불변식 위반 → 종료 코드 2, "스키마 변경 의심" 메시지.

## 고려한 대안 & 기각 이유

**대안1: 전체 파일을 메모리에 올려 파싱**

- 기각 이유: 실측 결과 대형 기록은 본문이 수백 MB에 달한다. 인덱스에 본문을 포함하지 않고 byte offset만 보관하면 같은 파일을 2초 내외로 처리할 수 있다 (ADR-0001 실측 근거)

**대안2: 중복 레코드를 만나면 마지막 값으로 덮어쓰기 (구현이 가장 간단함)**

- 기각 이유: 이 정책은 실제로 끊긴 지점이 있는데도 "끊긴 곳 없음"을 보고하는 사례가 실측에서 나왔다 (ADR-0004). `inspect`의 존재 이유가 정확한 진단이므로, 구현 편의를 위해 이 정책을 쓸 수 없다. 대신 정책을 Spec에 명문화하고, 정책이 다루지 못하는 케이스는 숨기지 않고 별도 경고로 노출한다

**대안3: orphan을 발견하면 즉시 예외로 중단**

- 기각 이유: orphan은 컴팩트가 여러 번 일어난 세션에서 정상적으로 발생하는 상태이지, 도구 오류가 아니다. `inspect`의 목적 자체가 orphan을 세고 위치를 보여주는 것이므로 발견 시 중단하면 안 된다. 예외로 처리하는 것은 "정상 세션에서 성립할 수 없는 상태"(예: parentUuid 필드 자체가 전멸)로 한정한다

## 향후 확장 고려사항

- `serve` 명령(웹 읽기 전용 뷰어)은 이 명령과 동일한 `buildIndex()` 결과를 소비한다. `inspect`의 세그먼트·orphan 판정 로직이 바뀌면 웹 화면도 함께 바뀐다 — 이것이 단일 언어·단일 로직을 택한 이유다 (ADR-0001)
- `reattach` 명령은 이 명령이 출력한 orphan/세그먼트 목록의 uuid를 입력으로 받는다. 따라서 `inspect --json` 출력 형식은 `reattach`의 입력 형식과 미리 맞춰둔다
- 정책으로 해소되지 않은 중복이 실제로 자주 나타나면, 그 패턴을 관찰해 정책을 추가하는 후속 Design 문서를 작성한다 (지금 임의로 정책을 늘리지 않는다)
