# Technical Design: 여러 세션을 한 서버에서 읽기

## Context

> 📋 출처: [docs/prd/20260902-0420-serve-command.prd.md](../prd/20260902-0420-serve-command.prd.md)
>
> 목표: 자기 기록 여러 벌을 한 화면에서 오가며 볼 수 있어야 한다. 처음 화면이 뜨는 시간이 기록 수에 비례해 길어지면 안 되고, 한 벌을 읽지 못해도 나머지는 보이되 못 읽은 것이 무엇인지 드러나야 한다.

`serve`는 세션 파일 하나만 받는다. 다른 세션을 보려면 서버를 끄고 다시 띄워야 하고, 그때마다 인덱싱을 처음부터 다시 한다. 컴팩트 경계가 여러 세션에 걸쳐 생기는 상황 — 이 도구가 존재하는 이유 그 자체 — 에서 사용자는 세션을 오가며 비교하게 되므로, 이 왕복은 실사용에서 반복적으로 발생한다.

이것이 범위 밖으로 기각된 적이 있는지 먼저 확인했다. PRD의 Non-Goal은 "여러 **사용자가** 동시에 같은 화면에 접속"을 제외하고 있는데, 이는 보는 사람이 여럿인 경우를 제외한 것이지 혼자서 여러 벌을 보는 경우가 아니다. 두 축은 다르며, 후자는 어느 문서에도 등장하지 않는 **정의되지 않은 공백**이었다. PRD를 함께 고쳐 이 구분을 명시한다.

단일 세션 전제는 `serve` 한 곳이 아니라 여러 층에 퍼져 있다 (실측):

| 지점                                                   | 전제                                          |
| ------------------------------------------------------ | --------------------------------------------- |
| `runServe`                                             | `positionals[0]` 하나, 없으면 종료 코드 2     |
| `createRequestHandler(filePath, initial)`              | 파일 경로와 상태 보관자를 클로저로 고정       |
| `/api/index`, `/api/segment/{uuid}`, `/api/body?uuid=` | 경로에 세션 차원이 없음                       |
| `buildSegmentDetail(…, filePath, …)`                   | 재연결 명령어 문자열에 파일 경로가 들어감     |
| `src/web/app.ts`                                       | 기동 시 `/api/index` 1회, 세션 선택 수단 없음 |

## 적용하는 기존 ADR

- [ADR-0004: 스키마 드리프트와 암묵 정책은 골든 픽스처와 시끄러운 실패로 방어한다](../adr/ADR-0004-schema-drift-defense.md) — 부분 실패 정책이 여기서 그대로 나온다. 한 세션의 인덱싱이 실패했을 때 목록에서 그 세션을 빼면 "읽을 수 있는 세션이 이게 전부"라는 **틀린 답을 조용히** 내놓는 것이다. ADR-0004가 `orphans: 0`에서 경계한 것과 같은 실패 모드 — 정상 결과와 고장 결과가 값으로 구분되지 않는다. 따라서 실패한 세션도 목록에 남기고 실패 사실을 표시한다
- [ADR-0007: 직접 구현과 기존 도구 도입을 "다져진 엣지 케이스"로 판별한다](../adr/ADR-0007-hand-roll-vs-existing-solution.md) — 상주 정책에 캐시 라이브러리를 도입하지 않는 근거. 아래 "대안3" 참조
- [ADR-0003: CLI가 쓰고 웹은 읽는다](../adr/ADR-0003-cli-writes-web-reads.md) — 세션이 여러 벌이 되어도 읽기 전용과 `127.0.0.1` 바인딩은 그대로다. 보안 전제가 바뀌지 않는 이유는 대상이 전부 같은 사용자의 파일이기 때문이다
- [ADR-0001: TypeScript 단일 스택](../adr/ADR-0001-typescript-single-language.md) — 세션 축은 서버 계층에만 추가하고 `src/core/`는 건드리지 않는다. `buildIndexDetailed`와 `buildSegmentDetail`이 이미 파일 경로를 인자로 받는 순수 함수라, 화면과 명령줄이 같은 계산을 공유한다는 전제가 유지된다

## 아키텍처 (How)

```
runServe(files[])
  └─ SessionRegistry            파일 경로 → 세션 항목
       ├─ id          절대경로 해시 앞 12자 (충돌 안전, 아래)
       ├─ label       사람이 읽는 이름 (표시 전용, 조회 키 아님)
       ├─ state: IndexState | null   ← 아직 안 읽음
       └─ failure: string | null     ← 읽다 실패함

요청 → 세션 id로 항목 조회 → 없으면 그때 인덱싱 → 기존 stale 검사 그대로
```

**세션 `id`는 절대경로의 해시로 만든다.** `sha256(path.resolve(file))`의 앞 12자(hex)를 쓴다. 파일명(basename)을 쓰지 않는 이유는 충돌 때문이다 — Claude Code는 세션을 `~/.claude/projects/{작업경로}/{uuid}.jsonl`로 두어 basename이 uuid처럼 보이지만, 이 도구가 받는 것은 그 경로에 한정되지 않는다. `reattach`가 만드는 백업(`{file}.bak.{시각}`)이나 사용자가 복사해 둔 사본은 서로 다른 디렉터리에서 같은 파일명을 가질 수 있다.

id가 충돌하면 **대안5를 기각한 것과 똑같은 실패**가 한 층 위에서 재현된다 — 서로 다른 세션의 내용이 조용히 섞인다. 경로에 세션 축을 넣어 uuid 혼선을 막아놓고 id 자체를 충돌 가능하게 두면 방어가 무의미하다. 그래서 조회 키(`id`)와 사람이 읽는 이름(`label`)을 분리한다. `label`은 화면에만 쓰고 어떤 조회에도 쓰지 않으므로 중복되어도 안전하다 — 중복될 때 사용자가 구분할 수 있도록 상위 디렉터리까지 포함해 표시한다.

**CLI는 파일 인자를 여러 개 받는다.** `sessgraph serve <file...> [--port n]`. `parseArgs`는 이미 `allowPositionals: true`라 여분의 위치 인자를 배열로 모으므로 파싱 자체는 바뀌지 않고, `positionals[0]`만 보던 것을 전부 쓰도록 바꾸면 된다.

바뀌는 것은 파싱이 아니라 **명령 서술(`src/cli/registry.ts`)이다.** 지금 `serve`의 `positionals`는 `{ name: "file", required: true }` 하나이고, `src/core/types.ts`의 `PositionalDescriptor`에는 "여러 개 받을 수 있다"를 표현할 필드가 없다. 이 서술은 `schema` 명령이 기계 판독 출력으로 내보내는 계약이므로([ADR-0006](../adr/ADR-0006-machine-readable-cli-envelope.md)), 실제 동작만 바꾸고 서술을 그대로 두면 **도구가 자기 인터페이스를 틀리게 광고**하게 된다.

따라서 `PositionalDescriptor`에 가변 인자 여부를 나타내는 필드를 더해야 하고, 이는 `src/core/`가 노출하는 타입 변경이므로 루트 CLAUDE.md의 **인터페이스 변경 게이트** 대상이다. 그 절차 1단계("변경 필요성을 Design 문서에 먼저 기록")를 이 문단으로 갈음한다. 기존 필드를 바꾸지 않고 더하기만 하므로 `CliSchema.schemaVersion`은 1로 유지된다 — 기존 소비자의 판독이 깨지지 않는다.

**파일을 하나만 준 호출의 동작은 바뀌지 않는다.** `sessgraph serve session.jsonl`은 지금처럼 바로 그 세션의 타임라인을 보여준다. 세션이 하나일 때 목록 화면을 먼저 끼워 넣으면 기존 사용자가 클릭을 하나 더 하게 되고, 얻는 것이 없다. 목록은 세션이 둘 이상일 때만 화면에 등장한다. `/api/sessions`는 개수와 무관하게 항상 제공한다 — 화면이 개수에 따라 무엇을 그릴지 정할 뿐, 경로가 개수에 따라 생겼다 사라지지 않는다.

**세션 축은 경로에 넣는다.** `/api/session/{id}/index`, `/api/session/{id}/segment/{uuid}`, `/api/session/{id}/body?uuid=`. 세션 목록 자체는 `/api/sessions`로 따로 낸다. uuid는 세션 안에서만 유일하므로 세션 축 없이 uuid만으로 조회하는 경로는 남기지 않는다 — 남기면 서로 다른 세션의 같은 uuid가 조용히 섞인다.

**기동 시에는 아무것도 인덱싱하지 않는다.** 지금은 기동 시 1벌을 인덱싱하는데, 그 비용은 실측 1초대~2.14초로 기록되어 있다(`src/cli/serve.ts`의 `loadIndexState` 주석은 823MB 파일 기준 약 1초, [원 설계](20260902-0420-serve-command.tdd.md) 대안2는 2.14초 — 파일과 측정 시점이 달라 이 설계는 둘 중 작은 쪽을 하한으로 삼는다). 이를 N벌로 늘리면 첫 화면까지의 대기가 기록 수에 비례해 길어진다 — PRD 성공 기준을 정면으로 위반한다. 대신 세션 목록은 파일 상태 조회만으로 만들고, 인덱싱은 **그 세션을 실제로 열 때** 한다. 한 번 읽은 인덱스는 지금과 같이 상주시킨다.

**실패는 세션 단위로 격리하되 숨기지 않는다.** 지금은 인덱싱 실패가 곧 프로세스 종료(코드 2)다. 세션이 여럿이면 한 벌이 깨졌다고 나머지를 못 보게 하는 것은 과하다. 실패한 세션은 목록에 남기고 실패 사유를 함께 실어 보내며, 화면은 그 항목을 열 수 없는 상태로 표시한다. 목록에서 제외하지 않는 이유는 ADR-0004에 있다.

**보여줄 수 있는 세션이 하나도 없으면 기동하지 않는다.** 인자가 비었거나, 준 경로가 **전부** 존재하지 않는 경우다. 이때만 종료 코드 2를 유지한다 — 보여줄 것이 없는데 서버를 띄우는 것은 사용자에게 빈 화면만 주는 일이다. 반대로 일부만 없으면 기동하고, 없는 항목은 목록에 실패로 남긴다. 이 비대칭의 기준은 "사용자가 화면에서 얻을 것이 남아 있는가"다.

## 데이터 흐름

1. `runServe`가 인자로 받은 파일 경로들을 등록한다. 이 단계에서는 파일 상태만 확인하고 내용을 읽지 않는다. **존재하지 않는 경로는 이 시점에 실패로 확정한다** — 사용자가 그 항목을 열어볼 때까지 미루지 않는다. 오타 난 경로를 목록에 정상인 것처럼 세워두면, 사용자는 그것을 열어보고 나서야 알게 된다. 파일이 없다는 것은 인덱싱 없이 즉시 알 수 있으므로 미룰 이유가 없다
2. 화면이 `/api/sessions`를 요청한다 → 각 항목의 식별자, 표시용 이름, 현재 상태(안 읽음 / 읽음 / 실패)를 응답
3. 사용자가 한 세션을 고른다 → `/api/session/{id}/index` → 그 항목이 아직 인덱싱되지 않았으면 이 요청 안에서 인덱싱하고 상주시킨다
4. 이후 요청은 기존 경로 그대로다 — `refreshIfStale`이 그 세션의 지문만 비교해 필요하면 다시 인덱싱한다. 지문은 세션마다 독립적이다
5. 인덱싱이 실패하면 그 항목에 실패 사유를 기록하고 해당 요청에 오류를 응답한다. 다른 세션의 요청은 영향받지 않는다. 낡은 인덱스로 폴백하지 않는 현재 규칙은 유지된다

**새로 생기는 실패 모드 하나.** `buildIndexDetailed`는 동기 함수라 한 요청의 인덱싱이 끝날 때까지 다른 요청이 끼어들지 못한다 — 지금은 이것이 "잠금 없이도 중복 인덱싱이 없다"는 장점으로만 작용한다(`src/cli/serve.ts`의 `refreshIfStale` 주석). 세션이 여럿이 되면 같은 성질이 **한 세션의 인덱싱이 다른 세션의 요청을 그 시간만큼 막는다**는 결과로도 나타난다. 실측 기준 1초대이고 혼자 쓰는 도구이므로 지금은 감수하되, 이것이 의도된 트레이드오프임을 여기 남긴다.

## 고려한 대안 & 기각 이유

**대안1: 기동 시 지정된 세션을 전부 인덱싱한다**

- 기각 이유: 첫 화면까지의 대기가 기록 수에 비례해 늘어난다. 위 하한인 1초/벌로 잡아도 10벌이면 10초이고, 그중 사용자가 실제로 여는 것은 보통 한둘이다. PRD 성공 기준("기록 수에 비례해 길어지지 않는다")을 직접 위반한다

**대안2: 요청마다 인덱싱하고 상주시키지 않는다**

- 기각 이유: 상주 비용은 사라지지만 조각을 펼칠 때마다 그 비용을 다시 치른다. 이는 [원 설계](20260902-0420-serve-command.tdd.md) 대안2가 이미 기각한 선택지이며, 세션이 여럿이 된다고 해서 그 판단이 달라지지 않는다

**대안3: 캐시 라이브러리로 상주 인덱스를 관리한다 (LRU 축출 등)**

- 기각 이유: 축출이 필요하다는 근거가 아직 없다. 한 사용자가 한 번에 여는 세션은 소수이고, 상한을 넘겼을 때의 동작을 정하기 전에 상한 자체가 관측되지 않았다. [ADR-0007](../adr/ADR-0007-hand-roll-vs-existing-solution.md) 기준으로 여기에는 회피할 다져진 엣지 케이스가 없다 — 지금 필요한 것은 `Map`에 넣고 빼는 일이다
- 다만 **상주 인덱스가 메모리를 실제로 압박하는 것이 관측되면 이 기각은 뒤집힌다.** 축출 정책은 그때 도입한다

**대안4: 서버를 세션마다 하나씩, 포트를 나눠 띄운다**

- 기각 이유: 사용자가 포트 번호를 세션과 대응시켜 기억해야 하고, 세션을 오갈 때마다 다른 주소로 이동해야 한다. "한 화면에서 오가며 본다"는 요구를 만족하지 못한다. 프로세스 수만큼 인덱스가 중복 상주하는 문제도 그대로다

**대안5: 세션 축을 경로가 아니라 조회 문자열로 넣는다 (`/api/index?session=…`)**

- 기각 이유: 세션 지정을 빠뜨린 요청이 문법적으로 유효해져 기본값 처리가 필요해진다. 기본값을 두면 서로 다른 세션의 같은 uuid가 조용히 섞이는 경로가 열린다 — 이 도구에서 가장 비싼 실패 유형이다(ADR-0004). 경로에 넣으면 누락이 곧 404다

**대안6: 디렉터리를 받아 세션 파일을 자동으로 찾는다**

- 기각 이유: 편의성은 높지만 어떤 파일이 세션인지 판별하는 규칙이 새로 필요하고, 그 규칙이 틀리면 사용자가 열려고 한 기록이 목록에 없거나 무관한 파일이 섞인다. 명시적으로 받은 경로만 다루면 이 판별 자체가 없다. 자동 탐색은 별개 요구로 다룬다

## 향후 확장 고려사항

- 세션 목록이 커지면 목록 자체에 검색·정렬이 필요해진다. 지금은 명시적으로 지정한 소수를 전제하므로 범위 밖이다
- "다중 축은 조회 문자열이 아니라 경로에 넣고, 축을 빠뜨린 요청에 기본값을 두지 않는다"는 대안5의 판단은 이 기능에만 국한되지 않는다. 같은 형태의 축이 또 추가되면 `src/cli/CLAUDE.md`에 옮겨 재논증을 없애는 것이 낫다. 지금 옮기지 않는 이유는 사례가 하나뿐이어서다 — 하나짜리 일반화는 다음 사례에서 틀린 것으로 드러나는 쪽이 흔하다
- 세션을 오가는 것이 자연스러워지면, 다음 요구는 "두 세션을 나란히 놓고 비교"가 될 가능성이 높다. 그때는 화면 하나에 목록 두 벌이 놓이므로 [좁은 화면 레이아웃 설계](20260904-1130-responsive-layout.tdd.md)가 컨테이너 쿼리를 채택한 이유가 그대로 작동한다 — 뷰포트가 아니라 상자 자신의 폭에 반응하므로 추가 작업 없이 좁은 칸에서도 겹치지 않는다
- 인덱싱이 다른 세션의 요청을 막는 것이 체감되면, `buildIndexDetailed`를 비동기 경계로 쪼개는 것이 다음 수순이다. 그 시점에는 지금 불필요했던 in-flight 잠금이 함께 필요해진다
