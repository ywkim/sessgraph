# Technical Design: 좁은 화면 레이아웃

## Context

> 📋 출처: [docs/prd/20260902-0420-serve-command.prd.md](../prd/20260902-0420-serve-command.prd.md)
>
> 목표: 손에 든 작은 화면으로도 같은 내용을 읽을 수 있어야 하고, 화면이 좁아져도 글자가 서로 겹치거나 가려지지 않아야 한다.

390px 폭에서 노드 목록의 본문 미리보기가 바로 위 노드의 uuid와 겹치는 것을 실측으로 확인했다. 원인은 두 가지가 겹친 것이다 — `.node-body`의 `margin-left: 80px`가 uuid가 한 줄에 들어간다는 전제로 고정되어 있고, `src/web/app.ts`의 `ROW_HEIGHT = 52`가 `.node`의 실제 높이와 암묵적으로만 동기화되어 있어 uuid 36자가 세 줄로 감기는 순간 그 전제가 깨진다.

즉 이것은 "모바일 지원이 없다"가 아니라 **레이아웃 상수가 특정 폭을 암묵 전제로 삼고 있다**는 문제다. `index.html`에는 이미 `width=device-width` 뷰포트 선언이 있어 좁은 화면을 배제한 적도 없다.

## 적용하는 기존 ADR

- [ADR-0007: 직접 구현과 기존 도구 도입을 "다져진 엣지 케이스"로 판별한다](../adr/ADR-0007-hand-roll-vs-existing-solution.md) — 이 설계의 도구 선택 전부가 이 기준에서 나온다. CSS 커스텀 프로퍼티·`clamp()`·`@container`는 문제의 본체가 브라우저 안에 있으므로 라이브러리 없이 직접 쓴다. 반대로 가변 높이 가상 스크롤은 다져진 엣지 케이스가 실재하므로 직접 구현하지 않는다 — 이 설계는 같은 ADR의 "제약을 설계로 격상시켜 문제를 없앤다"를 택해 그 요구 자체를 만들지 않는다
- [ADR-0001: TypeScript 단일 스택](../adr/ADR-0001-typescript-single-language.md) — 웹 자산도 `tsc` 검증을 거친다. 번들러를 도입하지 않으므로 스타일은 `src/web/app.css` 한 파일로 유지하고 빌드는 `scripts/copy-web-assets.js`의 복사 경로를 그대로 쓴다

## 아키텍처 (How)

```
:root  토큰 레이어 (간격·타이포·레이아웃)
  → @container (max-width: …)  토큰만 재정의
    → .segment / .node  토큰을 소비, 자신은 브레이크포인트를 모른다

src/web/app.ts
  ROW_HEIGHT = 52  ← 상수로 유지 (아래 "행 높이 불변" 참조)
```

**토큰 레이어.** 지금 `:root`에는 색상 7개만 있고 간격·크기는 규칙 없는 리터럴로 흩어져 있다(`padding: 12px`, `margin: 0 0 4px 16px`, `height: 420px`). 이를 8의 배수 그리드 기반 간격 토큰과 타이포 토큰으로 모으고, 좁은 화면에서 달라져야 하는 값은 **선언부를 고치지 않고 토큰만 재정의**한다. 규칙이 한 곳에 모이므로 다음에 값을 바꿀 때 어디를 고쳐야 하는지가 하나다.

**폭에 따라 바뀌지 않아도 되는 값은 애초에 나누지 않는다.** 글자 크기처럼 연속적으로 변해도 되는 값은 브레이크포인트로 쪼개지 않고 `clamp()`로 뷰포트에 보간한다. 분기가 없으면 분기 사이의 어중간한 폭에서 깨질 자리도 없다.

**컨테이너 쿼리를 쓴다.** 반응의 기준은 뷰포트 폭이 아니라 `.viewport`(노드 목록이 실제로 놓이는 상자) 자신의 폭이다. 이 목록은 앞으로 좁은 패널 안에 놓일 수도 있는데, 그때 뷰포트가 넓다는 이유로 넓은 레이아웃을 그리면 같은 겹침이 다시 난다. 반응해야 할 대상은 요소가 실제로 가진 폭이다.

**행 높이 불변.** `ROW_HEIGHT`는 가상 스크롤이 각 행의 위치를 계산하는 기준이므로, 이 값이 콘텐츠에 따라 달라지는 순간 가변 높이 virtualization이 필요해진다. 그 요구를 만들지 않기 위해 **행이 절대 감기지 않게 만든다** — uuid는 좁은 폭에서 앞부분만 노출하고 본문 미리보기는 줄 수를 고정한다. 그러면 행 높이는 콘텐츠와 무관한 진짜 상수가 되고, `ROW_HEIGHT`는 상수로 남을 수 있다.

이때 줄여서 보여준 값은 사용자가 전체를 확인할 방법이 있어야 한다(PRD 성공 기준) — 줄인 표시임을 시각적으로 드러내고, 전체 값은 별도 수단으로 도달 가능하게 한다.

## 데이터 흐름

1. 브라우저가 `.viewport`의 폭을 계산
2. 폭이 임계값 아래면 컨테이너 쿼리가 `:root` 토큰 일부를 재정의 (본문 들여쓰기, uuid 노출 길이, 목록 높이)
3. `.node`·`.segment`는 재정의된 토큰을 그대로 소비해 배치 — 선언부에는 브레이크포인트가 등장하지 않는다
4. 행 높이는 폭과 무관하게 일정하므로 `ROW_HEIGHT` 기반 위치 계산은 재실행이 필요 없다. 화면 회전이나 창 크기 변경 시에도 가상 스크롤 상태를 다시 만들지 않는다

에러 처리 경로: 이 설계에는 실패할 수 있는 실행 경로가 없다 — 전부 선언적 스타일이며 조회하거나 계산하는 값이 없다. 다만 **회귀는 조용하다** — 겹침은 예외를 던지지 않고 화면에서만 틀린다. 따라서 좁은 폭에서 행의 머리와 본문이 화면상 겹치지 않는지를 검증하는 자동 테스트가 이 설계의 안전망이며, 이것 없이는 같은 회귀가 다시 들어와도 아무도 알지 못한다.

## 고려한 대안 & 기각 이유

**대안1: 브레이크포인트마다 행 높이 상수를 따로 준다**

- 기각 이유: 행 높이가 폭에 따라 달라진다는 것을 인정하면서 그 가변성을 상수 몇 개로 근사하는 것이다. 브레이크포인트 사이의 폭(예: 500px)에서 uuid가 두 줄로 감기면 같은 겹침이 그대로 재발한다. 가변 높이 가상 스크롤을 조악하게 흉내내는 것이므로 [ADR-0007](../adr/ADR-0007-hand-roll-vs-existing-solution.md)이 경계한 방향이다

**대안2: 가변 높이 가상 스크롤 라이브러리를 도입한다**

- 기각 이유: 기술적으로는 옳은 해법이지만 **현재 요구에 가변 높이가 없다.** 행마다 높이가 달라야 할 이유가 확인되지 않았고, uuid 축약과 본문 줄 수 고정으로 문제가 사라진다. 없는 요구를 위해 런타임 의존성과 번들러 부재라는 구조적 비용을 먼저 지불하지 않는다
- 다만 이 기각은 요구가 없다는 관찰에 근거하므로, **행마다 높이가 달라야 한다는 요구가 실제로 생기면 즉시 뒤집힌다.** 그때는 직접 구현하지 않고 기존 도구를 도입한다 — 근거는 ADR-0007에 이미 있다

**대안3: CSS 프레임워크나 토큰 패키지를 도입한다**

- 기각 이유: 이 설계가 쓰는 기능(커스텀 프로퍼티, `clamp()`, `@container`, 논리적 속성)은 전부 브라우저 벤더가 검증한 네이티브 스펙이다. 그 위의 패키지는 네이밍 레이어를 한 겹 더할 뿐 회피할 엣지 케이스가 없다(ADR-0007). 토큰이 10여 개 규모인 지금은 직접 선언이 의존성보다 싸다

**대안4: 뷰포트 기준 미디어 쿼리를 쓴다**

- 기각 이유: 노드 목록이 놓인 상자가 뷰포트보다 좁을 수 있으므로 뷰포트 폭은 겹침 여부를 정확히 예측하지 못한다. 컨테이너 쿼리는 이 도구의 실행 환경(로컬 최신 브라우저)에서 폴리필 없이 쓸 수 있어 대가가 없다

**대안5: 좁은 화면 전용 화면을 따로 만든다**

- 기각 이유: 같은 기록에 대해 두 벌의 표시 로직이 생긴다. 두 화면이 다른 답을 내는 실패 모드는 [ADR-0001](../adr/ADR-0001-typescript-single-language.md)이 언어 선택에서 이미 다룬 것과 같은 종류이며, 표시 계층에서 반복할 이유가 없다

## 향후 확장 고려사항

- 토큰이 정착한 뒤 간격·크기 리터럴이 다시 등장하는 것을 막으려면 스타일 린트 규칙으로 기계적으로 강제하는 방법이 있다. 다만 지금은 막을 대상이 아직 발생하지 않았으므로 실제로 재출현이 관측되면 도입한다
- 색상 토큰이 `:root`에 모여 있으므로 사용자 시스템 설정에 따른 어두운 표시는 토큰 재정의만으로 확장할 수 있다. 지금 범위 밖이지만 토큰 레이어가 그 경로를 막지 않도록만 둔다
- 행마다 높이가 달라야 하는 요구(예: 본문 전체를 목록 안에서 펼쳐 읽기)가 생기면 대안2의 기각이 뒤집힌다. 그 시점에 가상 스크롤 구조를 재검토한다
