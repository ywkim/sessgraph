# Technical Design: 표시 시각의 시간대

## Context

> 📋 출처: [docs/prd/20260902-0420-serve-command.prd.md](../prd/20260902-0420-serve-command.prd.md)
>
> 목표: 화면에 표시된 시각을 보고, 사용자가 자신이 그 일을 겪은 시점과 맞는지 바로 알 수 있어야 한다.

`src/web/format.ts`의 `formatTime`은 원본 timestamp 문자열(ISO 8601, `Z` 종료 → UTC)에서 `T`를 공백으로 바꾸고 앞 19자만 자른다. 값을 계산하거나 변환하지 않는다 — 즉 **UTC 시각을 시간대 변환 없이 그대로 보여준다.**

이 화면을 보는 사용자는 대부분 자신의 로컬 시간대(KST 등)로 벌어진 일을 확인하려는 것이므로, 표시된 값을 자기 시간대의 시각으로 읽을 가능성이 높다. UTC와 로컬 시간대가 다르면 사용자는 실제와 다른 시점을 자신이 겪은 시점으로 착각한다 — 예외를 던지지 않고 화면 값만 조용히 틀리는, [ADR-0004](../adr/ADR-0004-schema-drift-defense.md)가 경계한 것과 같은 실패 모드다.

이 문제는 이번에 처음 검토하는 것이다. PRD·ADR·설계 문서 전체를 확인했지만 시간대를 다룬 문서가 없었다 — 검토 후 로컬 변환을 기각한 기록이 아니라, 애초에 논의 대상이 아니었던 공백이다.

## 적용하는 기존 ADR

- [ADR-0007: 직접 구현과 기존 도구 도입을 "다져진 엣지 케이스"로 판별한다](../adr/ADR-0007-hand-roll-vs-existing-solution.md) — 시간대 변환은 브라우저의 `Intl.DateTimeFormat`이 이미 제공하는 네이티브 기능이다. 문제의 본체(각 지역의 표기 규칙, DST 규칙)가 브라우저 안에 있으므로 라이브러리 없이 직접 쓴다
- [ADR-0004: 스키마 드리프트와 암묵 정책은 골든 픽스처와 시끄러운 실패로 방어한다](../adr/ADR-0004-schema-drift-defense.md) — "조용히 틀린 값을 보여주는" 실패 모드를 이 설계가 다루는 근거

## 아키텍처 (How)

```
formatTime(timestamp: string | null): string
  ISO 문자열 파싱 (Date 객체화)
    → Intl.DateTimeFormat(undefined, {...}).format(date)
      undefined locale = 브라우저 자신의 로캘/시간대 설정을 그대로 따른다
```

`Date` 객체는 UTC 기준 시각을 내부에 그대로 들고 있고, 표시 시점에만 실행 환경의 시간대로 변환한다. `formatTime`은 이 표시 변환 한 곳만 담당하며, 저장·전송 경로의 timestamp 값 자체는 손대지 않는다(그 값은 여전히 UTC ISO 문자열로 API를 오간다) — 표시 계층에서만 지역화한다.

## 데이터 흐름

1. `/api/index`, `/api/segment/:uuid`가 UTC ISO 문자열을 그대로 응답 (변경 없음)
2. `formatTime`이 이 문자열을 `Date`로 파싱해 사용자 브라우저의 로컬 시간대로 변환한 뒤 표시용 문자열을 만든다
3. `null`이면 빈 문자열을 반환한다 (기존 동작 유지)

에러 처리 경로: 파싱 불가능한 문자열이 들어오면 `Date`는 `Invalid Date`를 만든다. 이 상태로 조용히 빈 칸이나 "Invalid Date" 문자열을 표시하면 [ADR-0004](../adr/ADR-0004-schema-drift-defense.md)가 경계한 것과 같은 조용한 실패가 된다 — 파싱 실패를 감지해 원본 문자열을 그대로 보여주는 fallback을 둔다(값이 사라지는 것보다 가공 전 원본이 보이는 편이, 사용자가 이상을 알아챌 단서가 된다).

## 고려한 대안 & 기각 이유

**대안1: 지금처럼 UTC를 그대로, 대신 "UTC" 라벨을 붙인다**

- 기각 이유: 사용자가 매번 자기 시간대와의 오프셋을 암산해야 한다. 이 화면의 목표는 "이 시각이 내가 겪은 시점과 맞는지 바로 안다"이므로, 변환 없이 라벨만 붙이는 것은 성공 기준을 충족하지 못한다

**대안2: 서버(`serve` 프로세스)가 실행되는 호스트의 시간대로 변환한다**

- 기각 이유: 이 도구는 로컬에서 실행되는 개인용 CLI이므로 보통 서버와 브라우저가 같은 기기다. 다만 원격 접속(다른 시간대의 기기에서 이 서버에 접속) 시나리오가 생기면 서버 시간대는 틀린 답을 준다. 브라우저의 `Intl.DateTimeFormat`은 항상 "보는 사람"의 시간대를 쓰므로 이 시나리오에서도 맞는 답을 낸다

**대안3: 시간대를 사용자가 화면에서 직접 선택하게 한다**

- 기각 이유: PRD에 이런 요구가 없고, 브라우저가 이미 정확한 기본값(사용자의 시스템 설정)을 제공한다. 없는 요구를 위해 UI 상태(선택값 저장 등)를 새로 만들지 않는다

## 향후 확장 고려사항

- 상대 시각 표시("3일 전")가 필요해지면 이 위치(`formatTime`)에서 같은 `Intl.RelativeTimeFormat` 네이티브 API로 확장할 수 있다. 지금은 요구가 없으므로 다루지 않는다
