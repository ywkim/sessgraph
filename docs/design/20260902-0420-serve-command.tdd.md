# Technical Design: `serve` 명령

## Context

> 📋 출처: [docs/prd/20260902-0420-serve-command.prd.md](../prd/20260902-0420-serve-command.prd.md)
>
> 목표: 끊긴 지점이 여러 개인 긴 기록에서, 조각별 시간순 그림으로 전체 구조를 한눈에 파악하고, 조각을 펼쳐 내용을 확인하며, 이을 지점을 눈으로 고를 수 있게 한다. 이 화면은 보여주기만 하고 실제 변경은 CLI가 한다.

## 적용하는 기존 ADR

- [ADR-0001: TypeScript 단일 스택](../adr/ADR-0001-typescript-single-language.md) — 이 명령이 화면에 그리는 세그먼트·orphan 판정은 `inspect`가 쓰는 `buildIndex()` 결과를 그대로 소비한다. 웹이 자체 파싱을 하면 CLI 리포트와 화면이 다른 답을 내며, 이 ADR이 단일 언어를 택한 이유가 무효가 된다
- [ADR-0003: 웹 읽기 전용, CLI 단독 쓰기](../adr/ADR-0003-cli-writes-web-reads.md) — 서버는 쓰기 API를 갖지 않고 `127.0.0.1`에만 바인딩한다. 절단 지점마다 **복사 가능한 `reattach` 명령어**를 표시하는 것이 웹→CLI 핸드오프의 전부다 (중간 파일 포맷 없음)
- [ADR-0004: 시끄러운 실패](../adr/ADR-0004-schema-drift-defense.md) — 정책으로 해소되지 않은 중복 등 도구가 판단하지 못한 케이스를 화면에서 숨기지 않고 표시한다 (`src/web/CLAUDE.md` "표시 규칙")

## 아키텍처 (How)

```
sessgraph serve <file> [--port N]
  → src/core: buildIndex()로 인덱스 구축 (inspect와 동일 함수, 1회)
  → src/cli: 인덱스를 메모리에 상주시킨 채 localhost HTTP 서버 기동
    → GET /                     정적 자산 (HTML/JS/CSS)
    → GET /api/index            IndexResult (본문 없음 — 세그먼트·orphan·중복 경고만)
    → GET /api/segment/:root    해당 세그먼트의 노드 목록 (구조 필드만, 본문 없음)
    → GET /api/body?uuid=X      단일 노드의 본문 — byteOffset으로 seek해서 그때 읽음
  → src/web: 세로 타임라인 렌더 (조각 기본 접힘) + 펼칠 때 가상 스크롤
```

핵심 비대칭은 **노드 수는 적고(실측 10,726개) 본문은 크다(수백 MB)**는 점이다(`src/core/CLAUDE.md`). 서버는 인덱스만 상주시키고, 본문은 화면에 실제로 보이는 노드에 한해 `byteOffset`으로 seek해서 응답한다. 파일 전체를 문자열로 메모리에 올리지 않는다.

`src/web`은 JSONL을 직접 파싱하지 않는다. 브라우저가 받는 것은 이미 `src/core`가 판정을 끝낸 `IndexResult`와 그 하위 조회 결과뿐이다 — 세그먼트 경계나 orphan 여부를 프런트엔드가 다시 계산하지 않는다.

## 데이터 흐름

1. 사용자가 `sessgraph serve <file>` 실행
2. `buildIndex()`로 인덱스 구축 (`inspect`와 동일 비용 — 실측 2.14초). 실패하면 서버를 띄우지 않고 종료 코드 2
3. `127.0.0.1`의 지정 포트(기본값은 Spec에서 정의)에 HTTP 서버 기동. 접속 URL을 stdout에 출력
4. 브라우저가 `/`를 요청 → 정적 자산 응답
5. 프런트엔드가 `/api/index` 요청 → 세그먼트 목록(각각 root/leaf/nodeCount/시작·끝 시각/rootSubtype), orphan 목록, 해소되지 않은 중복 목록을 받음. **본문은 포함하지 않는다**
6. 세로 타임라인 렌더: 세그먼트를 시작 시각 순으로 배치, 각각 기본 **접힌 상태**. 초기 렌더 대상은 세그먼트 수(실측 39개)뿐이므로 즉시 그려진다
7. 각 세그먼트 경계(root가 `compact_boundary`인 지점)에 복사 가능한 `sessgraph reattach ... --uuid X --parent Y --reason "..."` 문자열을 표시. `--parent`에는 직전 세그먼트의 leaf uuid를 채워 둔다
8. 사용자가 세그먼트를 펼침 → `/api/segment/:root`로 그 세그먼트의 노드 목록(구조 필드만) 요청 → 가상 스크롤로 화면에 보이는 노드만 DOM에 올림
9. 화면에 보이는 노드에 대해서만 `/api/body?uuid=X` 요청 → 서버가 `byteOffset`/`byteLength`로 seek·read해서 해당 줄만 응답
10. 사용자가 `Ctrl-C`로 서버 종료

에러 처리 경로: 파일 없음 → 서버 미기동, 종료 코드 2. 인덱싱 중 불변식 위반(ADR-0004) → 서버 미기동, 종료 코드 2. 포트가 이미 사용 중 → 종료 코드 2, 다른 포트를 안내(임의로 다른 포트를 고르지 않는다 — 사용자가 어디에 접속해야 하는지 모호해진다). 서버 기동 후 원본 파일이 외부에서 변경됨 → 상주 인덱스는 갱신되지 않으므로 `/api/body`의 seek 결과가 인덱스와 어긋날 수 있다. 이 경우 응답의 uuid가 요청한 uuid와 일치하는지 검증해 불일치면 오류를 반환하고 화면에 "파일이 변경되었습니다. 서버를 재시작하세요"를 표시한다 (조용히 엉뚱한 본문을 보여주지 않는다).

## 고려한 대안 & 기각 이유

**대안1: 서버 없이 정적 단일 HTML 파일을 생성 (기존 도구 다수가 택한 방식)**

- 기각 이유: 정적 HTML은 본문 전체를 파일에 인라인해야 한다. 실측 세션(829MB, 본문 수백 MB)에서는 결과 HTML이 수백 MB가 되어 브라우저가 열지 못하거나 극도로 느려진다. PRD 성공 기준("매우 큰 기록이라도 오래 기다리지 않아야 하고, 펼칠 때 즉시 반응")을 만족할 수 없다. 서버 방식은 인덱스만 상주시키고 본문을 지연 로딩하므로 파일 크기와 무관하게 초기 렌더가 세그먼트 수에만 비례한다.
- 다만 이 트레이드오프는 방향이 하나가 아니다. 정적 HTML은 서버 프로세스 없이 파일 하나를 공유·보관할 수 있다는 장점이 있고, 실제로 그 방식으로 fork point 시각화를 구현한 선행 도구가 존재한다. 본 설계가 서버를 택한 것은 **본문 크기가 이 도구의 지배적 제약**이기 때문이며, 본문을 제외한 구조 요약만 내보내는 정적 출력은 향후 별도 기능으로 검토할 수 있다 (지금 범위 밖).

**대안2: 서버가 인덱스를 상주시키지 않고 요청마다 파일을 다시 인덱싱**

- 기각 이유: 인덱싱은 실측 2.14초다. 노드를 하나 펼칠 때마다 이 비용을 치르면 PRD의 "그때그때 즉시 반응" 기준을 만족할 수 없다. 인덱스는 프로세스 수명 동안 상주시키고, 파일이 외부에서 바뀐 경우는 위 "에러 처리 경로"의 uuid 일치 검증으로 감지한다

**대안3: 프런트엔드가 JSONL을 직접 받아 브라우저에서 파싱**

- 기각 이유: `src/web/CLAUDE.md`가 금지한다. 브라우저에서 파싱하면 세그먼트·orphan 판정 로직이 두 벌이 되고, 중복 처리 정책이 갈리는 순간 CLI 리포트와 화면이 다른 답을 낸다 — ADR-0004가 실측으로 확인한 실패 모드다. 또한 수백 MB 본문을 브라우저 메모리에 올리는 대안1과 같은 문제가 생긴다

**대안4: force-directed 그래프 레이아웃으로 구조를 표현**

- 기각 이유: 세션은 시간 순서가 있는 체인이다. force-directed는 노드를 물리 시뮬레이션으로 배치하므로 시간 순서를 뭉개고, 매 렌더마다 배치가 달라져 "어디가 언제 끊겼는가"를 읽기 어렵다. 세로 타임라인 고정 배치를 쓴다 (`src/web/CLAUDE.md` "렌더링 제약")

**대안5: 화면에서 직접 재연결을 실행할 수 있게 함**

- 기각 이유: ADR-0003이 이미 기각했다. 세션 파일에는 자격증명과 개인정보가 들어 있고, 이를 수정할 권한을 브라우저에서 도달 가능한 경로에 두지 않는다. 웹→CLI 핸드오프는 복사 가능한 명령어 문자열로 충분하다

## 향후 확장 고려사항

- `verify`가 정의한 `findSegmentForUuid()`([verify Design](20260902-0411-verify-command.tdd.md))는 "이 노드에서 몇 개까지 연결되어 있는가"를 조회한다. 화면에서 노드를 클릭했을 때 같은 정보를 보여주려면 이 함수를 그대로 재사용한다 — 웹에서 다시 계산하지 않는다
- `reattach`/`revert`로 파일을 수정한 뒤 화면을 갱신하려면 현재는 서버 재시작이 필요하다. 이 불편이 실제로 문제가 되면 인덱스 재구축 엔드포인트를 검토한다 (지금 임의로 만들지 않는다 — 쓰기 API가 아니라 읽기 갱신이므로 ADR-0003과 충돌하지는 않는다)
- 본문을 제외한 구조 요약만 정적 파일로 내보내는 기능(대안1의 장점만 취하는 방향)은 공유·보관 요구가 실제로 생기면 별도 PRD로 다룬다
